  - `vllm/entrypoints/cohere/serving.py`
  - `vllm/entrypoints/openai/chat_completion/serving.py`

### Summary

**What changed and why**  
Refactors the shared OpenAI chat streaming generator into a new chat_completion_stream_generator_raw method that yields ChatCompletionStreamResponse or ErrorResponse objects without SSE framing, while the existing chat_completion_stream_generator serializes those objects and appends [DONE]. Cohere and Anthropic adapters now consume raw chunks directly instead of re-parsing serialized JSON, so parser and generation errors are preserved and surfaced as their native error events rather than being lost or replaced by validation errors.

**Technical impact**  
Changes the internal streaming contract for Cohere and Anthropic serving paths and adds a new public-ish generator method on OpenAIServingChat. Cohere now closes open blocks and emits message-end(ERROR) plus [DONE] even when no normal chunk was seen, and Anthropic closes any active block, emits an error event with the sanitized original message, and omits message_stop on failure. OpenAI output framing, usage metadata, and [DONE] termination are intended to remain byte-compatible, including a new fallback error frame when serialization itself fails.

**Potential risks**  
The refactor touches three API adapters and the core streaming loop, so subtle regressions in OpenAI frame shape, usage chunk emission, or [DONE] placement are possible despite the comparison tests. Anthropic now raises RuntimeError from an ErrorResponse and relies on the outer exception handler to sanitize and emit the error, which could alter error codes or messages if the handler changes. Cohere's removal of the [DONE] break path and the changed _chat_completion_stream_to_v2 signature may affect any other callers or tests not updated here. Validation used controlled CPU engine outputs only, with no GPU or real model generation, so end-to-end streaming behavior under load is not directly exercised.

**Key insights**  
The root cause was that adapters assumed every streamed item was a serialized normal chunk, so an ErrorResponse envelope triggered a second validation failure and masked the original error. Moving serialization to the API output boundary is a clean separation of concerns and lets each protocol emit its own error semantics. The added tests cover errors before the first chunk and during text, thinking, and tool-use blocks, which are the meaningful edge cases for this bug.

  - `vllm/v1/watermarking/gpu_sampler.py`
  - `vllm/v1/worker/gpu/sample/sampler.py`
  - `vllm/v1/worker/gpu/sample/states.py`

### Summary

**What changed and why**  
This PR speeds up the small-batch split top-p Triton pipeline in two ways: (1) _topp_split_count now keeps doubling the split count past one program per SM as long as slices remain at least _SPLIT_MIN_SLICE (7168) vocab entries, and (2) apply_top_k_top_p/apply_top_k_top_p_triton gain a has_topp_only_rows hint so the split pipeline is skipped entirely when no row is top-p-only. MRV2's SamplingStates.get_top_k_top_p now also returns this flag (computed host-side from numpy state, no sync), and call sites in sampler.py, gpu_sampler.py, and diffusion_gemma.py pass it through. Tests were extended for B=48, large-vocab mixed batches, the skip path, and the new flag.

**Technical impact**  
Changes the split count S for the Triton top-k/top-p path, which affects spec-decode verification and non-fused sampling on CUDA and ROCm. Reported gains are up to ~2.5x on top-p-only and mixed batches at B>=32, with all-top-k batches improving 1.00-1.21x under MRV2 (split launch skipped) but slightly regressing (0.90-0.98x) for callers that do not pass the hint. The API signature of get_top_k_top_p changes (now returns a 3-tuple and takes vocab_size), and apply_top_k_top_p gains a keyword arg, so all callers must be updated. Workspace size and warmup dispatch coverage are unchanged.

**Potential risks**  
The has_topp_only_rows flag is a correctness-critical hint: passing False when a top-p-only row exists would silently drop top-p masking for that row, so correctness depends on every caller computing it accurately (the default True is safe). Output can change at the p boundary because different S values alter fp32 summation order and tie handling; the PR documents small kept-mass differences and notes a pre-existing per-8192-block tie-count restart bug that shifts over/under-keep counts. ROCm and GPUs with fewer than 132 SMs were not measured, so the new split-count rule could regress there. The 7168 floor is tuned to specific vocab sizes and may not generalize.

**Key insights**  
The core insight is that the step kernels are latency-bound at one program per SM, so splitting further (while keeping slices large enough to amortize per-program overhead) helps more than pure occupancy targeting, which shrinks slices too far. The hint is valuable because the split pipeline is otherwise launched as 7 kernels that all exit immediately for all-top-k batches. The PR is well-validated with microbenchmarks, A/A noise floors, real MiMo logits, serving ITL, and GSM8K accuracy, but the flag's correctness contract and unmeasured ROCm/small-SM behavior are the main things reviewers should scrutinize.

**What changed and why**  
Fixes a bug in the split top-p mask Triton kernel (_topp_sb_mask_kernel) where the count of tied boundary-value copies (num_preceding) was reset at every 8192-entry block, causing slices longer than one block to keep too many copies of the boundary value. **Technical impact**

**Potential risks**  
The added reduction runs inside the block loop and could marginally affect performance for tied rows, though only on the tie path. The fix relies on counting all copies (kept or not) via dmask, which is claimed equivalent to the monolithic kernel's kept-copy counting; any subtle divergence in tie semantics between the two kernels would need verification. Test coverage depends on GPU SM count (B=64 yields multi-block slices on GPUs with <256 SMs), so the regression may not trigger on very large-SM hardware.

**Key insights**  
This is a genuine correctness bug affecting all current vocab sizes on current GPUs (S=1 or 2 at batch 64), not an edge case. The existing test_topp_tie_break_deterministic could not catch it because all ties fit in one block. The new test is well-constructed: the -8.0 tail avoids the keep-everything fallback and p=0.75 places the boundary mid-copy to prevent fp32 reference off-by-one.
