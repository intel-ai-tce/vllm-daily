  - `vllm/model_executor/layers/quantization/utils/gptq_utils.py`
  - `vllm/transformers_utils/config.py`

### Summary

**What changed and why**  
Fixes a GPTQ loading bug where checkpoints whose weights are not named model.safetensors (e.g. gptq_model-4bit-128g.safetensors) failed to load on a cold cache. The metadata lookup relied on HfApi.get_safetensors_metadata, which only knows model.safetensors and its index, so it raised NotASafetensorsRepoError and the quantized-layer list came back empty, causing every linear layer to be built unquantized. The fix adds a repo file-listing fallback that reads headers of all *.safetensors files, and treats an empty module list as 'unknown' rather than 'nothing quantized'.

**Technical impact**  
Adds _read_safetensors_metadata_in_repo in vllm/transformers_utils/config.py, invoked after the fixed-name lookup fails and before the local-cache fallback, fetching only headers via parse_safetensors_file_metadata. Changes is_layer_gptq_quantized in gptq_utils.py so an empty quantized_layers list returns True (assume quantized), which is the safe default since loading GPTQ weights unquantized cannot work. Adds a warning_once when no metadata can be retrieved by any route, and extends tests in test_auto_gptq.py and test_config.py.

**Potential risks**  
The empty-list-means-quantized change is a behavioral inversion that could mask genuinely empty or malformed metadata, potentially attempting to load unquantized checkpoints as GPTQ and producing confusing downstream errors instead of a clear failure. The new repo-listing path adds an extra Hub API call (list_repo_files plus per-file header parses) on the failure path, which could add latency or hit rate limits for repos with many safetensors files. The broad except Exception in the new helper silently returns {} and only logs at debug level, so real errors may be hard to diagnose.

**Key insights**  
The root cause was a warm shared cache masking the bug: the local-cache fallback matches *.safetensors and found the oddly named file, so CI only ever passed with a warm cache. AWQ avoided the issue because it derives the complement, so an empty answer excludes nothing rather than everything. The fix aligns the metadata lookup with how the weight loader already locates weights, and the empty-list semantics change is the key correctness guard for offline or metadata-less scenarios.

### Summary

**What changed and why**  
This PR replaces the probe-release-bind (and child-side bind plus address report-back) approach for frontend ZMQ ports with a supervisor-owned listener transfer model. The supervisor now binds raw TCP/IPC listeners before launching engines or frontends, records resolved endpoints, passes the listener descriptors to Python children (via ZMQ_USE_FD) and Rust subprocesses (via pass_fds and a new bind_listener API), then closes its own descriptor copies after spawn. This eliminates the TOCTOU race where a port could be claimed between allocation and bind, and removes the frontend-to-supervisor address report protocol and its pipe/stdout coordination.

**Technical impact**  
Introduces new abstractions (ZmqListener, EngineZmqBindAddresses, EngineZmqListeners) and changes the TransportMode::Bootstrapped Rust variant from string addresses to raw listener fds. The Rust frontend adopts inherited descriptors through zeromq's bind_listener, requiring a pinned upstream git revision of zmq.rs since no crates.io release contains the API. Python make_zmq_socket gains a listener parameter using ZMQ_USE_FD, and APIServerProcessManager/RustFrontendProcessManager now transfer and close listener descriptors. Ray DP actors receive resolved endpoints at construction time, and the single-process MPClient path binds its own sockets and reads LAST_ENDPOINT.

**Potential risks**  
The change is broad and touches process lifecycle, fd ownership, and cross-language boundaries, so subtle descriptor leaks or double-closes are possible if any path fails to close parent copies or mishandles spawn failures. Pinning zeromq to an unreleased git master revision is a supply-chain and reproducibility risk until a crates.io release ships the API. The new fd-adoption path validates fds with fcntl and assumes TCP/IPv6/UNIX domains, so unexpected descriptor types or platforms could fail. IPC cleanup semantics (unlinking paths only when the bind succeeded) and shutdown ordering (terminate frontends before closing listeners) are critical and could regress if reordered. The large diff and removal of the report-back protocol mean any missed call site still passing addresses instead of listeners would break startup.

**Key insights**  
The core insight is that keeping the kernel listener bound continuously from allocation through frontend startup structurally eliminates the TOCTOU race rather than narrowing its window, which is stronger than the child-side bind plus report-back approach in #51033. The ownership model is explicit and well-documented: bind templates, owned listeners, and resolved addresses are separated into distinct types, and descriptor ownership is transferred exactly once. The PR includes deterministic red/green fault-injection validation for both Python and Rust paths, which is strong evidence, though the zeromq git pin and the breadth of the change warrant careful maintainer review of fd lifecycle and shutdown ordering.

### Summary

**What changed and why**

This PR removes that ROCm-only Triton kernel and Torch path and routes ROCm prefill through the shared combine_topk_swa_indices kernel already used by CUDA, gaining the SWA bounded-replay bound, SWA-only guard, and JIT warmup. The shared kernel also gains two guards: clamping both lengths at zero for negative positions (warmup batches) and preserving -1 for invalid top-k candidates instead of mapping them to a previous request's row.

**Technical impact**  
Behavior changes in the shared kernel affect both CUDA and ROCm paths, but the guards are designed to leave well-formed input untouched. The shared kernel is now on the critical path for ROCm prefill, so any regression in the new guards or in the shared kernel affects both CUDA and ROCm. The negative-position clamp and -1 preservation change index semantics for edge cases; although tests cover seq_len below query_len, seq_len zero, compress_ratio zero, non-zero query_start_loc base, -1 candidates, and windows 64/128/256, other shapes or metadata combinations may not be covered. Removing the ROCm-specific kernel also removes a previously documented gfx950 safety workaround, so the shared kernel must be verified safe on that hardware. The PR description notes #59136 is no longer needed, which may affect coordination with that change.

**Key insights**  
This is a consolidation and performance PR: it deletes a ROCm-specific workaround in favor of the shared kernel and adds defensive guards that make the shared kernel robust to warmup and invalid candidates. The test strategy of copying the old Torch path verbatim as a reference is sound for preventing drift. The main review focus should be on the two new guards in cache_utils.py and on confirming the shared kernel is safe on gfx950 for all prefill metadata shapes, since the removed ROCm kernel existed specifically to avoid an out-of-bounds access there.
