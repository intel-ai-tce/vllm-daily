  - `vllm/models/qwen4_exp/amd/qsa.py`
  - `vllm/models/qwen4_exp/nvidia/qsa.py`

### Summary

**What changed and why**  
The PR removes the hardcoded 4x M-RoPE cos/sin cache headroom for Qwen3-VL, Qwen3.5, and Qwen3.8 by introducing a configurable positions_factor (default 4) threaded through get_rope, MRotaryEmbedding, and the relevant attention/decoder layers. These models use Qwen3-VL-style positions that never exceed the token count, so the headroom is unnecessary unless video pruning is enabled, which preserves dropped-token positions. It also fixes Qwen3.5's YaRN correction range to use the original context length, matching Transformers.

**Technical impact**  
Reduces per-GPU cos/sin cache memory by 4x (e.g., 256 to 64 MiB for Qwen3-VL at 262k, 512 to 128 MiB for Qwen3.5 with YaRN at 1M) and lowers build peak memory proportionally. Without YaRN the new cache is a bit-exact prefix of the old one, so outputs are unchanged; with YaRN, Qwen3.5 frequencies now match Transformers. ModelConfig.compute_hash now includes video pruning state since it affects cache shape, and drafters inherit the target's pruning setting.

**Potential risks**  
The change touches shared rotary embedding and multiple model files, so any model that relies on the 4x headroom but is not explicitly updated could regress. Qwen3.8 Flash-Next was not validated end-to-end, relying on reasoning about QSA indexer positions. With YaRN, outputs change (though within bf16 noise), which could affect users expecting bit-identical results. The hash change for video pruning could invalidate caches or trigger recompilation unexpectedly.

**Key insights**  
The 4x headroom originated with Qwen2.5-VL video positions and is unnecessary for Qwen3-VL-family models whose positions stay below token count. The design cleanly threads positions_factor through the rope stack with a safe default of 4, and correctly keeps 4x when video pruning is on because pruning retains dropped-token positions. The YaRN correction range fix aligns Qwen3.5 with Transformers and is validated by frequency comparison and end-to-end logprob checks.

  - `tests/model_executor/test_qwen_vl_triton_warmup.py`
  - `vllm/model_executor/warmup/qwen_vl_triton_warmup.py`

### Summary

**What changed and why**  
The Qwen-VL Triton warmup for M-RoPE is now skipped when every module that holds the MRotaryEmbedding as a child sets use_fused_qk_norm_rope_gate, since fused attention reads cos_sin_cache directly and never calls MRotaryEmbedding.forward, making the compiled specialization dead. The change adds an early-return condition in _warm_mrope and parametrizes the existing test over fused-only, non-fused, and mixed rope holders.

**Technical impact**  
Avoids compiling a Triton M-RoPE specialization that is never launched in Qwen3-Next-style fused attention configurations, saving warmup time and avoiding a misleading 'Warmed M-RoPE Triton kernels.' log. Behavior is preserved for any model where at least one rope holder is not fused, such as Qwen4Exp whose QSA indexer shares the rope.

**Potential risks**  
The skip condition relies on the use_fused_qk_norm_rope_gate attribute being present and accurate on every module that directly owns the rope; if a future fused path still invokes MRotaryEmbedding.forward or a holder lacks the flag, the warmup could be incorrectly skipped or retained. The all() over an empty generator would be True, but that case is guarded by the preceding rope is None check, so it is not reachable here.

**Key insights**  
The check correctly scopes to modules that directly hold the rope as a child rather than any module in the model, preventing an unrelated fused module from disabling the warmup. The parametrized test explicitly covers the mixed fused/non-fused case, which would fail under a naive any(...) check, and the fused-only case, which would fail without the early return, giving good regression coverage for the new logic.

Previously the attention-op exclusion only applied under torch.compile via FX graph splitting; this extends the same splitting behavior to breakable cudagraphs, fixing an illegal memory access crash on Nemotron-3-Nano-30B-A3B.

**Technical impact**  
These Mamba ops will now execute eagerly during breakable CUDA graph capture instead of being captured, aligning breakable-cudagraph behavior with the existing torch.compile attention-op exclusion mechanism. **Potential risks**  
Eager breaks reduce CUDA graph coverage for these ops, which may lower performance for Mamba-family models under breakable cudagraphs. The decorator is applied to module-level forward functions, so correctness depends on eager_break_during_capture being safe to apply at these call sites and on the break semantics matching the FX-splitting behavior. Only one model/config was tested, so other Mamba variants or configurations could still exhibit issues.

**Key insights**  
The change is small (5 files, +10 lines) but behaviorally significant because it alters CUDA graph capture semantics for Mamba ops. The PR description provides a clear before/after reproduction (crash vs. working gsm8k), which strongly supports the fix. Reviewers should verify that eager_break_during_capture is a no-op when breakable cudagraphs are disabled and that the decorator placement does not interfere with torch.compile paths.
