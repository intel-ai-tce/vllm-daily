### Summary

**What changed and why**  
Adds internal prefill checkpoints to the FlashInfer GDN prefill backend so Qwen3-Next/Qwen3.5 prompts crossing a prefix-cache block boundary can be prefilled in one pass instead of two, claiming 10-20% TTFT gains. It generalizes the previously Kimi-K3-only MambaPrefillCheckpointExporter into a shared Triton store kernel with optional recurrent_rows, adds a host-side FlashInfer checkpoint plan (gcd stride, cu_starts, row mapping), introduces MambaBase.get_prefill_checkpoint_alignment plus platform block alignment (1056 -> 1088 for Qwen3.5-35B), sizes a workspace buffer at profile time, and warms up all four FlashInfer CP/checkpoint kernel variants.

**Technical impact**  
Behavior changes are gated: only active when the GDN prefill backend resolves to FlashInfer, mamba_cache_mode is align, and every Mamba layer declares a checkpoint alignment; otherwise block size, scheduler splits, and GDN spec stay as on main (Qwen3.8-Flash-Next keeps its 800-token block). **Potential risks**  
The shared exporter/kernel refactor could regress Kimi-K3 or Mamba2 checkpoint paths despite the subclass shim, and the Triton store kernel still compiles on first use due to KV-cache-dependent strides. Validation is SM100-only (FlashInfer also supports SM90/SM120), MRV1 was not validated, and the ~3% larger aligned block plus a finer prefix_match_unit can grow the workspace (up to ~0.5 GiB and ~1 ms/8k step in the worst case). The e2e test now pins gdn_prefill_backend=triton for align-mode LLMs, so the original split-prefill script no longer exercises FlashInfer there; correctness relies on the new FlashInfer-specific test. Benchmark TTFT numbers were not re-measured against main on the latest base commit, so the headline gains are somewhat stale.

**Key insights**  
The design is well-scoped: opt-in via per-layer alignment declarations, no device-to-host syncs (reuses host offsets/query_lens), and graceful fallback to split prefill when any Mamba layer cannot checkpoint. The Qwen4Exp regression analysis (832-token block causing an eager 1344-token tail) is a good example of why alignment must be conditional. Main residual concerns are cross-backend regression risk from the exporter refactor and limited hardware coverage; the test suite is thorough for the new path but the shared-kernel change deserves extra scrutiny.

  - `vllm/v1/kv_offload/tiering/p2p/data/nixl.py`
  - `vllm/v1/kv_offload/tiering/p2p/session/session.py`

### Summary

**What changed and why**  
Moves NIXL peer registration (add_remote_agent plus per-block prep_xfer_dlist, O(num_blocks)) off the scheduler thread by adding a new DataTransport.add_remote_peer_async method with an inline default and a NixlTransport override backed by a single-worker ThreadPoolExecutor. P2PSession now starts registration in _on_connect and defers ConnectAckMsg until the future resolves, using the ack as a safety barrier so a peer cannot fetch before it is registered locally. A per-peer generation counter guards against late registrations reviving reaped peers, and a pending registration counts as session pending work.

**Technical impact**  
Registration work is split into an unlocked _build_peer_handles and a lock-protected _publish_peer, keeping the scheduler thread free during the expensive descriptor build while making the generation check and install atomic. The wire protocol is unchanged and the default add_remote_peer_async preserves behavior for transports with cheap registration. Session close cancels pending registrations and relies on the manager's remove_remote_peer generation bump to release stale handles, and NixlTransport.close shuts down the executor before tearing down the agent.

**Potential risks**  
The change relies on NIXL being safe to call concurrently from the registration worker and the main transfer thread under the default syncMode=NONE, justified only by analogy to NixlConnector rather than by measurement here. The handshake deadline now must exceed remote registration time, so slow registrations could trip the 30s timeout and kill otherwise healthy peers. Performance validation is explicitly outstanding, and the generation guard's correctness depends on remove_remote_peer always being called on reap; any path that closes a session without it could still leak handles.

**Key insights**  
The ack-as-barrier design is the crux: gating ConnectAckMsg on registration completion preserves the invariant that any peer permitted to fetch is already registered, so write_blocks cannot observe an unregistered peer. The generation counter closes a real reap race where a late worker would otherwise publish handles for a peer with no session. The PR is deliberately scoped to registration only, leaving per-step gating for a separate measurement, and the test suite adds deterministic coverage via a defer_registration fake rather than relying on thread timing.

## 3. [[Perf][Model][Qwen4Exp] QSA: decode four FP8 e4m3 bytes per register below sm_89](https://github.com/vllm-project/vllm/pull/60992)


### Base Information

- **PR Number:** #60992
- **Author:** [kimseunghyun-kr](https://github.com/kimseunghyun-kr)
- **Merged By:** [gau-nernst](https://github.com/gau-nernst)
- **Merged time:** 2026-10-13 22:06:17
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/60992/files) (1):**
  - `vllm/models/qwen4_exp/nvidia/ops/qsa.py`

### Summary

**What changed and why**  
The uint8 fallback branch of _maybe_dequant in vllm/models/qwen4_exp/nvidia/ops/qsa.py, used to decode FP8 e4m3 KV cache bytes on GPUs below sm_89, was rewritten from a per-element mask/shift/or sequence to a packed inline PTX asm that decodes four bytes per 32-bit register using shf, lop3, two prmt, and two and instructions. The goal is to cut the cost of the byte-to-fp16 conversion, which is a large fraction of reader time at prefill-sized row counts on A100-class hardware.

**Technical impact**  
Behavior is intended to be identical: the asm produces the fp16 of x * 2^-8 with the 2^8 folded into host scales, matching the previous path including the two NaN codes decoding to +/-480. The PR reports bitwise-equal output versus main for all 256 byte values in each of the four register positions, and 0.64-0.78x reader time at 128-2048 rows on one A100, with no effect on BF16 caches or sm_89+ GPUs since they never enter this branch. Only the uint8 branch body changes; no new syncs or host-side changes.

**Potential risks**  
The change relies on Triton's pack=4 lane mapping (element k in byte k of the input register and half k of the two output registers) matching the hand-written prmt selectors; if a future Triton version changes this mapping, results could silently corrupt. Validation is limited to a single A100 (sm_80) with no sm_86 or CI coverage, and the A/B harness is not included in the PR, so reproducibility depends on the author's cluster. Inline asm also reduces portability and readability, and correctness is asserted rather than enforced by an in-tree test.

**Key insights**  
The optimization is well-motivated and the PR provides strong evidence (bitwise equality, per-byte exhaustive check, kernel A/B, and end-to-end TTFT showing ~5% improvement at long inputs). The main review concerns are maintainability and guardrails: adding a small unit test that exhaustively checks all 256 byte values against a reference decode, and documenting the Triton pack-mapping assumption, would substantially de-risk the inline asm. The plain-Triton alternative being only 4-10% slower is worth weighing against the added complexity if portability becomes a concern.

**Key insights**  
The core insight is that sleep mode remaps KV cache virtual addresses to new physical pages, invalidating RDMA registrations that point at old pages, so connectors must drop and redo registrations around sleep. ### Summary

**What changed and why**  
Fixes a regression from #52314 where kill_process_tree could abort early with psutil.NoSuchProcess when a child was reaped between parent.children() and child.name(). The fix adds psutil.NoSuchProcess to the existing contextlib.suppress around the warning log, and a new test exercises the mid-walk child exit scenario with real processes.

**Technical impact**  
Restores correct force-kill behavior: the loop now continues to SIGKILL remaining descendants and the target pid even if one child disappears mid-walk. The fix is a one-line exception broadening backed by a targeted regression test that validates both the skipped child and the successful SIGKILL of the rest of the tree.

### Summary

**What changed and why**  
Adds FP8 (e4m3) KV-cache support for the Qwen4Exp QSA sparse attention path on Ampere (sm_80/sm_86), where Triton cannot use an fp8e4nv pointer type. Below sm_89 the cache is kept as raw uint8 and decoded in-kernel via a bit-cast helper (_maybe_dequant), with 2^8 folded into host K/V scales; sm_89+ keeps the native e4m3 view. The fused prepare/cache-write kernel is skipped below sm_89 with FP8, and an sm_80-specific 128-column/4-warp launch is added.

**Technical impact**  
Replaces the IS_FP8 constexpr with dtype-driven dispatch in the Triton kernel, interleaves load and dequant per K/V tile, and adjusts warmup to compile the correct cache dtype per architecture. Reported results: fixes 4 failing FP8 attention tests on sm_80, ~1.8x KV capacity, and large serving gains at higher concurrency (2.7x requests, ~9x lower p95 TTFT at concurrency 16) due to better prefix-cache retention. Accuracy is close to BF16 run-to-run noise and kernel time is roughly on par with BF16.

**Potential risks**  
No CI coverage for sm_80/sm_86 (no A100 runner), so regressions on Ampere would go undetected; validation is external only. The byte decode maps the two e4m3 NaN codes to +/-480 instead of NaN, a deliberate deviation from IEEE semantics justified by merged vLLM precedents but still a correctness question for reviewers. The sm_80 launch rule (128 columns, 4 warps) is tuned only for the Qwen3.8-Flash-Next TP8 geometry and unmeasured for other head counts/selection widths and for sm_86. Serving benchmarks used a non-stock scheduler hook and predate the maintainer refactor (though output is claimed bitwise identical).

**Key insights**  
The change is well-scoped (2 files, ~67 lines) and leverages dtype-based dispatch instead of architecture flags, which is cleaner and keeps a single e4m3 cache format across architectures. The strongest evidence is the serving data showing FP8 KV cache indirectly improves throughput via prefix-cache retention rather than raw kernel speed. The main open items are the NaN-handling policy decision and the absence of automated Ampere coverage; a follow-up for NaN handling across architectures and any available sm_80 CI would strengthen confidence.
