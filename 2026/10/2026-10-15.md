### Summary

**What changed and why**  
Adds text-only DeepSeek-V4.1-Flash Prefill Context Parallelism (PCP) support on NVIDIA CUDA for Model Runner V2 with FlashMLA sparse attention, including rank-local compressor pooling with cross-rank predecessor gathering, gathered KV/indexer cache writes, aligned Engram lookback and MoE routing IDs, and explicit NotImplementedError guards for unsupported topologies (PP/DP/DCP, spec decode, KV transfer, prefix caching, MegaMoE, ROCm). It also adds substantial tests and a CI entry.

**Technical impact**  
Introduces PCP-aware branching in attention, compressor, sparse-MLA metadata builders, model forward, and model_state, plus new Triton kernels (save_ring_rows) and a new prev_rows path in fused_save_compress_norm. Behavior changes for PCP>1 only, but touches shared code paths (slot_mapping chunking, lookback kernel signature change from num_computed_tokens to query_start_loc/positions) that affect non-PCP execution and require careful regression coverage.

**Potential risks**  
The lookback kernel now derives num_computed from positions[query_start_loc[batch_idx]] instead of req_states.num_computed_tokens, which could subtly change non-PCP behavior for edge cases (empty batches, chunked prefill). PCP correctness depends on strict collective ordering across ranks, including empty shards, and on equal num_rows across ranks; any divergence risks hangs or silent corruption. The PR itself notes GPU/model measurements were not rerun for the rank-local revision, and one GSM8K sample hit max_tokens after ~9700s, so quality/latency equivalence is not fully established. Unsupported-feature guards are broad and may reject valid configurations.

**Key insights**  
The design deliberately scopes PCP to a narrow, single-instance, eager, FlashMLA-sparse configuration to establish correctness before layering KV handoff, replay, and spec decode. The rank-local compressor revision removes InputBatch/PCPManager plumbing and the global FP32 kv_score gather, relying instead on per-request ring-block/position keys to link cross-chunk ratio-2 pairs. Validation covers TP8/PCP1, TP4/PCP2, TP2/PCP4 with near-identical GSM8K accuracy and meaningful prefill speedups, but the authors explicitly flag that these numbers predate the current revision and need revalidation on H20.

Validation is tokenizer/render-only, not full inference or GPU, and a full current-HEAD native rebuild was not run.

**Key insights**  
The fix is narrowly scoped and well-tested, with negative controls demonstrating the baseline failure and explicit-override precedence. The appended commit addressing review findings (Mistral kwarg filtering, missing-attribute tolerance) shows iterative hardening.   - `vllm/v1/structured_output/__init__.py`
  - `vllm/v1/structured_output/request.py`

### Summary

**What changed and why**  
Adds a read-only implicit_reasoning_end_token_ids property to ParserEngine and its reasoning adapter, then uses it in StructuredOutputManager to compute, per request, the implicit reasoning-end tokens (e.g. GLM's <tool_call>) that the request's grammar rejects as its first token. While a request is reasoning, unconstrained bitmask rows (including speculative draft and bonus rows) now allow every token except those ids, preventing the model from sampling a token that would later be fed to the grammar and cause a 'grammar rejected tokens' HTTP 500. The fix targets the failure path introduced by #59627 and is cached on StructuredOutputRequest.

**Technical impact**  
Changes bitmask filling in both serial and parallel paths, adding a fourth tuple element (masked_ids) to the fill batch and a per-request cached tuple on StructuredOutputRequest. Reasoning rows are no longer fully unconstrained when the grammar cannot start with an implicit end; constrained rows, padding rows, and requests whose grammar accepts the implicit end (required/named/auto tool calls) are unchanged. Cost is one validate_tokens call per implicit end per request plus a few bit clears on host-side numpy rows, with no device work or host sync. Tests cover serial, parallel, and speculative flows for xgrammar and guidance.

**Potential risks**  
The reasoning token distribution is altered without a flag, which could affect model behavior or output quality in edge cases even though the alternative is an error. Scope is limited to engine-based parsers and single-token implicit ends; multi-token or text-only ends (deepseek_v4, inkling) remain vulnerable. The change overlaps with open PR #61456 in _fill_bitmasks, so whichever lands second must preserve the reasoning-row mask, creating merge-conflict risk. The cached masked set assumes the grammar does not advance before reasoning ends; if that invariant changes, the cache could become stale. Validation is extensive but relies partly on custom CPU harnesses and a single GPU run.

**Key insights**  
The root cause is that reasoning rows are unconstrained while the grammar is not advanced, so a sampled implicit end is later rejected when fed to the grammar. Masking only grammar-rejected implicit ends is a minimal, targeted fix that preserves existing behavior for tool-call requests where the grammar accepts the marker. The PR is well validated with unit, real-component, CPU end-to-end, speculative decoding, and GPU runs, and it explicitly documents tradeoffs and the interaction with #61456.

### Summary

**What changed and why**  
Generalizes the gfx950 (MI355) low-latency MoE router GEMM from five hard-coded (hidden_size, num_experts) shapes to any shape with M<=32, adding a masked K tail, a swept launch-config rule, bf16 weight support, and size guards that decline to the fallback when it would be slower. GateLinear now enables the fp32 router tier on gfx950 for any shape and routes bf16-weight/fp32-logit gates (tier 6) through the same fp32_router_gemm_dispatch op instead of torch.mm. Tests are extended and a new MI355 CI job mirroring the B200 Gate Linear CuTeDSL job is added.

**Technical impact**  
Decode-time router GEMM latency drops from roughly 9-13us (F.linear) or 5-11us (hipBLASLt) to 1.9-4.9us at low token counts, yielding reported 1-14% decode speedups across eight MoE models with flat prefill and no accuracy change. The kernel now handles arbitrary hidden sizes via EVEN_K masking, accepts bf16 weights directly (no fp32 copy), and uses a launch rule fitted on 12 shapes and validated on 10 held-out shapes. Runtime branching remains inside the existing custom op, preserving torch.compile compatibility, and scope is limited to gfx950.

**Potential risks**  
The launch-config heuristic and size guards (_MAX_MACS = 2^27, _MAX_BF16_TOKEN_EXPERTS = 8192) are empirically tuned on MI355 and could regress on unseen shapes or future hardware; two 1024-expert M=32 cases intentionally keep F.linear. The tier-6 change alters the bf16-weight path for all gfx950 gates, so any subtle dtype or numerics difference versus torch.mm could affect logits, though tests assert fp32 output and close agreement. The new CI job is marked optional, so regressions may not block merges. End-to-end coverage is incomplete for MiniMax-M2.5, Kimi-Linear-48B, and LongCat-Flash-Lite, which were not measurable or crash on main.

**Key insights**  
This is a well-scoped performance PR with strong evidence: paired A/B benchmarking, McNemar accuracy tests, kernel microbenchmarks, mutation-tested unit tests, and a control model confirming no regression on the unchanged path. The design cleanly separates eligibility (can_use_rocm_fp32_router_gemm with size guards) from dispatch, keeping the fallback safe. Reviewers should focus on the launch-rule thresholds, the bf16 tier-6 routing change in GateLinear, and whether the optional CI job should be made required.
