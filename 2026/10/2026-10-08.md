## 3. [[Perf][DSv4.1] Trim the last KV-source layer in decoder replay](https://github.com/vllm-project/vllm/pull/59894)


### Base Information

- **PR Number:** #59894
- **Author:** [gcanlin](https://github.com/gcanlin)
- **Merged By:** [ivanium](https://github.com/ivanium)
- **Merged time:** 2026-10-08 23:07:50

  - `tests/models/test_deepseek_v41_replay_batch.py`
  - `vllm/models/deepseek_v41/attention.py`
  - `vllm/models/deepseek_v41/decoder_replay_layers.py`
  - `vllm/models/deepseek_v41/nvidia/model.py`
  - `vllm/models/deepseek_v41/nvidia/model_state.py`

### Summary

**What changed and why**  
This PR changes the decoder replay optimization for DeepseekV4.1 so that the last KV-source layer (layer 20 on DSV4.1-Flash) is now included in the replay region instead of running on every row. A new DeepseekV4DecoderLayer.write_kv / DeepseekV4Attention.forward_kv path writes only the KV (SWA, compressed, index K) for all rows, then the layer runs as the first replay layer on the replay rows. The replay break decision for PIECEWISE CUDA graphs now uses graph size via DecoderReplayLayers.replays()/graph_uses_replay_batch() rather than replay_batch being set, since replay_batch is unset at capture time. The indexer row-buffer compaction logic is removed, and model_state now builds a separate SWA attention metadata for the first replay layer using the batch's window starts.

**Technical impact**  
Shifts the replay boundary one layer earlier, so the cut layer's indexer scoring, top-k, sparse MLA, wo, and MoE are skipped for trimmed rows while its KV is still written for all rows. Introduces a new forward_kv path that must bit-for-bit match the KV half of the existing fused qnorm/rope/kv insert, and adds a second attention metadata build (first_swa_prefix) with the batch's window starts to keep sliding-window semantics exact. PIECEWISE graph capture now correctly captures the replay break and trimming, which previously did not happen because replay_batch was unset during capture. Reported gains are +1.7% to +5.5% throughput with unchanged GSM8K accuracy (0.9606).

**Potential risks**  
The new forward_kv must exactly reproduce the KV writes of the full forward path; any divergence in rope, scaling, or cache insertion would silently corrupt attention. The dual attention metadata (replay_groups vs first_swa_groups) and the changed replay_start semantics for the first layer are subtle and could break window correctness if window starts are not propagated correctly. The PIECEWISE break now depends on trim_threshold being set at capture time; if threshold is None or mismatched between capture and runtime, trimming may be skipped or applied incorrectly. The added assertion compress_ratio <= 1 and the changed Engram condition (i >= cut instead of i > cut) narrow supported configurations and could disable replay on setups that previously worked. Test changes rely on MagicMock and index-based build selection (state.builds[-2]), which are somewhat brittle.

**Key insights**  
The core insight is that the last KV-source layer's KV is needed for all rows but its compute (indexer, sparse MLA, MoE) is only needed for replay rows, so splitting KV write from the rest of the layer lets it be trimmed. The second key insight is that PIECEWISE graph capture cannot rely on runtime replay_batch state, so the break decision must be a pure function of graph size (trim_threshold) shared between capture and runtime. The removal of indexer row-buffer compaction simplifies the design by making the cut layer write KV for every row before compaction. Performance gains are modest but consistent across input lengths and agent workloads, with no accuracy regression.

## 6. [[Frontend] Accept each connection on the least loaded API worker](https://github.com/vllm-project/vllm/pull/60723)


### Base Information

- **PR Number:** #60723
- **Author:** [hao-aaron](https://github.com/hao-aaron)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-10-08 21:40:13
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/60723/files) (4):**
  - `tests/entrypoints/launchers/test_balanced_accepts.py`
  - `vllm/entrypoints/launchers/api_server/entry.py`
  - `vllm/entrypoints/launchers/launcher.py`
  - `vllm/v1/utils.py`

### Summary

**What changed and why**  
This PR changes how multiple API server workers (--api-server-count N > 1) accept connections on a shared listening socket. Instead of letting each worker's event loop accept every queued connection on wakeup (which causes bursts to land on one worker), each worker now publishes its open-connection count into a shared RawArray and only accepts when it is the least loaded, deferring up to 5 ms with 1 ms rechecks before accepting anyway. It adds a custom accept loop in NoSignalServer, wires peer_loads through build_and_serve/run_server_worker, and allocates the shared array in APIServerProcessManager.

**Technical impact**  
Substantial behavior change to the API server accept path: replaces uvicorn's asyncio server with a hand-rolled accept loop using loop.connect_accepted_socket per connection, adds shared-memory load tracking, and introduces new shutdown/cancellation handling for accept and handshake tasks. Reported gains are large: RL abort cycle 40.0s to 21.5s, and +43-85% short-request throughput with lower TTFT, with connections evenly distributed (16 per worker vs 31-34 on main). Single API server behavior is unchanged and no new flags are added.

**Potential risks**  
The balancing introduces a latency trade-off: when all workers are busy rendering, short requests like /health can wait behind a render (p99 ~50-100 ms vs <1 ms on main), and under CPU overload all balanced schemes sit around 1.5s. The custom accept loop bypasses uvicorn's own server, so correctness depends on faithfully replicating protocol setup, TLS handling, backlog/listen semantics, and shutdown draining; edge cases like EMFILE, failed TLS handshakes, and cancellation are handled but add surface area. The shared RawArray uses int32 with INT32_MAX sentinel, and correctness relies on workers publishing load promptly; a crashed or stalled worker could skew least-loaded selection. Tests cover many scenarios but the multi-process balance test is skipped on machines with fewer than 8 CPUs.

**Key insights**  
The root cause is that all workers inherit one listening socket and whichever wakes first drains the whole burst, so a shared-load-aware accept gate is a targeted fix that outperforms both SO_REUSEPORT (hash clumping) and accept pacing (staggered arrivals still favor one worker). The design reuses the existing mp_admission_counters shared-array mechanism, keeping the change localized. The 5 ms defer window is a deliberate balance between connection spread and added latency for short requests, and the PR documents this trade-off plus the fact that it balances connections, not requests, since keep-alive clients stay pinned to their worker.

### Summary

**What changed and why**  
Fixes a bug in Internlm2ToolParser.extract_tool_calls_streaming where streamed tool-call argument deltas dropped characters when a chunk boundary fell inside a JSON string. The old code computed the delta via extract_intermediate_diff(cur_args_json, prev_args_json), but prev_args_json contained synthetic closers added by partial_json_parser that were never actually sent to the client, causing real characters like the closing quote and final brace to be lost. The fix computes the delta from the length of text already streamed (self.streamed_args_for_tool), using find_common_prefix for partial parses and full cur_args_json[sent:] when the JSON is complete.

**Technical impact**  
Aligns Internlm2ToolParser with the streaming scheme already used by llama_tool_parser.py and granite_20b_fc_tool_parser.py, replacing the extract_intermediate_diff import with find_common_prefix. Streamed argument deltas now concatenate to valid, complete JSON matching the final arguments regardless of chunk boundaries, and get_remaining_unstreamed_args() correctly returns empty when the JSON is complete. A regression test test_streaming_arguments_match_final_arguments is added covering split-inside-string and char-by-char chunking.

**Potential risks**  
The parser still streams json.dumps of the partial parse rather than raw text slices, so number literals that json.dumps normalizes differently (e.g. 1E-3 to 0.001, 0.00001 to 1e-05) can still produce wrong values for some splits, though the output is now valid JSON rather than malformed. The same extract_intermediate_diff branch exists in jamba_tool_parser.py and may share the bug but is not fixed here. No end-to-end server streaming test was run because internlm2_5-7b-chat weights were unavailable, so validation relies on direct parser invocation and a chunk-boundary sweep.

**Key insights**  
The root cause was a mismatch between the parser's internal partial-parse representation (with synthetic closers) and what was actually streamed to the client; tracking sent length directly is the correct source of truth. The author's sweep of 13,887 streams found no regressions and 6,649 newly-correct streams, providing strong evidence the fix is safe. The remaining number-literal limitation is a known, pre-existing constraint shared with other tool parsers and is explicitly documented rather than hidden.

It also adds a bounded-Gumbel prune (skip tokens whose logit gap exceeds GUMBEL_MAX=37.5), fixes greedy_argmax NaN handling to match torch.argmax, adds input validation, and wires the new test file into CPU CI.

**Technical impact**  
Behavioral change in the CPU sampling path: fused_gumbel_argmax now produces statistically correct samples matching softmax, and greedy_argmax now returns the first NaN index when NaNs are present (matching torch.argmax semantics) instead of silently ignoring them. The kernel drops the SIMD vectorized table lookup in favor of scalar per-token RNG/exp/log, which is faster for top-k/top-p serving (most logits are -inf and get pruned) but significantly slower for full-vocab random sampling (e.g. batch=1 random 0.44ms -> 6.17ms). A batch=1 serial fast path avoids OpenMP fork overhead. New TORCH_CHECKs add device/dtype/shape validation, and seeds are now made contiguous before use. Extensive new tests cover distribution correctness, the sliding-window regression, Zipf head/tail, masked support, tie-breaking at float max, non-contiguous inputs, and empty batches.

**Potential risks**  
The full-vocab random sampling path is roughly 14x slower at batch=1, which could regress latency for workloads that use unfiltered random sampling rather than top-k/top-p; the PR acknowledges this but it is a real performance tradeoff. The GUMBEL_MAX=37.5 prune relies on the 53-bit uniform bound; any change to the RNG bit-width or the u-in-(0,1) construction could invalidate this constant and silently drop valid candidates. The new NaN handling in greedy_argmax changes output for NaN-containing logits, which is a behavior change that could affect downstream consumers relying on the old (arguably buggy) behavior. The scalar per-token loop may also be slower on very large vocabularies even with pruning, and the correctness of the SplitMix64 key derivation (key + (i+1)*GAMMA) depends on the mixing function's quality, which the tests validate statistically but not exhaustively.

**Key insights**  
The root cause was a subtle aliasing bug: reusing one Gumbel table with a seed offset creates correlated noise across seeds, which is invisible to small-vocab chi-squared tests (the old test used vocab=100) but severe for large-vocab Zipf distributions. The fix correctly separates the RNG stream per (seed, token) and the new test_noise_not_sliding_window directly targets the regression. The comparison-in-(logit, noise)-space design is a thoughtful detail to avoid losing noise precision when logits are near float max, and the bounded-Gumbel prune is a clever way to recover serving performance despite the scalar loop. ### Summary

**What changed and why**  
Fixes issue #60093 where enabling --enable-moe-shared-loras on 3D-weight MoE models (e.g. GPT-OSS) crashed during LoRA warmup with AttributeError: 'MoERunner' object has no attribute 'lora_a_stacked'. The fix adds _enable_moe_shared_loras to the condition that disables _is_3d_moe_model, so shared-outer adapters route through FusedMoEWithLoRA (which builds lora_a_stacked) instead of FusedMoE3DWithLoRA. A docstring in LoRAConfig was also updated to reflect this behavior.

**Technical impact**  
Changes wrapper selection logic in vllm/lora/model_manager.py so that when enable_moe_shared_loras is set on a 3D-weight MoE model, the model uses the 2D FusedMoEWithLoRA wrapper rather than FusedMoE3DWithLoRA. This aligns shared-outer adapters with the same 2D layout already used for enable_mixed_moe_lora_format, allowing create_dummy_lora to index lora_a_stacked correctly and completing engine warmup. 3D PEFT adapters without the flag continue to use FusedMoE3DWithLoRA, preserving the fused gate/up path.

**Potential risks**  
Validation was limited to a single-layer, 8-expert GPT-OSS-20b run on a T4 with dummy weights; the full 24-layer mxfp4 serve path was not exercised, so untested interactions with real quantized checkpoints remain. There is no CI coverage for enable_moe_shared_loras, so regressions in this path would go undetected. Users with 3D PEFT checkpoints (fused gate/up on disk) must still avoid the flag or convert under --enable-mixed-moe-lora-format, which is a documented but easy-to-miss limitation.

**Key insights**  
The root cause is a wrapper-selection mismatch: shared-outer adapters use a 2D packed layout, but 3D-weight models defaulted to FusedMoE3DWithLoRA, whose create_lora_weights ignores the shared flag and never populates lora_a_stacked. The fix mirrors the existing mixed-format handling by treating shared-outer adapters as another reason to force the universal 2D wrapper. The change is small and targeted, but the lack of CI coverage and full-model validation means the fix is best characterized as verified in a constrained reproduction rather than broadly proven.
