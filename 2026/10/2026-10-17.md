## 1. [[Bugfix][MRV2] Fix speculative warmup deadlock with pipeline parallelism](https://github.com/vllm-project/vllm/pull/62129)


### Base Information

- **PR Number:** #62129
- **Author:** [chenjr97](https://github.com/chenjr97)
- **Merged By:** [khluu](https://github.com/khluu)
- **Merged time:** 2026-10-17 23:51:33
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/62129/files) (3):**
  - `tests/v1/worker/test_gpu_warmup_blocks.py`
  - `tests/v1/worker/test_mixed_warmup_gate.py`
  - `vllm/v1/worker/gpu/warmup.py`

### Summary

**What changed and why**  
Fixes a pipeline-parallel startup deadlock in MRV2 speculative decoding introduced by PR #59260. The extra greedy warmup pass was previously gated on the presence of a rejection sampler, which only exists on the last PP stage, so earlier stages skipped the pass while the last stage blocked waiting for their activations. The gate is changed to speculative_config so every PP stage runs matching forwards, and regression tests are added.

**Technical impact**  
Behavior change is confined to the warmup condition in vllm/v1/worker/gpu/warmup.py: all PP ranks now execute the additional greedy warmup forward when speculative decoding is enabled, keeping sends and receives aligned across stages. Tests add a speculative_config stub to existing fixtures and a new parametrized test verifying identical warmup rounds on non-last and last PP ranks with speculative decoding on and off.

**Potential risks**  
The new gate assumes speculative_config is consistently set on all PP ranks; if it is None on some stages but not others, the deadlock could reappear or new mismatches could occur. Earlier PP stages now perform an extra warmup forward, adding minor startup cost. Validation relies on unit tests plus a single GLM-4.7-Flash smoke run with no accuracy benchmark, so broader model/config coverage is limited.

**Key insights**  
The root cause is a collective-operation mismatch: gating a warmup pass on a rank-local object (rejection_sampler) breaks PP synchronization. Gating on a cluster-wide config (speculative_config) is the correct fix. The added test directly encodes the invariant that all PP stages run the same warmup rounds, which is a good regression guard for future changes.

Full builds and the AMD test suite have not yet run, so end-to-end behavior is unverified.

**Key insights**

### Summary

**What changed and why**  
Fixes an intermittent multi-layer EPLB race in the NIXL communicator where NIXL READs (issued from CPU, unordered with the device stream) could overwrite expert_buffer before the previous layer's queued copies out of that buffer executed. The PR synchronizes the current stream and the EPLB stream in set_transfer_context before the first READ of each layer, and restores the previously no-op set_stream override so the stream is actually stored.

**Technical impact**  
Behavior changes in the NIXL EPLB path: set_stream now records the stream instead of discarding it, and set_transfer_context performs a ROCm-only stream synchronization (guarded by gpu_sync_allowed) before issuing READs. **Potential risks**  
The added synchronization is gated on is_rocm(), so any analogous race on other backends would remain unaddressed. The sync could add per-layer overhead and potentially interact with async EPLB timing assumptions. Correctness depends on the main stream and self._stream being the relevant streams in async flows; if other streams touch expert_buffer, the fix may be incomplete. Limited to a single file with modest test coverage, though the PR reports extensive stress testing.

**Key insights**  
The root cause is a CPU-issued NIXL READ bypassing device stream ordering, a regression introduced when a prior sync was removed alongside send-buffer packing. The fix is narrowly scoped and well-validated with a reproducible race harness (idle GPU and injected delays) showing 0 failures versus high failure rates on main. The ROCm-only guard suggests the issue is currently observed only on AMD hardware.

**Key insights**  
Well-scoped optimization that reuses an existing extension point rather than modifying core parser logic, with strong differential fuzz evidence (27,500 calls, ~194K deltas identical). ### Summary

**What changed and why**  
Replaces sorted() over the mapped weight stream in the DeepSeek-V4 VL and NVIDIA DeepSeek-V4.1 VL wrappers with a new stream_language_model_first helper that yields language_model.* weights immediately and defers (cloned) non-language-model weights until the end. A new parametrized test and a Buildkite registration are added.

**Technical impact**  
Behavioral change in weight delivery order: language_model weights now stream through as they arrive rather than in globally sorted name order, and vision/aligner weights are cloned and emitted last. This keeps AutoWeightsLoader's per-contiguous-group delegation intact so the child still finalizes exactly once after all its weights, but changes memory profile (lower peak anonymous memory for materialized loaders, fewer simultaneously mapped shards) and load ordering for non-language-model tensors. The clone adds a copy per deferred tensor, a minor CPU/memory cost for vision weights.

**Key insights**  
The core insight is that contiguity only requires a non-interleaved group, not a total sort, so a streaming partition is sufficient and avoids the OOM and page-cache costs of sorted(). The clone of deferred weights is a deliberate trade to avoid pinning per-shard storage, and the test's mid-stream assertion directly encodes the regression being fixed.
