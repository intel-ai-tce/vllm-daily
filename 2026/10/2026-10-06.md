### Summary

**What changed and why**  
The Cohere v2 chat and render handlers in vllm/entrypoints/cohere/api_router.py previously caught every exception and returned a hard-coded HTTP 500, including client-caused errors like invalid temperature or out-of-range seed. This PR replaces the fixed 500 response with _error_response(create_error_response(e), raw_request), the same mapper used by the global exception handlers and /v1/messages, so client errors now return 4xx while unexpected errors still return 500. Tests in tests/entrypoints/cohere/test_api_router.py were updated and extended to assert the new 400 behavior.

**Technical impact**  
Behavioral change limited to the two except blocks in the Cohere router; the ErrorResponse branch and CohereErrorEnvelopeMiddleware are untouched, so the Cohere {message, id} wire envelope is preserved. Client errors (VLLMValidationError, pydantic.ValidationError, ValueError/TypeError/OverflowError fallbacks) now map to 4xx, NotImplementedError to 501, and server-side VLLMErrors keep their 5xx status. This aligns Cohere routes with the OpenAI routes and prevents Cohere SDK clients from retrying malformed requests, since the SDK retries any status >= 500.

**Potential risks**  
A stray ValueError or TypeError raised by an internal bug rather than bad input will now be reported as 400 instead of 500, potentially masking server-side defects and confusing monitoring or alerting based on 5xx rates. The change relies on create_error_response's mapping being correct and stable; any future change to that mapper silently alters Cohere error semantics. The PR notes that test_chat_v2.py, which boots a real server with model weights, was not run, so end-to-end coverage of the full path is limited to stubbed tests.

**Key insights**  
The root cause was a hard-coded 500 with a misleading 'parity' comment, mirroring the earlier /v1/messages issue fixed in #52246; reusing create_error_response is the established pattern for this class of fix. The PR is well-validated with reproduction scripts, before/after status tables, and regression tests that fail on main and pass with the fix. The main residual concern is the intentional broadening of 400 responses to internal ValueErrors, which is consistent with existing shared handlers but worth noting for observability.

- **[Changed Files](https://github.com/vllm-project/vllm/pull/60210/files) (6):**
  - `tests/kernels/mamba/test_precopy_mamba_align.py`
  - `tests/v1/worker/test_mamba_utils.py`
  - `vllm/v1/worker/gpu/model_runner.py`
  - `vllm/v1/worker/gpu/model_states/interface.py`
  - `vllm/v1/worker/gpu/model_states/mamba_hybrid.py`
  - `vllm/v1/worker/mamba_utils.py`

### Summary

**What changed and why**  
Fixes a correctness bug in Mamba 'align' state copies under MRV2 + PP + MTP where the precopy/postprocess kernels indexed persistent per-request-slot block tables by batch row (req_idx), causing them to read another request's blocks when a postprocess ran after later steps re-gathered the batch-ordered input_block_tables. The fix changes the kernels to index by req_idx (request slot), splits the block-table pointers into separate state-copy and aligned-index sets, and eagerly builds the align context once in initialize_kv_cache via a new ModelState hook instead of lazily from whichever caller ran first.

**Technical impact**  
Adds a new initialize_kv_cache hook to the ModelState interface and calls it from gpu/model_runner.py after KV cache allocation, so MambaHybridModelState binds both the per-request-slot block_tables and the batch-order input_block_tables eagerly. MambaSpecDecodeGPUContext now carries aligned_index_block_table_ptrs separately, with compute_aligned_state_indices reading the gathered batch-order tables (preserving padded-row and CUDA graph behavior) while state-copy kernels read the slot tables. Kernel work is unchanged; the throughput gain comes from recovered acceptance length.

**Potential risks**  
The fix relies on the invariant that a request is not rescheduled (row not rewritten, slot not reused) until its in-flight step's output is processed; if that assumption is violated, late reads of the source tables could still be stale. Eager binding in initialize_kv_cache changes initialization ordering and could interact with profiling/capture paths or other ModelState subclasses that override the new hook. The new default of aligned_index_block_tables falling back to block_tables must remain correct for MRV1 and any caller not passing the second table set.

**Key insights**  
The root cause is a mismatch between two indexing domains: per-request decision arrays are in req-state-slot order while the batch-ordered input_block_tables are re-gathered every step, so under PP a delayed postprocess reads the wrong rows. Splitting the two table sets and indexing state copies by req_idx is a smaller, more direct fix than the lazy-binding machinery proposed in #55506/#57807, and it avoids changing padded-row behavior. The PR includes targeted kernel and context-binding tests that fail when the kernels are reverted to batch-row indexing, plus E2E evidence showing recovered acceptance length and throughput on GB200.

### Summary

**What changed and why**  
The PR fixes an integer overflow bug in the ep_gather Triton kernel where the output row offset cur_token * output_tensor_stride0 was computed in int32. With the DeepEP v2 expanded layout, the output can exceed 2^31 / hidden_size rows, causing the offset to wrap and produce an out-of-bounds store (cudaErrorIllegalAddress). The fix casts cur_token to int64 before multiplication, mirroring the earlier input-read widening in #53914, and adds a regression test that exercises an output row count just past the int32 overflow threshold.

**Technical impact**  
Behavior changes only for large outputs where the row offset previously overflowed; the cast forces 64-bit address arithmetic in the Triton store, preventing the illegal memory access. The added test in tests/kernels/moe/test_deepgemm.py validates correctness at hidden_size=6144 with num_rows just above 2^31/hidden_size, providing coverage for the previously failing path. Small-output behavior is unchanged since int64 arithmetic yields identical addresses within int32 range.

**Potential risks**  
The regression test allocates a very large output tensor (roughly 2^31 elements of bf16, ~4 GB) plus matching recv_topk_ids, weights, and input_index, which may OOM or be skipped on GPUs with limited memory and could be slow in CI. The fix only widens the output offset; if other offset computations in the same kernel (e.g., input indexing) still use int32, similar overflow issues could remain for other large-layout cases. No test plan or test results were provided in the description, so end-to-end validation is not documented.

**Key insights**  
This is a targeted, well-scoped fix for a real out-of-bounds bug caused by int32 address arithmetic in a Triton kernel, consistent with a prior analogous fix. The main review concerns are the memory footprint and CI feasibility of the new test, and whether any other int32 offset computations in the kernel need the same treatment. The change is low-risk for typical workloads but critical for large expanded-layout MoE runs.
