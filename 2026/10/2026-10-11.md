## 2. [[Bugfix][Distributed] Own SHM out-of-band buffers before releasing read slots](https://github.com/vllm-project/vllm/pull/61000)


### Base Information

- **PR Number:** #61000
- **Author:** [hubert-marek](https://github.com/hubert-marek)
- **Merged By:** [ywang96](https://github.com/ywang96)
- **Merged time:** 2026-10-11 22:44:13
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/61000/files) (2):**
  - `tests/distributed/test_shm_broadcast.py`
  - `vllm/distributed/device_communicators/shm_broadcast.py`

### Summary

**What changed and why**  
Fixes a shared-memory lifetime bug in MessageQueue.dequeue where out-of-band NumPy arrays reconstructed via pickle.loads(buffers=...) remained views into a reusable SHM ring slot, so later writes corrupted already-received data. The fix copies out-of-band buffers into an owned bytearray before the read slot is released, and _rebuild_tensor now reuses that owned bytearray instead of copying again. Tests were expanded with a deterministic ring-reuse regression and improved distributed_run process reaping.

**Technical impact**  
Received NumPy arrays (writable and read-only) and Torch tensors now own their storage independent of the ring slot, matching the ownership convention previously applied only to Torch tensors. Torch reconstruction avoids a redundant copy by reusing the bytearray, while remote/overflow ZMQ frames and the tensor arena keep existing behavior. Adds one allocation and CPU copy per SHM out-of-band buffer, with measured dequeue overhead rising from ~0.02ms to ~0.08-0.63ms for 1-8 MiB payloads.

**Potential risks**  
The added per-buffer copy increases CPU and memory bandwidth cost on the SHM path, which could matter for large or high-frequency out-of-band payloads even though the reported GB200 throughput A/B showed no regression. The test changes also alter distributed_run semantics (clearing and repopulating failed_processes, always joining children), which could mask or surface different failure modes in other distributed tests. The fix is validated on synthetic serving workloads, not the reporter's original training scenario, so the historical failure's root cause is not fully confirmed.

**Key insights**  
The root cause is a clear ownership violation: pickle buffer views outlive the ring slot they point into, and the existing Torch-only protection in #48442 did not cover plain NumPy arrays. The PR is well-scoped, includes a baseline-failing regression, a real-queue reproducer, and a lifetime audit showing 17/26 corrupted arrays dropping to 0/26, which is strong evidence. The main review focus should be the copy-cost tradeoff and whether the distributed_run test harness changes are safe for the broader suite.

### Summary

**What changed and why**  
Endpoint plugins could register routes that collided with core routes, but core routes were registered first and won during dispatch, so plugin overrides silently failed while OpenAPI could still describe the plugin handler. This PR changes attach_endpoint_plugins to replace earlier APIRoute operations sharing the same path template and HTTP method, preserves non-overridden methods, lets the last registered plugin win, and clears the OpenAPI cache so the schema matches actual dispatch. Docs and tests were updated accordingly.

**Technical impact**  
The routing logic in vllm/plugins/endpoint_plugins/interface.py now post-processes app.routes after plugin attach_router calls, deduplicating APIRoute entries by path and method intersection, splitting methods when only some overlap, and reinserting replacements ahead of mounts. app.openapi_schema is reset when plugins are present so FastAPI regenerates the schema. This changes request dispatch behavior for any plugin that registers a colliding path, and the added tests exercise HTTP dispatch and OpenAPI via ASGI.

**Potential risks**  
The route-rewriting loop mutates app.router.routes in place and relies on id-based tracking of pre-existing routes, which is subtle and could misbehave if plugins mutate app.routes directly or if route objects are reused. Method-set splitting via copy(previous) assumes APIRoute internals remain valid after shallow copy. Ordering interactions with mounts and multiple plugins are only partially covered by tests, and clearing openapi_schema on every plugin attach may have performance implications for large schemas. No model-level evaluation was run, so only HTTP routing and OpenAPI generation are validated.

**Key insights**  
The fix correctly addresses the documented-but-broken override contract and aligns OpenAPI with runtime dispatch, which is the core value. The implementation is non-trivial and warrants careful review of the route-reordering algorithm, especially edge cases around mounts, method splitting, and plugin ordering. Test coverage is solid for the described scenarios (override, hook visibility, method preservation, plugin conflicts) and all six new cases reportedly fail on the unpatched baseline, which is good evidence of regression protection.

## 9. [[Fix] MiniMax: fix CUDA IPC handle exchange on cuda-bindings >= 13.4](https://github.com/vllm-project/vllm/pull/60917)

  - `vllm/model_executor/layers/minimax_rms_norm/lamport_workspace.py`

### Summary

**What changed and why**  
The MiniMax fused allreduce+RMSNorm path serialized CUDA IPC handles via the cudaIpcMemHandle_t.reserved field, which NVIDIA removed in cuda-bindings 13.4, causing an AttributeError and a silent fallback to the slower eager path. The fix adds _ipc_handle_to_bytes and _ipc_handle_from_bytes helpers that copy the opaque 64-byte handle through getPtr() using ctypes, and rewires the all_gather_object exchange in lamport_workspace.py to use them.

**Technical impact**  
Behavior is restored on cuda-bindings >= 13.4 while remaining compatible with older versions, since getPtr() exists across releases and the CUDA ABI fixes the handle as a 64-byte opaque struct. The change is confined to one file and only affects the IPC handle serialization/deserialization path, so the fused kernel can again be used instead of the eager fallback.

**Potential risks**  
The code assumes sizeof(cudaIpcMemHandle_t) is exactly 64 bytes; if a future CUDA version changes the handle size, the hardcoded constant would silently truncate or over-read memory. ctypes.string_at and memmove operate on raw pointers with no bounds checking, so a malformed or wrong-length peer handle could cause undefined behavior, though the added assert on length provides partial protection. The assert on raw is not None is also stripped under python -O.

**Key insights**  
Using getPtr() plus ctypes sidesteps the removed reserved field without version branching, which is a pragmatic fix for a fast-moving dependency. The underlying issue is that vLLM relied on a private/implementation detail of cuda-bindings rather than a stable serialization API, so similar breakage could recur if NVIDIA changes the handle layout. The reported test result (6 passed, fallback message gone) confirms the fused path is exercised again.
