## 1. [[RL] Send NCCL weight metadata once and reuse it](https://github.com/vllm-project/vllm/pull/35911)


### Base Information

- **PR Number:** #35911
- **Author:** [S1ro1](https://github.com/S1ro1)
- **Merged By:** [ywang96](https://github.com/ywang96)
- **Merged time:** 2026-10-19 23:21:58
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/35911/files) (3):**
  - `docs/training/weight_transfer/nccl.md`
  - `tests/distributed/test_weight_transfer.py`
  - `vllm/distributed/weight_transfer/nccl_engine.py`

### Summary

**What changed and why**  
Adds a metadata-reuse optimization to the NCCL weight transfer path. The worker (NCCLWeightTransferEngine) now caches the last NCCLWeightTransferUpdateInfo per model and reuses it when an update arrives with empty names/dtype_names/shapes; the cache is cleared on init_transfer_engine. The trainer engine (NCCLTrainerWeightTransferEngine) tracks the last sent ParamMeta list and sends empty update info when metadata is unchanged. Update info fields become default-empty lists, and docs describe the new contract.

**Technical impact**  
Eliminates per-round out-of-band transmission of ~19k name/dtype/shape entries for large models, reducing overhead for RL trainers that resend identical parameters. Behavior is backward compatible for callers that always send full metadata (TRL, HTTP without vLLM). The change relies on a strict contract: empty lists mean 'reuse previous', so a first round with empty lists loads nothing, and any parameter change must resend full metadata or the worker will hang or load wrong values.

**Potential risks**  
Silent correctness hazard: if a caller sends empty lists after parameters changed (added/removed/reordered/reshaped/re-dtyped), the worker reuses stale metadata, causing NCCL hangs or wrong weight loads with no validation. The cache is keyed by model object identity, so model replacement without re-init could reuse stale metadata. The trainer's _sent_meta is only updated after a successful round, which is correct, but any divergence between trainer and worker views (e.g., partial failures, retries) is not detected. Tests cover the happy paths but not mismatch/failure scenarios.

**Key insights**  
The design trades a wire-protocol change for an implicit stateful contract between trainer and worker, which is simpler but less robust than explicit metadata versioning or checksums. The per-model keying correctly separates target and draft models, and clearing on re-init is a sensible safety measure. The main residual risk is undetected metadata divergence; a lightweight version/hash check would harden this without the cost of resending full lists.

  - `vllm/v1/worker/lora_model_runner_mixin.py`

### Summary

**What changed and why**  
Fixes a correctness bug where waking from level-2 sleep without reload_weights() left LoRA GPU state (TP logits reindex mapping, adapter slots, punica metadata) corrupted because it was allocated in the discarded weights cumem pool. The fix wraps LoRA manager creation in use_memory_pool(tag="runtime") when sleep mode is enabled on CUDA/ROCm, so the state is offloaded and restored across sleep levels. Tests are updated to assert the mapping is correct (not just present) after wake-up.

**Technical impact**  
LoRA state now lives in the runtime pool, which is preserved across all sleep levels, keeping tensor addresses stable so CUDA graphs and cached LoRA kernel pointer tables remain valid. This covers both MRV1 and MRV2 via LoRAModelRunnerMixin.load_lora_model without touching worker or LoRA-manager APIs. Level-2 sleep now copies LoRA slots to host memory instead of discarding them, adding some host-memory cost proportional to max_loras x layer size x rank.

**Potential risks**  
XPU is not covered since nested memory pools are unsupported there, leaving the original bug on that platform. The new TP>1 test is skipped in CI (single-GPU H200 MIG), so the regression guard relies on manual/out-of-CI validation. Behavior depends on the runtime pool being correctly restored for all sleep levels and on the nested use_memory_pool restoring the outer weights tag; any future change to pool semantics could silently reintroduce corruption.

**Key insights**  
The root cause is that level-2 sleep discards the weights pool, and LoRA state was allocated there without being registered as a preserved buffer. Reusing the existing runtime pool is a minimal, low-risk fix that avoids new wake-up hooks or LoRA-manager APIs. The test improvement from checking mapping presence to checking mapping correctness is important, since a garbage-but-present tensor would otherwise pass.

## 6. [[Bugfix][KV Connector][Mooncake] Wait for all peers before completing failed receives to avoid potential KV block write-after-free](https://github.com/vllm-project/vllm/pull/62282)


### Base Information

- **PR Number:** #62282
- **Author:** [zhou-yuhan](https://github.com/zhou-yuhan)
- **Merged By:** [Isotr0py](https://github.com/Isotr0py)
- **Merged time:** 2026-10-19 21:13:30
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/62282/files) (3):**
  - `tests/v1/kv_connector/unit/test_mooncake_connector.py`
  - `tests/v1/kv_connector/unit/test_mooncake_connector_hma.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py`

### Summary

**What changed and why**  
Fixes a KV-block write-after-free in the Mooncake connector: when one P peer fails a transfer, the D side previously marked the request finished and released its destination blocks immediately, even though other peers could still write to those addresses. The change makes each peer settle its own pending entries via a shallow-copied pull_metas map, decrements pull_tasks_count on both success and failure, reports the first failure only once, and publishes receive completion only when the count reaches zero. It also settles still-pending requests on FINISH to cover expired requests omitted by P, preventing a block leak.

**Technical impact**  
Refactors failure and success handling into a shared _complete_pull_task helper and moves err_reqs processing ahead of ok_reqs in process_pulling_result. Per-peer pull_metas copies isolate peer bookkeeping while sharing the underlying PullReqMeta objects, so counters and the sticky failed flag remain consistent across peers. Adds two unit tests covering partial/duplicate replies, peer-wide errors, exceptions, FINISH with omitted results, and HMA/SWA variants.

**Potential risks**  
The FINISH path now calls _handle_failed_recv on all remaining pending requests, which could misreport failures if a peer legitimately sends FINISH before all its results in some protocol variant. The shallow-copy approach relies on all peers sharing the same PullReqMeta instances; any future code that replaces rather than mutates metas could break counter accounting. Remote quiescence after a local socket timeout is explicitly out of scope, so a timed-out peer could still theoretically write late.

**Key insights**  
The root cause is that failure notification was treated as completion, allowing block reclamation before all writers finished. Deferring completion until pull_tasks_count hits zero for both success and failure paths is the correct invariant. The E2E reproducer (21/20 write-after-free events before, 0 after) and added tests provide strong evidence the fix works, and the change also closes a latent block-leak when P expires requests.

## 8. [[Frontend] Write run-batch responses incrementally instead of at the end](https://github.com/vllm-project/vllm/pull/52505)

  - `tests/entrypoints/launchers/test_run_batch.py`
  - `vllm/entrypoints/launchers/run_batch.py`

### Summary

**What changed and why**  
The run-batch frontend was reworked to stream responses to the output in input order as the batch runs, instead of buffering all responses and writing once at the end. This adds a two-pass input reader (validate then execute), a seekable/staged input abstraction for pipes and URLs, an incremental output writer with truncate-at-start and upload-on-success semantics, a bounded reorder window (16x --max-inflight) to keep the engine busy, and validation of args/batch before the model loads. Tests and README were updated accordingly.

**Technical impact**  
Behavior changes meaningfully: partial output is now persisted on failure/interrupt (a prefix of real responses), output URLs are only uploaded on success, --max-num-queued-reqs/--max-num-queued-tokens are ignored with a warning, and a new --max-inflight option controls concurrency. Memory no longer scales with input size, and malformed batches or bad output paths fail fast before engine startup. The reorder window trades some throughput on heavy-tail workloads for ordered output.

**Potential risks**  
Writing in input order can significantly reduce throughput when a few long requests block the window (reported up to -60% at 1x window, though mitigated at 16x). Interrupts discard finished-but-unwritten responses behind a slow request, so a resume reruns them. URL input download retries on stall with escalating timeouts, which could extend run time on flaky servers. Ignoring admission limits changes engine behavior and may surprise users relying on those flags. The change is large (+947/-137) and touches I/O, staging, and error handling paths, so edge cases around partial lines, symlinks, and FIFOs need care.

**Key insights**  
The PR is well-validated with unit tests, model-launching tests, and real-hardware SIGINT/SIGTERM/SIGKILL experiments showing improved durability and lower RSS. The main design tension is ordered output vs. throughput, addressed via a configurable reorder window. The follow-up resume mechanism (side file for ahead-of-prefix responses) is acknowledged as future work, so current interrupt behavior is a known limitation rather than a regression.

### Summary

**What changed and why**  
The PR changes the FP8 fused-QKV sharding in mimo_v2.py so that, when tp_size is a proper divisor of ckpt_tp and the geometry allows it, the rank's rows are gathered byte-for-byte from the checkpoint instead of going through a dequantize-requantize round trip. Two exact paths are added: a pure block permutation for block-aligned segments (SWA layers), and a zero-padded [Q \\| K V pad] layout for straddling K/V segments (GA/Pro layers), the latter wired via a MergedColumnParallelLinear plus a new _split_qkv forward split. **Technical impact**  
Behavior changes for qualifying geometries: ranks now take checkpoint rows without arithmetic, which should improve numerical fidelity versus the requantizing path. **Potential risks**  
The exact gather is now the default with no environment gate, so deployments on qualifying geometries will change outputs without an opt-out; the PR explicitly notes no model eval was run, so correctness on real models is unverified. The padded layout couples weight-loading order to forward-split order, and a one-sided change could swap K/V rows while shapes stay valid (mitigated by the round-trip test but still a maintenance hazard). The new ValueError path could break loading for checkpoints whose scales are not per chunk that previously loaded (with requantization). MergedColumnParallelLinear may have different quantization/loading semantics than QKVParallelLinear that are not fully exercised here.

**Key insights**  
The core value is eliminating a lossy dequantize-requantize round trip by exploiting checkpoint geometry, which is a meaningful fidelity improvement for FP8 KV/W4A8 recipes. The design cleanly separates geometry detection (_fused_qkv_kv_chunk_rows) from gather logic and forward splitting, and the tests pin writer/reader symmetry.
