## 2. [[Bugfix][LoRA] Slice expert LoRA by the unpadded per-rank size under TP](https://github.com/vllm-project/vllm/pull/61235)


### Base Information

- **PR Number:** #61235
- **Author:** [aoshen02](https://github.com/aoshen02)
- **Merged By:** [jeejeelee](https://github.com/jeejeelee)
- **Merged time:** 2026-10-12 23:25:17
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/61235/files) (1):**
  - `vllm/lora/layers/fused_moe.py`

### Summary

**What changed and why**  
Fixes incorrect expert LoRA slicing under tensor parallelism when the MoE backend pads the expert intermediate dimension (e.g. Marlin, FlashInfer TRTLLM MXFP4). The slice stride in _slice_w13_b and _slice_w2_a previously used moe_config.intermediate_size_per_partition, which RoutedExperts overwrites with the padded size, while base expert weights are sharded by the unpadded size. The PR introduces a _tp_shard_size property using intermediate_size_per_partition_unpadded and pads the w1 half of the concatenated 3D layout so w3 lands at the allocated per-rank offset.

**Technical impact**  
Aligns adapter shard offsets with base weight shard offsets, so every TP rank applies the correct LoRA rows instead of silently reading wrong rows into a zero buffer. No behavior change when the backend does not pad, since the unpadded size equals the padded size. The 3D concatenated (gate, up) layout now zero-pads the w1 slice to the allocated per-rank size before concatenation, matching base w13 layout. Validation shows adapter effect projection improving from 0.38 to 0.76 and MAE returning to the no-adapter floor.

**Potential risks**  
The fix relies on intermediate_size_per_partition_unpadded being correctly populated; if it is None the code falls back to the padded size, preserving the old (buggy) behavior. The GPT-OSS MXFP4 block-aligned shard stride (cdiv(intermediate_size/32, tp_size)*32) is explicitly not addressed and may still mismatch at TP 4/8. The added F.pad allocation on the 3D path adds minor memory/copy overhead per slice. Validation was done outside the test suite, so no CI regression coverage is added.

**Key insights**  
Root cause is a stride mismatch between adapter slicing (padded size) and base weight sharding (unpadded size), masked because slices are copied into zero buffers so nothing raises. The fix is small and targeted (one property plus three call-site changes) and the PR provides thorough empirical evidence including a TP 1 reference comparison. The remaining GPT-OSS block-alignment gap is a known limitation worth tracking separately.

### Base Information

- **PR Number:** #51309
- **Author:** [amd-sriram](https://github.com/amd-sriram)
- **Merged By:** [AndreasKaratzas](https://github.com/AndreasKaratzas)
- **Merged time:** 2026-10-12 22:25:57
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/51309/files) (5):**
  - `tests/kernels/attention/test_rocm_aiter_mla_sink.py`
  - `tests/kernels/attention/test_rocm_aiter_mla_sparse_index_remap.py`
  - `tests/kernels/attention/test_rocm_aiter_mla_sparse_metadata_sync.py`
  - `tests/v1/attention/test_rocm_aiter_triton_sparse_mla.py`
  - `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`

### Summary

**What changed and why**  
The ROCm AITER sparse MLA backend previously remapped the shared top-k buffer into paged_kv_indices on every attention layer, even on non-indexer layers that never write the buffer. This PR adds a per-layer owns_indexer flag and an index_epoch counter (tracked per top-k buffer in a module-level _INDEX_EPOCHS dict keyed by id()), plus remapped_buf/remapped_epoch fields on the metadata, so the remap runs only when the layer owns an indexer, the metadata's remapped epoch is stale, or the buffer differs. This cuts remaps from 78 to 21 per forward pass for GLM-5.2 with index_topk_freq=4.

**Technical impact**  
Behavior is gated on the new is_index_group_leader KV cache grouping so indexer and non-indexer layers get separate metadata instances with independent paged_kv_indices; the first non-indexer layer in each group still remaps, and subsequent ones reuse it until a later indexer write bumps the epoch. The default index_topk_freq=1 path and speculative decoding (which still remaps every layer) are unchanged. Reported kernel launches drop 73.3% and GPU time 73.0%, with ~+0.6% throughput and accuracy within noise.

**Potential risks**  
The epoch counter is keyed by id() of the top-k buffer, which is fragile: a freed buffer's id can be reused by a new tensor, and the dict is never pruned, so correctness depends on buffers outliving all readers and on construction order matching layer order. The skip logic also assumes non-indexer layers never mutate the buffer or the remap inputs (req_id_per_token, block_table, paged_kv_indptr); any future path that changes those on a non-indexer layer would silently reuse stale indices. The tests patch internals heavily and rely on an autouse fixture clearing _INDEX_EPOCHS, so coverage of real multi-group metadata behavior is limited.

**Key insights**  
The core insight is that remap validity is a property of the metadata's paged_kv_indices, not of the layer, so the cache key must combine the source buffer identity and the indexer-write epoch rather than just checking indexer presence. The PR description's table and the regression test for cross-layer index sharing (RULER collapse to 0.026) show that a naive buffer-only check was insufficient and the epoch is what makes reuse safe. The id()-keyed global dict is the main maintainability concern and would be more robust as a per-buffer attribute or weak-reference map.

## 7. [[ROCm][Perf] Skip cleaning sparse prefill MQA logits](https://github.com/vllm-project/vllm/pull/51314)

  - `tests/v1/attention/test_rocm_aiter_mla_sparse.py`
  - `vllm/v1/attention/ops/rocm_aiter_mla_sparse.py`

### Summary

**What changed and why**  
The sparse prefill path in rocm_aiter_mla_sparse.py now passes clean_logits=False to AITER's fp8_mqa_logits, so the MQA-logits buffer is allocated with torch.empty instead of torch.full(..., -inf), eliminating an FP32 fill kernel launched before every logits kernel. A new ROCm/AITER-gated test asserts that clean_logits=False is forwarded. The motivation is a measured ~0.89% reduction in GPU kernel time and improved TTFT on the prefill path.

**Technical impact**  
Removes a serialized FP32 fill kernel (reported 18,162 launches / 1,250 ms in the capture) from the sparse prefill path, shifting the buffer to uninitialized memory. The only consumer, top_k_per_row_prefill, reads rows only within [cu_seqlen_ks, cu_seqlen_ke) and guards the final partial vectorized load, so padding is never read and top-k results are unchanged. Reported e2e effect is modest: ~+0.1% throughput and ~-1.1% TTFT geomean at ISL 8192, with accuracy within run-to-run noise.

**Potential risks**  
Correctness now depends on the AITER kernel never reading outside the valid row range; any future change to top_k_per_row_prefill or its vectorized tail handling that touches padding could expose uninitialized (garbage) values instead of -inf. The test only verifies the flag is forwarded, not that results are numerically identical, and it is skipped entirely without ROCm+AITER, so coverage is limited to that environment. The performance gains are small and largely within measurement spread, so the benefit is marginal relative to the added coupling to AITER's clean_logits contract.

**Key insights**  
A targeted micro-optimization that trades a defensive -inf initialization for reliance on a documented read-range invariant in the downstream kernel. The safety argument is sound given current top_k_per_row_prefill behavior, but the guarantee is implicit and would benefit from a numerical equivalence test (comparing top-k indices against the clean_logits=True path) rather than only a flag-forwarding assertion. Overall low-risk, low-reward change appropriate for the ROCm sparse prefill path.
