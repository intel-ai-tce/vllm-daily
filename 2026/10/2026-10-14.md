  - `vllm/multimodal/video_decoders/pynvvideocodec.py`

### Summary

**What changed and why**  
This PR fixes two PyNvVideoCodec failure modes: a failed decode poisoning a cached decoder slot, and resolution changes growing the cached frame pool and leaking replaced decoders until GPU memory is exhausted. It adds pre-construction stream capability validation, bounded decoder dimensions (max_width/max_height), batched decoding (32 frames per batch with per-batch sync/release), slot retirement/recovery logic, and dimension-aware GPU memory reservation. Tests and docs are updated accordingly.

**Technical impact**  
Decoder slots now carry max_width/max_height and are rebuilt when a new source exceeds them, with failed slots removed from the pool rather than returned. Memory reservation in gpu_ipc_memory.py now scales with configured decoder dimensions via get_pynvvideocodec_decoder_gpu_memory_bytes, and max_width/max_height are treated as startup-only kwargs (stripped from runtime overrides). Batched decoding bounds native frame surface retention, and recovery distinguishes stream-local rebuild from device-wide cleanup.

**Potential risks**  
The new _validate_decoder_caps path adds a CreateDemuxer call per request and depends on GetDecoderCaps semantics that may vary across PyNvVideoCodec versions (validation was on 2.0.4, while the description references 2.2.3 behavior). Default orientation-envelope logic and clamping could reject or mis-size streams in edge cases (e.g., macroblock limits, unusual aspect ratios). Full 300-video H200 validation is still pending, and the memory-budget formula is a heuristic that may under- or over-reserve for some codecs. Behavior changes to exception chaining (__cause__/__context__ now None) could affect callers relying on the previous chained errors.

**Key insights**  
The fix addresses root causes rather than symptoms: bounding decoder dimensions at construction prevents pool growth, and retiring failed slots prevents poisoned decoders from being reused. Keeping routine rebuilds stream-local while reserving device-wide recovery for failed requests is a sound performance tradeoff. The dimension-aware memory reservation is a meaningful correctness improvement for large-resolution workloads, but the pending full-scale H200 validation and version-dependent decoder caps are the main areas to watch before merge.

  - `vllm/v1/kv_offload/cpu/host_register.py`
  - `vllm/v1/kv_offload/cpu/shared_offload_region.py`

### Summary

**What changed and why**  
The PR changes host-registration of the shared CPU offload region so that, outside the replicated layout, each worker pins only its own slot of every row (page-rounded) instead of the entire shared region. Previously every worker cudaHostRegister'd the whole region, causing redundant pinning (e.g., 4x at TP4). A new iter_worker_slot_ranges helper in SharedOffloadRegion is reused for both MADV_POPULATE_WRITE and registration, and a MIN_HOST_REGISTER_SAVED_BYTES threshold decides when per-slot registration is worthwhile. A cached CudaRTLibrary wrapper avoids repeated runtime construction.

**Technical impact**  
Reduces pinned memory per rank substantially (e.g., 68.8 GB vs 274.9 GB at TP4), cutting offload startup and pinning time (63.6s to 34.8s, 20.8s to 6.8s in the reported benchmark). The replicated layout and small-savings cases still register the whole region, preserving existing behavior. The change touches the pinning path used by both OffloadingSpec and TieringOffloadingSpec workers, so it affects all CPU offload users. The functools.cache on _get_cudart is a process-wide singleton, which is reasonable for a runtime wrapper but introduces shared state.

**Potential risks**  
Correctness depends on the slot ranges being page-aligned and non-overlapping across workers; a bug in iter_worker_slot_ranges could cause unpinned or double-pinned pages, leading to silent performance regressions or registration failures. The savings threshold (3 MiB) is heuristic and may behave differently across hardware or driver limits. The cached CudaRTLibrary could mask initialization errors or leak state across tests/processes if the runtime is torn down. Rollback logic on partial failure must still correctly unregister only the ranges actually registered. The benchmark is on a specific commit and hardware, so broader validation is limited.

**Key insights**  
The refactor nicely unifies the populate and register range computation via iter_worker_slot_ranges, reducing duplication and ensuring both paths agree on which pages a worker owns. The decision to fall back to whole-region registration based on bytes saved rather than row count is a sensible guard against per-call overhead dominating. Test coverage is strong, including a parametrized check that large row counts do not disable slot registration and a test for cudart reuse. The reported 3x reduction in pinning time is a meaningful win for large TP/EP deployments.

## 5. [[Perf][KV Connector][Mooncake] Send the KV layout once per peer](https://github.com/vllm-project/vllm/pull/59825)


### Base Information

- **Author:** [staryxchen](https://github.com/staryxchen)

- **Merged time:** 2026-10-14 22:36:32
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/59825/files) (3):**
  - `tests/v1/kv_connector/unit/test_mooncake_connector.py`
  - `tests/v1/kv_connector/unit/test_mooncake_connector_hybrid_mamba.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py`

### Summary

**What changed and why**  
The MooncakeConnector now exchanges the decode KV layout once per peer instead of embedding the full ~9 KB region layout in every pull. Decode mints a random 63-bit layout_id at register_kv_caches, sends the layout only until prefill echoes that id back, and prefill caches aligned regions per (host, port, tp_rank, pp_size, tp_size, layout_id) in an LRU. A new LAYOUT_MISS status triggers a one-time resend, and old peers that never echo keep receiving the full layout, preserving mixed-version correctness.

**Technical impact**  
Per-pull metadata drops from ~9500 B to ~316 B per rank on a 146-region model, and prefill control-plane time per pull falls from ~0.078 ms to ~0.014 ms P50. Behavior is backward compatible in both directions because layout-less pulls are only sent after an echo and old decodes send layout_id=0. The change adds ~130 net lines to the connector, a new response status, and an LRU cache, with unit tests covering resend, old-peer, reused-id, and eviction paths.

**Potential risks**  
The LAYOUT_MISS resend, same-address-new-id reuse, and LRU-eviction-then-resend paths have unit coverage only, not end-to-end, because restarted peers always get new ports. The LRU is bounded at 1024 but _prepared_transfer_regions remains unbounded and grows on every decode restart. There are known textual conflicts with #59592 (remote_block_size must be set on both full and layout-less pulls) and #59625 (sleep-mode re-registration). A prefill restart still requires a proxy restart, and empty req_blocks still gets no response.

**Key insights**  
The design mirrors NixlConnector's exchange-once model but piggybacks the layout on the first pull rather than adding a handshake round trip, using the layout_id echo as the handshake response. Random nonzero layout ids avoid stale matches across restarts, and eviction is always safe since it only costs a resend. The stated benefit is fixed per-pull overhead that scales with region count and layer-name length, not a TTFT win at current scale, so the tradeoff is complexity for future-proofing deeper and multi-cache models.

### Summary

**What changed and why**  
Adds a 30-second progress deadline for unanswered P2P LookupMsg probes in the KV offload client, so a peer that keeps its transport alive but stops answering lookups no longer leaves the consumer returning RETRY indefinitely. The deadline starts on the first unanswered batch, is rearmed only by responses that resolve previously unanswered probes, and is cleared on full resolution, fetch, or request finish. On expiry the session sends a best-effort DisconnectMsg and marks the whole peer session dead, letting the manager fall back to local prefill (MISS). Server-side result draining was also reordered so deferred store results are collected after transfer finalization, and a Ruff datetime.UTC fix was applied to a sweep tool.

**Technical impact**  
Changes behavior in the P2P session state machine: flush_pending_lookups now takes a send_ready flag and is gated on ConnectAckMsg, new per-request deadline tracking is added to the client, and session.poll() checks lookup expiry after draining buffered messages and completed transfers. Expiry triggers a session-wide teardown rather than a request-local failure, so other outstanding work on the same peer also fails via the existing disconnect path. Server collect_results now drains _pending_store_results after finalization, changing when deferred store results surface (same poll instead of next poll). Wire format and model computations are unchanged.

**Potential risks**  
The session-wide failure policy is aggressive: one stalled lookup kills all in-flight work on that peer, and the PR notes maintainer agreement on this is still pending. The pre-handshake ConnectAck wait remains unbounded (#51504), so issue #56823 is only partially addressed. The 30s deadline is a progress timeout, not a per-key age limit, so a peer that trickles partial responses could keep a request alive longer than expected. Reordering store-result draining could affect callers that relied on next-poll delivery, though tests were updated. Validation is CPU-only for this revision; no new GPU/NIXL transfer results are claimed.

**Key insights**  
The fix correctly distinguishes progress (resolving previously unanswered probes) from activity (duplicate responses, unknown keys, new keys, repeated polls), which prevents a stalled peer from indefinitely extending the deadline. Draining buffered messages and completed transfers before expiry preserves timely replies and completed load/store results during teardown. The reconnect regression test with real loopback TCP/ZMQ and a negative control (reverting server.py/session.py makes regressions fail) provides reasonable confidence. The main open question is whether session-wide teardown is the right blast radius versus a request-local timeout, which the PR explicitly argues against because it would leave the stalled peer available for future requests.
