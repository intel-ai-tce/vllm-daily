## 1. [[Bugfix][Multimodal] Fix per-video cache option reuse](https://github.com/vllm-project/vllm/pull/55203)


### Base Information

- **PR Number:** #55203
- **Author:** [bvolpato](https://github.com/bvolpato)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)
- **Merged time:** 2026-10-10 23:21:56
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/55203/files) (3):**
  - `tests/models/multimodal/processing/test_qwen3_vl.py`
  - `vllm/model_executor/models/qwen3_vl.py`
  - `vllm/multimodal/processing/processor.py`

### Summary

**What changed and why**  
Fixes a multimodal caching bug in Qwen3-VL where per-video sampling options (fps, num_frames) were not part of each video's cache identity, causing repeated videos to reuse the first video's result despite different settings, and partial cache hits to drop videos without dropping their corresponding option entries. The fix adds overridable hooks (_get_mm_hashes, _get_cache_missing_processor_kwargs) in the base processor and implements them in Qwen3VLMultiModalProcessor to fold per-video options into hashes and to filter option lists in sync with cache misses. It also adds a guard rejecting option lists shorter than the number of videos.

**Technical impact**  
Changes cache identity computation for Qwen3-VL videos so that fps/num_frames participate in hashing, and aligns option-list filtering with partial cache hits, which alters cache hit/miss behavior and stored hashes for affected requests. The base processor refactor is behavior-preserving for other models since the new hooks default to the prior logic. A new ValueError is raised for malformed short option lists, and the final text/image HF call now suppresses configured video lists to prevent merging from reintroducing them.

**Potential risks**  
Cache identity changes may invalidate previously cached entries or cause extra cache misses for equivalent reordered requests, as the PR itself notes. The new ValueError could surface as a regression for callers who previously passed short lists (though those previously hit an IndexError). The suppression of video kwargs in the final HF call and the interaction with model defaults and nested/flat scopes are subtle and could affect other processors if the hooks are misused. Validation is limited to a 2B model comparison and CPU test suites, with CUDA sleep/wake integration skipped.

**Key insights**  
The root cause is that request-wide option-list hashes let repeated videos reuse the first video's result, and partial hits removed videos without removing matching option entries. The fix is well-scoped to the Qwen3 processor via new base-class extension points, preserving other processors' behavior. Test coverage is broad, exercising duplicates, partial hits, reordering, UUID reuse, flat/nested scopes, warm caches, and profiling with fewer videos than configured options, plus a loaded-model comparison showing identical outputs and logprobs.

## 2. [[Perf][MiniMax-M3] MSA prefill attends with the E4M3 query; bump fmha_sm100 to 968061a](https://github.com/vllm-project/vllm/pull/60684)

  - `vllm/models/minimax_m3/nvidia/model.py`
  - `vllm/models/minimax_m3/nvidia/sparse_attention_msa.py`

### Summary

**What changed and why**  
MiniMax-M3 MSA prefill previously dequantized the E4M3 query back to BF16 before every prefill call. Since both fmha_sm100 prefill kernels accept an E4M3 query natively, prefill now passes the FP8 query through directly and folds q_scale into softmax_scale, eliminating the BF16 copy. The PR also bumps the fmha_sm100 (MSA) dependency from be4a52a to 968061a, which brings the Blackwell prefill port, and updates the cmake install list for newly imported files.

**Technical impact**  
Changes the prefill attention data path in vllm/models/minimax_m3/nvidia/sparse_attention_msa.py so FP8-cache prefill runs FP8 QK/PV MMAs instead of staging K/V to BF16, and the NVFP4 kernel dequantizes to E4M3 rather than BF16. Reported gains are 26-37% faster prefill with an FP8 KV cache and 8-13% with NVFP4 on GB300. BF16 caches and the Triton decode fallback are unchanged, and the MSA function signatures vLLM calls are preserved.

**Potential risks**  
The E4M3-query kernels round softmax probabilities (and K/V for NVFP4) to E4M3, introducing small numerical error; tests relax tolerance to allow up to 1e-4 of elements outside atol/rtol 0.05 with a 0.25 bound, and the NVFP4 reference had to be changed to the E4M3-staged cache, which weakens the exactness guarantee. Validation is kernel-level only with no end-to-end accuracy eval or serving benchmark, and the E4M3-query NVFP4 kernel is untested on SM107. The dependency pin bump also pulls in new MSA code paths that could affect behavior beyond the intended change.

**Key insights**  
The core win is avoiding a redundant BF16 query copy and enabling native FP8 MMAs in prefill, with the pin bump alone contributing a smaller share of the FP8 gain. The test changes are meaningful: they monkeypatch the MSA kernels to assert the query dtype is float8_e4m3fn and add a new FP8-cache prefill test covering chunked prefill over cached context. The tolerance relaxation is justified by per-split E4M3 probability rounding tied to SM count, but reviewers should weigh the reduced reference strictness and the absence of end-to-end validation.

## 4. [[Bugfix][KV Connector] Fix speculative block reservations across KV cache groups](https://github.com/vllm-project/vllm/pull/59880)


### Base Information

- **PR Number:** #59880
- **Author:** [bzsuni](https://github.com/bzsuni)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-10-10 20:55:41
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/59880/files) (3):**
  - `tests/v1/kv_connector/unit/test_remote_prefill_lifecycle.py`
  - `tests/v1/kv_connector/unit/utils.py`
  - `vllm/v1/core/sched/scheduler.py`

### Summary

**What changed and why**  
Fixes speculative decode block reservation for async KV loads across multiple KV cache groups. Previously the scheduler converted the speculative token margin to blocks once using the scheduler block size, which under-reserved when groups use different allocation block sizes, potentially admitting a request that could not start decoding after its async load completed. The fix precomputes _spec_decode_step_blocks by summing cdiv(num_spec_decode_tokens, manager.block_size) over non-Mamba single_type_managers, and folds the spec margin into the token count passed to get_num_blocks_to_allocate.

**Technical impact**  
Changes scheduler admission accounting for async KV loads: reservations now reflect each cache manager's actual block size and exclude Mamba managers (which already account for their speculative state blocks), avoiding double reservation. The helper _spec_decode_step_blocks() method is replaced by a cached attribute computed at init, and _request_remaining_blocks now adds the spec/lookahead token margin before block conversion. Tests are extended to cover single-group, multi-group, mixed-block-size, and Mamba hybrid configurations, plus a new test asserting no double reservation for Mamba spec blocks.

**Potential risks**  
The precomputed _spec_decode_step_blocks assumes kv_cache_manager.coordinator.single_type_managers is fully populated and stable at scheduler init; any later mutation of managers or block sizes would make the cached value stale. Excluding MambaSpec managers relies on Mamba managers internally accounting for speculative blocks, so a regression there could reintroduce under-reservation. Validation was limited to simulated remote completion without live NIXL P/D or model-level runs, and the broader suite still showed 46 pre-existing failures, so real-world KV pressure behavior is not fully proven.

**Key insights**  
The core bug was a unit mismatch: one global block-size conversion cannot represent per-group allocation when groups have heterogeneous block sizes, and simply multiplying by group count fails for mixed sizes. Summing per-manager cdiv is the correct generalization, and the Mamba exclusion highlights that some managers already embed speculative state accounting, making naive summation double-count. The regression test wisely asserts admission and scheduling outcomes rather than helper arithmetic, which better captures the end-to-end deadlock scenario.

  - `tests/distributed/test_packed_tensor.py`
  - `vllm/distributed/weight_transfer/packed_tensor.py`

### Summary

**What changed and why**  
The PR fixes packed weight transfer for 0-D (scalar) tensors. On the producer side, pack_tensors and packed_ipc_producer now flatten with .view(-1) before reinterpreting to uint8, avoiding the RuntimeError that occurs when reinterpreting a 0-dim tensor across dtypes of different element sizes. On the consumer side, unpack_tensor now calls .view(shape) instead of .view(*shape), which correctly handles an empty shape list for scalars. Tests were extended with a parameterized CPU pack/unpack scalar test and a scalar added to the existing CUDA IPC round-trip test.

**Technical impact**  
The change is a small, targeted bug fix in vllm/distributed/weight_transfer/packed_tensor.py that makes packed mode accept the same inputs as the unpacked IPC path, which already round-trips 0-D tensors. The flatten-before-reinterpret ordering matches existing patterns elsewhere in the codebase (shm_broadcast, ec_transfer, fused_moe, fbgemm). For all non-scalar shapes the operations are byte-identical, so existing behavior is preserved. The new CPU test is device-agnostic and covers float32, float16, and bfloat16.

**Potential risks**  
The full CUDA/IPC suite was not rerun after the latest test-only simplification, so the CUDA path relies on the earlier reported results. The .view(shape) change preserves view semantics but would still fail for non-contiguous tensors if the preceding .contiguous() were removed; currently contiguous() is applied first, so this is safe. Scalar handling downstream depends on weight_loader reshaping shape-less weights, which is outside this PR's scope. No other callers of unpack_tensor or pack_tensors appear to depend on the previous argument-unpacking behavior.

**Key insights**  
The root cause was an ordering issue: dtype reinterpretation requires dim() > 0, so flattening must precede the uint8 view. Using view(shape) rather than view(*shape) is the minimal correct fix for empty shapes and avoids changing semantics for non-empty shapes. The PR correctly aligns packed mode with the already-working unpacked IPC path and adds focused regression coverage, though a full CUDA suite rerun would strengthen confidence.
