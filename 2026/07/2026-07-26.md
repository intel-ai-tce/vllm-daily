  - `rust/src/cmd/src/cli/tests.rs`
  - `rust/src/managed-engine/src/cli.rs`

### Summary

**What changed and why**  
Moved `max_model_len` from `SharedRuntimeArgs` (used by both frontend and serve) to `ManagedEngineArgs` (only used by serve). This fixes a deserialization bug where Python sends `-1` for `auto` but the Rust field was `Option<u32>`, causing serde to reject it. Now the frontend ignores `max_model_len` from JSON args, and serve forwards the raw string to Python without Rust validation.

**Technical impact**  
The Rust frontend no longer accepts `max_model_len` from `--args-json`, preventing the serde error. The serve command now stores `max_model_len` as `Option<String>` and passes it verbatim to the Python engine, supporting values like `auto`. Tests were updated to reflect the new field location and behavior.

**Potential risks**  
Low risk. The change is well-scoped: it only affects how `max_model_len` is parsed and forwarded. Existing frontend deployments that relied on `max_model_len` in `--args-json` will need to remove it, but that field was broken for `auto` anyway. The serve path remains backward-compatible.

**Key insights**  
The root cause was a type mismatch between Python's sentinel `-1` and Rust's `Option<u32>`. By moving the field to `ManagedEngineArgs` and using `Option<String>`, the Rust frontend avoids parsing engine-owned values, and the serve command preserves Python's original semantics.

### Summary

**What changed and why**  
Optimized the GDN convolution path for speculative decoding on CPU by replacing the fallback PyTorch conv1d loop with a native C++ kernel that uses AMX tile instructions. The change adds a new `causal_conv1d_update_multi_kernel_impl` function that processes multiple tokens per sequence in a single call, and updates the Python layer to use this kernel when AMX is available and conditions are met (width=4, equal sequence lengths). The conv state buffer layout is extended from `width-1` to a larger `state_len` to support rolling history for multi-token prediction.

**Technical impact**  
Improves CPU serving performance for Qwen3.5 GDN speculative decoding with MTP by 17-18% (output tokens/s) for k=1 and k=3, while maintaining accuracy. The change also adds support for 3D input tensors (batch, seqlen, dim) in the conv1d update kernel, enabling batched multi-token processing. The native kernel only supports width=4 and requires AMX support, so systems without AMX will use the slower fallback. The new kernel uses `std::memmove` and `std::memcpy` for state updates, which may have alignment or performance implications on some architectures. The accuracy tests show no regression, but edge cases with varying sequence lengths or non-contiguous indices could trigger the fallback path.

**Key insights**  
The optimization leverages AMX tile registers to fuse the convolution and state update into a single kernel, avoiding the overhead of multiple PyTorch ops and data copies. The design separates the conv1d update into two phases: a parallelized kernel for the convolution output and a sequential memmove/memcpy for state rolling. The Python layer uses a heuristic to decide when to use the native kernel (AMX, width=4, equal sequence lengths), falling back to the original loop otherwise.
