**Key insights**  
The fix addresses a protocol boundary issue where a valid encoding caused a panic. The approach distinguishes between zero rows (empty logprobs) and zero columns with rows (invalid). The tests cover both cases and confirm no regression in downstream tests.

### Summary

**What changed and why**  
Fixed a bug where aborting a queued request (one that never received KV block allocation) caused an assertion failure in the KV offloading scheduler. The root cause was that `storable_chunks()` could return a positive number even when no blocks were allocated, leading to a mismatch between offload keys and block IDs. The fix caps the number of storable chunks to the number of allocated blocks, and adds a unit test to prevent regression.

**Technical impact**  
Prevents a fatal crash (AssertionError) in the KV offloading path when a request is aborted before any KV blocks are allocated. The change is minimal and localized to the `storable_chunks` method and its callers, ensuring that store jobs are only built for requests that actually have allocated blocks. The new test validates the fix for both synchronous and asynchronous scheduling modes.

**Potential risks**  
Low risk. The change only adds a safety cap (`min(num_chunks, num_allocated_chunks)`) and passes the `group_state` parameter to `storable_chunks`. Existing behavior for requests with allocated blocks is unchanged. The test covers the edge case of aborted queued requests. No performance impact is expected.

**Key insights**  
The bug was triggered by an assumption that all offloaded chunks have corresponding block IDs, which fails for aborted requests that never ran. The fix ensures that `storable_chunks` respects actual allocation, making the scheduler robust to early aborts. The test reproduces the exact scenario from the issue and confirms the fix works.

**Key insights**  
The root cause was a circular import triggered by warning_once()'s lazy import of parallel_state during module initialization. The fix is a targeted revert that breaks the cycle without altering the shared logging infrastructure. The new test script fakes an old WSL kernel to reproduce the issue and verify the fix.

### Summary

**What changed and why**

The new mapping ensures adjacent threads access consecutive int32 words within the same row, fully coalescing memory accesses.

**Technical impact**  
Improves performance of AWQ int4-fp8 weight preprocessing kernel by 2.22x (from 1291.1 us/iter to 581.9 us/iter) on a 16384x16384 matrix. The grid dimensions changed from (size_k/32, size_n/8) to (size_k, (size_n/8+31)/32), and alignment requirement relaxed from size_n%256==0 to size_n%8==0 with a tail boundary check. Correctness is preserved as the same element space is covered exactly once.

**Potential risks**  
Low risk. The change is logically equivalent and covered by existing tests. The tail boundary check (if (col >= size_n/8) return) handles non-multiple-of-32 column sizes correctly. The (void)size_k; line silences an unused variable warning but does not affect behavior. Performance regression is unlikely given the nature of the fix.

**Key insights**  
Non-coalesced memory access is a common performance pitfall in GPU kernels. This fix demonstrates a simple thread remapping that yields significant speedup (2.22x) without algorithmic changes. The use of blockIdx.y for the column dimension and threadIdx.x for the column offset is a standard pattern for coalesced access. The PR also includes a clear performance benchmark and correctness tests, making it a well-documented optimization.

Tests have been updated to match the new return types, but edge cases (e.g., empty tensors, passthrough values) should be verified.

**Key insights**  
The optimization leverages Rust's borrowing and slicing to avoid unnecessary allocations, a classic zero-copy pattern. The benchmark confirms significant performance gains.
