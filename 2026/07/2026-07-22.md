No change in dtype, shape, or arithmetic. Low risk given these guarantees.

**Key insights**  
Simple in-place changes (mul_, add_) avoid temporary allocations that caused OOM in memory-constrained scenarios. The fix is general and benefits all hardware by reducing memory pressure. ### Summary

**What changed and why**  
Changed two occurrences of `.expand()` to `.repeat()` for shared NVFP4 MoE input scales in `flashinfer_fp4_moe.py`. `.expand()` creates views with overlapping memory (stride-zero), which prevents in-place copy operations needed during layerwise reload. `.repeat()` materializes independent per-expert storage, fixing a RuntimeError. Added a regression test in `test_trtllm_nvfp4_hidden_dim_padding.py` that verifies the scales are writable.

**Technical impact**  
Fixes a bug where NVFP4 online quantization of Qwen3 30B A3B failed during layerwise reload with 'unsupported operation: more than one element of the written-to tensor refers to a single memory location'. The fix ensures that shared input scale tensors have contiguous, writable storage, enabling correct copy-back of regenerated values. The change is minimal (4 lines) and only affects the memory layout of the scale tensors.

**Potential risks**  
Low risk. `.repeat()` allocates new memory, which may slightly increase memory usage (proportional to number of experts). However, the tensors are small (1D of length num_experts). The behavior is functionally equivalent for read-only use cases. The test covers the writability requirement. No other code paths depend on the stride-zero behavior.

**Key insights**  
The bug was caused by PyTorch's `.expand()` returning a view with overlapping memory, which is not writable in-place. Using `.repeat()` instead creates a contiguous copy. The fix is a one-line change in two functions, demonstrating how subtle tensor memory layout issues can cause runtime errors in model reloading. The regression test explicitly validates that the scales can be copied into after preparation.

  - `vllm/v1/core/kv_cache_coordinator.py`
  - `vllm/v1/core/kv_cache_manager.py`
  - `vllm/v1/core/sched/scheduler.py`

### Summary

**What changed and why**  
Fixes a bug where per-group prefix hits diverge for hybrid models (Mamba + full attention) with a KV connector. Under block pressure, one group's cached prefix may be evicted while another's survives, causing the scheduler to incorrectly report a deeper hit as locally computed, leading to engine crashes or dirty KV. The fix introduces a new method `get_computed_blocks_for_connector` that uses the full-attention group's hit length as the local prefix and flags divergence. If no external tokens are found to back the deeper hit, it falls back to the reconciled boundary that all groups agree on.

**Technical impact**  
Adds a new method to `KVCacheManager` and modifies the scheduler's `schedule` method to handle per-group hit divergence. The `HybridKVCacheCoordinator` now stores a `full_attention_group_id` for reference. Tests are added to verify both directions of divergence (FA deeper and Mamba deeper) and ensure the scheduler falls back correctly. The change is backward-compatible for non-hybrid models and cases without divergence.

**Potential risks**  
The fix relies on the assumption that full-attention groups are downward-closed; if this assumption is violated, the logic may misbehave. The new code path is only active for hybrid models with a connector, so non-hybrid models are unaffected. There is a slight performance overhead from the per-group lookup and divergence check, but it is negligible compared to the cost of incorrect scheduling.

**Key insights**  
The root cause is that per-group prefix hits can diverge due to eviction, and the scheduler must not assume the deepest hit is valid for all groups. The fix uses the full-attention group's hit as the conservative local prefix and relies on the connector to supply missing tokens. If the connector provides no external tokens, the scheduler falls back to the reconciled boundary, ensuring correctness at the cost of recomputing some tokens.
