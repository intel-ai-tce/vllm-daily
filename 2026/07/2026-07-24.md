  - `vllm/multimodal/media/video.py`

### Summary

**What changed and why**  
Made the number of retained PyNvVideoCodec hardware decoders configurable via a new `hw_decoders` media I/O option, replacing the previously fixed single decoder slot. This improves throughput in frontend-heavy workloads by allowing concurrent GPU video decoding. The default is set to 2, which showed up to 94% improvement in testing.

**Technical impact**  
Adds a new startup-only configuration parameter `hw_decoders` that controls the size of the decoder pool. GPU memory reservation scales with this value and the number of API server processes. The decoder pool is now dynamically bounded by the configured count instead of a constant. Request-level overrides are stripped to prevent runtime memory mismatches. Validation ensures the value is a positive integer and that the configuration is set only once.

**Potential risks**  
Increasing `hw_decoders` increases GPU memory usage, which could cause OOM if not accounted for. The default change from 1 to 2 may increase memory pressure for existing deployments. The configuration is immutable after startup, so misconfiguration requires a restart. The change touches memory reservation logic, which could affect KV cache sizing and overall GPU memory utilization.

**Key insights**  
The change introduces a trade-off between decoder concurrency and GPU memory. The recommended default of 2 balances throughput gains with memory overhead. The implementation uses a class-level slot pool with a condition variable for thread safety, and the configuration is validated and locked at first use. Tests cover slot bounding, configuration immutability, and rejection of invalid values.

### Summary

**What changed and why**  
Replaced the model-wide KV-head dedup logic (single put_step/head_or_tp_rank) with per-group TP replication factors. Each KV-cache group now has its own factor: MLA groups replicate across all TP ranks, GQA groups replicate across tp_size/num_kv_head ranks, and Mamba/linear-attention groups (which are head/dim-sharded) have factor 1. This fixes silent state corruption in hybrid models with TP>1 where Mamba state was incorrectly deduped across ranks.

**Technical impact**  
The Mooncake store connector now correctly handles TP-sharded Mamba/linear-attention state by writing every block on every rank (no striping) and using per-rank key namespaces. The lookup logic checks all shard keys per group before reporting a boundary hit. The change affects key namespace generation, PUT striping, and exists accounting, but preserves byte-identical store keys for all currently supported models. Three files modified: worker.py (+97/-78) and two test files (+214/-15).

**Potential risks**  
Risk of regression for non-hybrid models (MLA-only or GQA-only) if the per-group factor computation is incorrect. The PR includes tests for mixed MLA+GQA+Mamba and uniform groups, and e2e validation on DeepSeek-V4-Flash (MLA) shows no regression. Another risk is performance impact from writing every block for sharded groups (more PUTs), but this is necessary for correctness and only applies to Mamba groups which are typically few. The DCP path is explicitly guarded (factor=1) to avoid namespace collisions.

**Key insights**  
The root cause was treating replication as a model-wide property when it is actually per-group. The fix uses a simple classification of KV-cache specs (Mamba, MLA, GQA) to derive the replication factor. The PR includes comprehensive unit tests that reproduce the bug on main and verify the fix, plus e2e tests showing zero divergence for hybrid models and no regression for MLA models.
