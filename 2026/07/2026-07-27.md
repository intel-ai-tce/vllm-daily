## 7. [[Bugfix][KV Offload][OBJ] Preserve job completion during cleanup](https://github.com/vllm-project/vllm/pull/49947)


### Base Information

- **PR Number:** #49947
- **Author:** [mindungil](https://github.com/mindungil)
- **Merged By:** [orozery](https://github.com/orozery)
- **Merged time:** 2026-07-27 21:10:53
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/49947/files) (2):**
  - `tests/v1/kv_offload/tiering/test_obj_tier.py`
  - `vllm/v1/kv_offload/tiering/obj/manager.py`

### Summary

**What changed and why**  
The OBJ secondary tier manager's transfer cleanup logic was reordered to keep transfer entries in `_transfers` until `release_xfer_handle()` succeeds, preventing premature removal that could lose job completion. Previously, the transfer was removed before releasing NIXL resources; if `release_xfer_handle()` raised, no `JobResult` was published and the state was lost. The fix retries cleanup on the next scheduler step and treats descriptor-list and memory deregistration failures as best-effort to avoid suppressing job completion.

**Technical impact**  
This change ensures that job completion is always published exactly once, even when NIXL transfer handle release fails. It prevents pinned CPU cache blocks and stalled `has_pending_work()` by preserving the transfer entry until the handle is safely released. The parent `TieringOffloadingManager` can then correctly pop transfer jobs and call `primary.complete_read()`. The fix also adds regression tests that inject failures in `check_xfer_state()` and `release_xfer_handle()` to verify the retry behavior and end-to-end cleanup with the real manager.

**Potential risks**  
The retry loop could theoretically delay cleanup indefinitely if `release_xfer_handle()` keeps failing, but NIXL's contract indicates that repeated failures are unlikely and the transfer handle is not freed until success. The best-effort handling of `release_dlist_handle` and `deregister_memory` may leak NIXL metadata on persistent failures, but this is acceptable because no active data transfer remains. The change is localized to the OBJ tier manager and does not affect other tiers or model output.

**Key insights**  
The root cause was a race between transfer removal and resource release: removing the transfer entry before releasing the handle meant that a failure in `release_xfer_handle()` left no state to retry. The fix inverts the order and adds a retry mechanism, aligning with NIXL's documented behavior that releasing an active transfer can fail. The regression test uses mock injection to simulate real transport cancellation failures, which are hard to reproduce deterministically. The live validation with a real S3 backend confirms the normal path still works.

  - `vllm/v1/kv_offload/tiering/fs/io.py`
  - `vllm/v1/kv_offload/tiering/fs/manager.py`

### Summary

**What changed and why**  
Added C implementations of batch_store_block and batch_load_block that run GIL-free, and changed the thread pool to assign one job per request (batching all keys into a single task) instead of one task per key. This improves disk utilization by reducing GIL contention and allowing larger sequential I/O.

**Technical impact**  
Introduces a new C extension (fs_io_C) with batch I/O functions that release the GIL, and refactors the Python I/O layer to batch all keys of a request into a single call. The thread pool now enqueues one task per job instead of one per key, which changes concurrency granularity. Performance benchmarks show ~35% throughput improvement (from 1.7 to 2.3 req/s) and higher disk utilization (from <60% to ~80%).

**Potential risks**  
The 1-request-to-1-thread mapping may be detrimental at low concurrency; the PR notes this and suggests future batching at the key level. The C code uses O_DIRECT which requires aligned buffers; misaligned buffers will cause EINVAL errors. Error handling in the C extension removes partially written files on failure, which is safe but could mask transient errors. The change modifies the thread pool interface (enqueue_store/enqueue_load now expect a single task instead of an iterable), which could break other users of DualQueueThreadPool if any exist.

**Key insights**  
The main optimization is moving I/O work to GIL-free C code, not batching per se. The performance gain is significant even with few threads, indicating that GIL contention was a major bottleneck. The PR deliberately defers key-level batching to a follow-up, keeping this change focused on the C implementation. The test suite is extended to cover both C and Python paths, including edge cases like empty batches and out-of-bounds block IDs.
