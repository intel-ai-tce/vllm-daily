### Summary

**What changed and why**  
This PR introduces a set of Blackwell (SM100) decode optimizations for the GLM-5.2 model, including a new bf16 skinny GEMM kernel for small-batch decode shapes, enhancements to the fused A GEMM kernel to support additional (N,K) pairs and tile sizes, integration of CuTeDSL fused query kernels, PDL (programmatic dependency launch) support in NVFP4 quantization kernels, and improvements to the fused allreduce+rmsnorm fallback and MTP speculative decoding. These changes aim to improve decode throughput and latency on Blackwell GPUs by replacing generic cuBLAS calls with custom kernels tuned for weight-bandwidth-bound decode shapes.

**Technical impact**  
The PR adds 29 files with +2139/-138 changes, including new CUDA kernels (bf16_skinny_gemm), modifications to existing kernels (dsv3_fused_a_gemm, nvfp4_quant_kernels), Python bindings, test cases, and model integration code. The bf16_skinny_gemm kernel replaces cuBLAS splitK for M<=32 decode shapes, achieving up to 1.8x speedup. The fused A GEMM now supports additional shapes (6144x2624, 2048x2048, 1536x3072) with tile_m=32 to reduce wave quantization. The CuTeDSL fused query kernel fuses RoPE, quantization, and indexer operations into a single kernel. PDL support is added to several kernels to enable overlapping with preceding operations. The fused allreduce+rmsnorm fallback handles oversize tensors and mnnvl backend auto-selection. MTP speculator gains lifecycle hooks for skip_topk index sharing. These changes are specific to SM100+ and require CUDA >= 12.0.

**Potential risks**  
The new kernels are only compiled for SM90+ and CUDA >= 12.0, so older hardware is unaffected but may miss optimizations. The bf16_skinny_gemm kernel uses template instantiations for specific (N,K) pairs; unsupported shapes fall back to cuBLAS, which is safe but may be slower. The fused A GEMM changes modify the MmaComputer struct to support tile_m=32, which could affect correctness for existing DSv3 shapes if the new code path is inadvertently triggered. The PDL additions in nvfp4_quant_kernels and fused_norm_rope may cause issues on non-Blackwell hardware if the PDL intrinsics are not guarded properly (they are guarded by __CUDA_ARCH__ >= 900). The fused allreduce+rmsnorm fallback introduces a new unfused path that may have different numerical behavior. The MTP index sharing relies on correct lifecycle hook ordering; incorrect usage could lead to stale indices. The test coverage is limited to bf16_skinny_gemm and fused_norm_rope; other changes lack dedicated tests.

**Key insights**  
The PR demonstrates a systematic approach to optimizing decode performance on Blackwell by identifying bandwidth-bound shapes and replacing generic GEMM with custom kernels that minimize wave quantization and exploit PDL for overlapping operations. The use of template metaprogramming for kernel dispatch (e.g., SkinnyLoopUnroller) ensures compile-time resolution of M values. The physical-index shadow for sparse attention avoids redundant block-table lookups across layers with index_topk_freq > 1. The MTP speculator lifecycle hooks enable clean integration of skip_topk without modifying the core speculator logic. The PR also includes a serving recipe for GLM-5.2-NVFP4, demonstrating the intended deployment configuration.

### Summary

**What changed and why**  
The IR test files for RMSNorm and LayerNorm previously relied on class-level `torch.set_default_device` to set the device, but this state was reset by a function-scoped fixture before parameterized tests, causing inputs to be on CPU while operators were compiled for ROCm. The fix adds an explicit `device` parameter to input generators and passes `current_platform.device_type` in all test calls, ensuring inputs are created on the correct device.

**Technical impact**  
This change ensures that IR tests for RMSNorm and fused-add RMSNorm run on the intended accelerator (CUDA, ROCm, XPU) rather than silently falling back to CPU. The input generators now accept an optional `device` argument, making them more flexible and explicit.

**Potential risks**  
The change is low risk as it only adds an explicit device parameter and does not alter the logic of the tests or operators. However, any test that calls `generate_inputs` without the new `device` argument will continue to work with default device behavior (CPU), so backward compatibility is maintained. There is a minor risk of missing a call site that should pass the device, but all affected tests in the PR have been updated.

**Key insights**  
The root cause was a subtle interaction between class-level default device setting and pytest fixture scoping. The fix follows best practices by making device explicit rather than relying on global state. This pattern should be applied to other IR tests to prevent similar issues. The change also improves code clarity by removing `setup_class` methods that were only used for setting the default device.
