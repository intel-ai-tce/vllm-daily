### Summary

**What changed and why**  
Fixed two bugs where attention runtime tensors were not preserved across weight reloads. In standard MLA, derived W_UV and W_UK_T were reassigned instead of updated in-place, causing CUDA graphs to reference stale memory. In FlashInfer, sink parameters were converted to float32 but the new tensor was not refreshed when the source changed. The fix uses replace_parameter with prefer_copy for MLA and keeps a source reference for FlashInfer to update in-place.

**Technical impact**  
Ensures that CUDA graphs captured before weight reloads remain valid and reflect updated weights, preventing silent corruption or divergence. The fix is minimal and avoids full graph recapture overhead. It also adds regression tests to prevent future regressions.

**Potential risks**  
Low risk. The changes are localized to two attention backends and use existing utilities (replace_parameter). The FlashInfer change adds a new attribute _sinks_source, which is safe. The tests cover the main scenarios. AITER FP8/FP4 branches are intentionally unchanged, so no risk there.

**Key insights**  
The root cause is that post-load processing replaced tensors instead of updating them in-place, breaking tensor identity assumptions of CUDA graphs. The fix leverages existing infrastructure (replace_parameter) and a simple source-reference pattern to maintain stable storage addresses. The validation includes both unit tests and end-to-end evaluation showing logprob differences drop from ~1.77 to ~0.06, matching the baseline.

### Summary

**What changed and why**  
Added a device synchronization call before pooling when a partial (chunked) prefill is detected, to fix a correctness bug where torch.compile + chunked prefill produced wrong relevance scores due to a buffer-lifetime/async race. Also added a regression test that runs under torch.compile to verify chunked scores match unchunked scores.

**Technical impact**  
Fixes a silent correctness bug in LAST-pooling models (e.g., Qwen3-Reranker-0.6B) under torch.compile with chunked prefill, where scores could drop from ~0.83 to ~0.01-0.36. The fix adds a CUDA stream synchronization only when a partial prefill is present, avoiding overhead in normal decode and single-chunk cases. The new test ensures the compiled path is exercised and scores remain consistent.

**Potential risks**  
The synchronization is a targeted workaround; a deeper fix in the compiled forward or custom-op annotation might be preferable. The sync could introduce a small latency penalty for chunked prefill requests, but this is limited to the pooling step and only when partial prefills occur. No risk to non-chunked or eager-mode paths.

**Key insights**  
The bug was triggered only by the combination of torch.compile and chunked prefill, making it hard to detect. The fix exploits the 'observer effect' where any host-syncing read before pooling corrects the issue, indicating a buffer reuse race in the compiled graph. The gating on is_partial_prefill() ensures minimal performance impact.

### Base Information

- **PR Number:** #48481
- **Author:** [arpera](https://github.com/arpera)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-07-16 03:42:37

  - `vllm/v1/core/sched/scheduler.py`
  - `vllm/v1/core/single_type_kv_cache_manager.py`

### Summary

**What changed and why**  
This PR fixes a race condition in PD disaggregation with async scheduling for hybrid attention + SSM/GDN models. When a decode-side request receives KV blocks from a remote prefill worker, the newly allocated attention blocks are overwritten by the incoming NIXL transfer. Under async scheduling, the zeroing kernel for newly allocated attention blocks can be queued behind a previous forward pass while the NIXL RDMA transfer writes directly into GPU memory. If the RDMA transfer completes first, the delayed zeroing kernel can erase the received attention KV, causing severe accuracy degradation. The fix makes NIXL metadata report the local attention blocks that will be overwritten by remote KV loads, and the scheduler excludes those blocks from zeroing while preserving zeroing for other newly allocated attention blocks. Additionally, if a load fails, the skipped blocks are re-recorded for zeroing before local recompute.

**Technical impact**  
The change adds a mechanism to skip zeroing of attention blocks that will be overwritten by async KV loads, preventing a race condition that caused accuracy degradation. It introduces new methods in KVCacheManager to get block IDs in a token range and to re-record blocks for zeroing on failed loads. The scheduler tracks skipped block IDs and filters them out when draining new block IDs for zeroing. This keeps the change scoped to connector-loaded attention blocks and avoids adding a CUDA synchronization point to the async pipeline. The fix is verified with GSM8K evaluations on Qwen3.5 models with TP=1 and TP>1, showing restored accuracy.

**Potential risks**  
The change relies on correct identification of blocks that will be overwritten by the connector. If the metadata is incorrect or the range calculation is off, blocks that should be zeroed might be skipped, or blocks that should not be zeroed might be zeroed. The fix also adds complexity to the scheduler and cache manager, which could introduce new bugs. However, the tests cover the main scenarios, and the change is scoped to hybrid models with async scheduling and KV transfer.

**Key insights**
