### Summary

**What changed and why**

**Key insights**  
The PR includes a test that verifies the lazy initialization behavior by monkeypatching the registry's load method and asserting it is not called for text-only messages. The change is minimal (2 files, +43/-11) and focused on performance optimization without altering the public API.

## 6. [[Bugfix] Fix stale latent MoE residual pointer in CUDA graphs](https://github.com/vllm-project/vllm/pull/50386)


### Base Information

- **PR Number:** #50386
- **Author:** [wzhao18](https://github.com/wzhao18)

- **Merged time:** 2026-07-29 23:13:31
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50386/files) (1):**
  - `vllm/model_executor/layers/fused_moe/runner/latent_moe_runner.py`

### Summary

**What changed and why**  
The `_get_zero_residual` method was modified to accept a `max_token_num` parameter and allocate a static buffer sized to `max_token_num * hidden_states.shape[-1]` instead of dynamically resizing based on the current `hidden_states.numel()`. This prevents the buffer from being reassigned during eager execution, which caused CUDA graphs to hold stale pointers leading to illegal memory access errors.

**Technical impact**  
Fixes a critical bug where CUDA graphs could reference freed memory, causing crashes under memory pressure. The buffer is now allocated once with a fixed maximum size, ensuring pointer stability across graph replays. The change also adds assertions to validate buffer compatibility, improving safety.

**Potential risks**  
The buffer size is now fixed to `max_token_num * hidden_states.shape[-1]`, which may increase memory usage if `max_token_num` is larger than typical batch sizes. However, this is necessary for correctness. The assertions may cause early failures if the buffer is misused, but this is acceptable.

**Key insights**  
The root cause was that CUDA graphs capture pointers to tensors, and if those tensors are reallocated (e.g., due to dynamic resizing), the graph references stale memory. Allocating a static buffer sized to the maximum possible token count eliminates reallocation and ensures graph stability. This pattern is important for any CUDA graph usage with dynamically sized tensors.

  - `vllm/distributed/kv_transfer/kv_connector/v1/nixl/push_worker.py`

### Summary

**What changed and why**  
This PR fixes a cross-node clock epoch mismatch bug where `reqs_to_send` deadlines were stamped with the scheduler's `time.perf_counter()` but compared against each worker's own `perf_counter`. On multi-node deployments, the epoch difference could cause premature lease expiration, leading to silent data corruption. The fix adds a `scheduler_clock` field to metadata and rebases deadlines onto the worker's clock at registration.

**Technical impact**  
Adds a new field `scheduler_clock` to `NixlConnectorMetadata` (6 bytes overhead per metadata object) and modifies the deadline rebasing logic in both pull and push workers. The change ensures correct lease TTL across nodes, preventing premature block reuse and silent accuracy corruption. The test verifies that deadlines are correctly rebased within a tolerance of 5 seconds.

**Potential risks**  
The rebasing logic assumes `metadata.scheduler_clock` is non-zero; legacy metadata without this field (value 0.0) skips rebasing, preserving backward compatibility. Broadcast latency only lengthens the lease, which is safe. However, if the scheduler clock is significantly off (e.g., due to NTP adjustments), the rebased deadline could be slightly longer than intended, but this is acceptable as it only delays block reuse.

**Key insights**  
The root cause is that `time.perf_counter()` is process-local and not comparable across processes on different nodes. The fix leverages the fact that broadcast latency is always positive, so rebasing with the worker's clock only extends the lease, never shortens it. The same pattern is applied to both pull and push workers for consistency.

### Summary

**What changed and why**  
Fixed a race condition where a prefill request could be preempted during its final step, causing its KV blocks to be freed before an async KV-consuming connector reads them. The fix adds a `requires_kv_delivery` property to connectors, defaulting to True for producers, and when set, the scheduler drops the in-flight output token on preemption so the request is recomputed with valid KV. **Technical impact**  
Introduces a new `requires_kv_delivery` property on KV connectors and the scheduler, modifies preemption logic to conditionally drop stale output tokens, and adds tests for the new behavior. The change is backward-compatible as the default behavior (no connector or consumer role) remains lossless.

**Potential risks**  
The fix may cause unnecessary recomputation for producer connectors if the race condition is rare, but this is acceptable to avoid handing off invalid KV. The property must be correctly overridden in custom connectors; otherwise, they may experience dropped tokens or stale KV delivery.

**Key insights**  
The race condition arises because preemption frees KV blocks while the final output token is still in flight. By dropping that token and requeuing the request, the system ensures the connector receives valid KV. The design leverages a connector property to distinguish between producers that require reliable delivery and best-effort caches that do not.
