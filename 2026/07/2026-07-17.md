## 1. [[Perf][Hybrid] Vectorize _copy_mamba_state_block to uint64 for temporal](https://github.com/vllm-project/vllm/pull/48110)


### Base Information

- **PR Number:** #48110
- **Author:** [fuscof-ibm](https://github.com/fuscof-ibm)
- **Merged By:** [tdoublep](https://github.com/tdoublep)
- **Merged time:** 2026-07-17 21:43:10
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/48110/files) (1):**
  - `vllm/v1/worker/mamba_utils.py`

### Summary

**What changed and why**  
Vectorized the temporal-state copy in _copy_mamba_state_block from 1-byte to uint64 loads/stores (8× wider transactions) to improve HBM bandwidth utilization. The original byte-wise copy achieved only ~33-62% of peak HBM bandwidth; the new approach reaches ~74-84% of peak, reducing kernel latency by up to 6.5× for low request counts and improving end-to-end throughput by up to 3% on GB200 with MTP speculative decoding.

**Technical impact**  
Replaced the byte-by-byte copy loop for temporal states with uint64 vectorized loads/stores, processing 8 bytes per thread per instruction. Added a masked byte tail loop for any remaining 0-7 bytes. Also added alignment assertions in MambaSpecDecodeGPUContext to ensure the state base pointer and block stride are 8-byte aligned, guaranteeing safe uint64 access. The conv state copy path remains unchanged.

**Potential risks**  
Low risk: the alignment assertions provide a compile-time guard against misaligned addresses; if they fail, the error is caught early during initialization. The tail loop handles non-8-byte-multiple sizes correctly. The change only affects temporal states, which are always 8-byte aligned for supported dtypes (bf16, fp16, fp32). Performance regression is unlikely given the microbenchmark and e2e results.

**Key insights**  
The PR demonstrates that a simple data type widening from uint8 to uint64 in a Triton kernel can dramatically improve memory bandwidth utilization (from ~33% to ~74% on GB200, from ~62% to ~84% on H100). The improvement is most pronounced at low request counts (up to 6.5× speedup) and translates to measurable end-to-end throughput gains (up to +3%) in production-like serving scenarios with MTP speculative decoding, without affecting speculative acceptance rates.

The triton kernel changes may have subtle performance implications due to additional .to(tl.float32) calls.

**Key insights**  
The original unconditional fp32 copy was a hidden memory bottleneck that only manifested under speculative decoding with large vocab.   - `vllm/entrypoints/generate/beam_search/offline.py`

### Summary

**What changed and why**  
Replaced `sum(..., [])` with `itertools.chain.from_iterable` to flatten beams in `_beam_search_step`. The original `sum` concatenates lists in O(n²) time due to repeated copying, while `chain.from_iterable` is O(n). This improves performance for each decode step.

**Technical impact**  
Reduces time complexity of flattening beams from O(n²) to O(n) per decode step, where n is the total number of beams. This can significantly speed up beam search, especially with many beams or long sequences.

**Potential risks**  
Low risk. The change is a direct replacement that produces the same flattened list. However, `itertools.chain` returns an iterator, which is then converted to a list via `list()`, so the final type remains `list[BeamSearchSequence]`. No behavioral change.

**Key insights**  
Using `sum` for list concatenation is a common anti-pattern due to quadratic complexity. `itertools.chain` is the idiomatic and efficient alternative. This change aligns with Python best practices and improves performance without altering logic.
