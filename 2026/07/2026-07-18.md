### Summary

**What changed and why**  
This PR adds MRV2 virtual-batch prefill context parallelism (PCP) for MLA and sparse MLA models. It introduces a PCPManager that partitions the globally scheduled InputBatch into rank-local DualChunkSwap rows, preserving global request state for restore, logits, and postprocessing. It also aligns context-parallel group construction with an orthogonal PCP/DCP design, updates scheduler/offload tests for DCP-owned KV sharding, and adds concurrent GSM8K eval configurations for TP2+PCP2+EP and TP1+PCP4+EP.

**Technical impact**  
This change significantly extends vLLM's parallelism capabilities by adding a new PCP axis orthogonal to TP and DCP. It reduces prefill TTFT for long sequences (e.g., 100k tokens) by up to 52% (2.859s vs 6.015s) while maintaining model accuracy. The DualChunkSwap partitioning balances causal-attention work across PCP ranks. The orthogonal PCP/DCP design simplifies reasoning about KV shard count and replication factor.

**Potential risks**  
PCP is currently limited to MLA models and does not support PP, encoder-decoder, MM inputs, LoRA, speculative decoding, or full CUDA graphs. Sparse MLA PCP requires eager mode. The change modifies core parallelism state initialization and block size scaling, which could affect existing DCP-only deployments. The new code paths are exercised by the added tests and eval configs, but edge cases in mixed prefill/decode batches may need further validation.

**Key insights**  
The DualChunkSwap partition pairs early and late chunks to balance attention work across PCP ranks. PCP and DCP are treated as independent axes, with DCP groups spanning PCP first then TP, enabling two combined configurations (DCP=PCP or DCP=TP×PCP). The PCPManager rewrites only the per-step InputBatch, keeping the global batch view private for restore before sampling/postprocessing.

### Summary

**What changed and why**  
Fixed a bug where max_pixels/min_pixels were silently ignored for video prompts in Qwen3-VL and Qwen-Omni models. The issue was that HF video processors only read pixel budgets from size.{longest,shortest}_edge, and the engine's kwarg filtering stripped max_pixels before it reached the processor. The fix translates max_pixels/min_pixels into size.longest_edge/shortest_edge in the video branch of _call_hf_processor, ensuring the budget is honored.

**Technical impact**  
Video prompts now correctly respect max_pixels/min_pixels, reducing prompt token counts from uncapped values (e.g., 12044 to 324 for Qwen3-VL-4B). This fixes a profiling-vs-actual inconsistency and prevents inflated memory usage. No regression for uncapped usage.

**Potential risks**  
Low risk: the change is guarded by checking if the merged kwargs contain size/min_pixels/max_pixels, and only modifies video processing. Existing tests pass. Edge cases with custom size overrides are handled via dict merging.

**Key insights**  
The root cause was a mismatch between HF processor expectations and vLLM's kwarg filtering. The fix leverages ctx.get_merged_mm_kwargs to access the original budget and translates it into a format the processor accepts. This pattern could be reused for other models with similar issues.

## 6. [[ROCm][DSv3.2][Perf] Cap sparse MLA decode KV-splits with a work-per-split heuristic](https://github.com/vllm-project/vllm/pull/46832)


### Base Information

- **PR Number:** #46832
- **Author:** [frida-andersson](https://github.com/frida-andersson)
- **Merged By:** [tjtanaa](https://github.com/tjtanaa)
- **Merged time:** 2026-07-18 09:39:37
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/46832/files) (1):**
  - `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`

### Summary

**What changed and why**  
Added a heuristic to cap the number of KV-splits in the ROCm aiter sparse-MLA decode backend. Previously, aiter defaulted to splitting across all CUs (304 on gfx942), causing excessive overhead for small workloads. The heuristic computes a power-of-two split count based on effective sequence length and a minimum work-per-split threshold, capped by the number of compute units.

**Technical impact**  
Reduces the average decode reduce kernel time by ~75% (from 22.1 µs to 5.4 µs) and total kernel time by ~75% (from 4.16 s to 1.01 s). End-to-end serving throughput improves by ~4.3% for short-context scenarios, with larger gains expected for long-context decode. Numerics remain unchanged as partials recombine via LSE.

**Potential risks**  
Low risk. The change only affects the sparse-MLA decode path and is TP-invariant. The heuristic is conservative (capped by CU count) and mirrors the existing triton implementation. At high concurrency, the device cap converges to the old all-CU behavior, so no regression is expected. GSM8K accuracy is unchanged within noise.

**Key insights**  
The default aiter behavior of splitting across all CUs is suboptimal for sparse-MLA decode because the reduce kernel only processes a small number of tokens per row (≤ topk). The heuristic aligns with the triton backend's approach, ensuring sufficient work per split to amortize launch and combine overhead. The change is minimal (21 lines added) and well-documented.

## 10. [[Bugfix] Re-sync parameter tp_rank after process_weights_after_loading (fix replicated / disable_tp weight reload)](https://github.com/vllm-project/vllm/pull/48025)

  - `vllm/model_executor/model_loader/reload/layerwise.py`

### Summary

**What changed and why**  
Fixed a bug where weight reload could crash for replicated (disable_tp=True) parameters like DeepSeek-V2/V3 MLA fused a-projection. The root cause was that BasevLLMParameter.__init__ stamps tp_rank with the global rank, but update_param_tp_status() only runs at construction. When parameters are re-created after construction (e.g., FP8 process_weights_after_loading), they carry the global rank again, causing narrow overflow on ranks > 0. The fix makes update_param_tp_status() the single source of truth and re-runs it after process_weights_after_loading in both the default loader and layerwise reload path. Also removed redundant tp_rank kwargs from weight_loader_v2 call sites.

**Technical impact**  
Ensures correct weight reload for replicated parameters in tensor-parallel deployments, particularly for models like DeepSeek-V3 with MLA and FP8 quantization. The change is backward compatible: regular TP layers see identical offsets, and replicated layers load full weights at offset 0 on every rank. This also fixes load_column_parallel_weight which was previously unaddressed.

**Potential risks**  
Low risk. The change is minimal and targeted: it adds a call to update_param_tp_status() after process_weights_after_loading in two places and removes redundant tp_rank arguments. Existing tests should cover TP loading; the fix only affects the reload path for replicated weights. No performance impact expected.

**Key insights**  
The bug highlights the importance of keeping parameter TP state consistent across parameter re-creation. The solution unifies TP state management under update_param_tp_status(), making it the single source of truth. The fix was suggested by a contributor (Isotr0py) and supersedes an earlier approach that modified parameter loaders.
