## 2. [[Perf] DeepSeek-OCR-2 TTFT Optimize](https://github.com/vllm-project/vllm/pull/49531)


### Base Information

- **PR Number:** #49531
- **Author:** [LiuLi1998](https://github.com/LiuLi1998)
- **Merged By:** [Isotr0py](https://github.com/Isotr0py)
- **Merged time:** 2026-07-25 22:53:06
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/49531/files) (1):**
  - `vllm/model_executor/models/deepencoder2.py`

### Summary

**What changed and why**  
Optimized `create_custom_4d_mask` in DeepSeek-OCR-2 model by computing the mask in one shot and caching it. The mask is batch-invariant (token_type_ids pattern is same for every sample), so a single [1,1,S,S] mask is computed and broadcast over the batch. Cached via lru_cache keyed by (sequence_length, dtype, device). This eliminates per-sample loops and repeated index_put_ operations that were CPU-bound.

**Technical impact**  
Reduces TTFT p50 by ~46% (from 4193ms to 2283ms) and improves throughput by 1.83× (from 2.36 to 4.31 req/s). Eliminates 229,296 aten::_index_put_impl_ calls (52.2% CPU time) and reduces aten::copy_ calls from 532,122 to 71,592. The cache stores ≤2 tiny entries (<1 MB total) per (S, dtype, device).

**Potential risks**  
Cache key uses device string; if device changes (e.g., between CPU and GPU) the cache may hold stale entries, but this is unlikely in production. The mask assumes token_type_ids pattern is always [0]*n_query + [1]*n_query; if the model's token_type_ids pattern changes, the mask would be incorrect. The cache is unbounded in theory (maxsize=8) but keys are limited by sequence lengths and dtypes used.

**Key insights**  
The optimization leverages the observation that token_type_ids are identical across batch samples, enabling a batch-invariant mask computation. Using lru_cache with classmethod avoids recomputation for repeated sequence lengths. The refactor also simplifies the code by removing the need to store _current_token_type_ids and the per-sample loop.

### Summary

**What changed and why**  
This PR deduplicates replicated MLA KV cache blocks in the shared CPU offload region for pure MLA models with tensor parallelism (TP > 1). Previously, each TP rank stored its own replica of the latent KV payload, wasting CPU capacity and D2H bandwidth. Now, only TP rank 0 performs the D2H store, and all ranks load from the same shared host slot. The change is gated on a conservative `replicated_layout` decision derived from KVCacheSpec and parallel configuration, and is enabled only for single-node mp executor with TP-only parallelism and pure MLA attention.

**Technical impact**  
Reduces CPU memory consumption by approximately N times for replicated MLA blocks (where N is TP size) and reduces D2H store traffic by a factor of N. Scheduler dispatch and completion accounting remain unchanged. The change adds a `replicated_layout` field to `OffloadingConfig` and modifies `CPUOffloadingSpec` and `TieringOffloadingSpec` to compute single-copy block sizes. Worker logic is updated so non-writer ranks acknowledge store jobs without submitting them. New unit tests and a DeepSeek-V2-Lite TP=2 evaluation are added.

**Potential risks**  
The replicated layout is only enabled under strict conditions (pure MLA, TP > 1, no other parallelism, single-node mp). If those conditions are not met, the old per-rank layout is used, so there is no regression for unsupported configurations. However, the gating logic must be kept in sync with future changes to parallel configurations or attention specs. The change does not affect persistent cache naming or cleanup, which remain follow-up work.

**Key insights**  
The deduplication is safe because MLA latent KV is identical across TP ranks (no head sharding). The implementation uses a conservative gate to avoid incorrect behavior for mixed or wrapped cache layouts. The PR also refactors tests to use native `OffloadingConfig` objects instead of mocking `VllmConfig`, improving test clarity and maintainability.

**Key insights**  
The PR addresses a performance regression introduced by #42656, which added LRU ordering for prefix caching but inadvertently added overhead for the common case of caching being disabled.
