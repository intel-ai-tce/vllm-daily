  - `tests/multimodal/test_processing.py`
  - `vllm/multimodal/processing/processor.py`

### Summary

**What changed and why**  
Optimized multimodal placeholder discovery and token-match scanning in vllm/multimodal/processing/processor.py to reduce per-request overhead. Changes include fast-forwarding via list.index in iter_token_matches, lazy content resolution and first-token guard in _iter_placeholders, and caching first matches per target object in _find_matches. Added regression tests for negative start_idx, adversarial linearity, and lazy resolution.

**Technical impact**  
Significant performance improvements: placeholder scanning and token matching are now near-linear in typical cases, with benchmarks showing 10-20x speedups on real workloads. The changes are output-identical, verified by differential fuzzing and E2E tests. Negative start_idx now raises ValueError instead of silently misbehaving.

**Potential risks**  
The target-object identity cache in _find_matches assumes that matching depends only on target, prompt, tokenizer, and start_idx; if future updates change this, the cache could become stale. The fast-forward logic in iter_token_matches relies on list.index behavior and may have edge cases with overlapping matches, though tests cover common scenarios. The lazy resolution in _iter_placeholders changes when content is resolved, which could affect error handling if tokenizer is None.

**Key insights**  
The optimizations exploit C-level list.index for fast-forwarding and avoid redundant work by caching per-target results and resolving content only when needed. The differential fuzzing and mutation testing provide strong correctness guarantees. The performance gains are substantial, especially for large prompts and many images, directly improving MM request throughput.

  - `vllm/multimodal/media/video.py`
  - `vllm/multimodal/video.py`

### Summary

**What changed and why**  
This PR fixes a security issue where DeepStream was not recognized as a GPU-requiring codec, allowing request-level activation of NVDEC decoding without proper startup configuration or VRAM reservation. It also enforces pixel limits in the DeepStream decode path and strips request-controlled pool_size from runtime kwargs to protect the process-wide DecodePool singleton.

**Technical impact**  
The change adds a register_gpu_codec method to VideoLoaderRegistry and registers 'deepstream' as a GPU codec, so merge_kwargs will strip it from runtime overrides unless statically configured. It also adds a pixel limit check after probe_metadata in the DeepStream branch, matching other codec paths, and removes pool_size from runtime kwargs to prevent request-level control of the DecodePool. Tests are added to verify these behaviors.

**Potential risks**  
The change may break existing workflows that relied on passing pool_size at runtime for DeepStream, but this is intentional to enforce startup-only configuration. The pixel limit check could reject previously accepted large images, but this aligns with other codecs and is a security improvement. The register_gpu_codec method is new and could be misused if not documented, but it's straightforward.

**Key insights**  
The PR addresses a security gap by making the system fail-closed for unknown backends and ensuring GPU codecs are only used when statically configured. The addition of pixel limit enforcement in the DeepStream path closes a bypass of VLLM_MAX_IMAGE_PIXELS. The tests cover the new behaviors, ensuring the fixes are validated.

## 4. [Shard the K3 Latent-MoE up-projection on large batches](https://github.com/vllm-project/vllm/pull/50383)


### Base Information

- **PR Number:** #50383
- **Author:** [jeejeelee](https://github.com/jeejeelee)
- **Merged By:** [WoosukKwon](https://github.com/WoosukKwon)
- **Merged time:** 2026-08-03 00:49:40
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50383/files) (2):**
  - `vllm/model_executor/layers/fused_moe/runner/latent_moe_runner.py`
  - `vllm/models/kimi_k3/nvidia/model.py`

### Summary

**What changed and why**  
This PR refactors the latent MoE tail processing in the vLLM fused MoE runner to shard the up-projection on large batches (prefill) for better performance. It introduces a tiered dispatch (LatentTailTier) that selects among three tail implementations based on token count: a fused CuTeDSL path for small batches, an overlap-allreduce path for medium batches, and a new column-parallel sharded up-projection path for large batches. The change also moves the tail-fusion enablement logic from the model definition into the runner, and adds an aux-stream overlap for the shared expert all-reduce in the medium tier.

**Technical impact**  
The change adds a new code path (tier 2) that reduces up-projection FLOPs by 1/tp on large batches by sharding the up-projection weight and accumulating into the shared partial, which also stitches the routed shards during the final all-reduce. It also introduces a new helper method `_select_tail_tier` and three tail methods, and modifies the runner's constructor to compute tail-fusion capability based on the current platform. The model file is simplified by removing the runner_args parameter and the platform check, which is now handled inside the runner. Performance tests show TTFT improvements of ~4% at various concurrency levels, with negligible TPOT changes.

**Potential risks**  
The new tier 2 path changes the order of operations: it accumulates the up-projection into the shared partial before the final all-reduce, which may affect numerical precision compared to the previous approach. The tier selection relies on environment variables (VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD and VLLM_DISABLE_SHARED_EXPERTS_STREAM) and the platform capability check, which could lead to unexpected behavior if these are misconfigured. The code assumes the up-projection weight is replicated and shardable, which may not hold for all latent MoE configurations. The use of `maybe_execute_in_parallel` with CUDA events and aux stream introduces potential synchronization issues if not handled correctly.

**Key insights**  
The PR demonstrates a performance optimization strategy that adapts the computation based on batch size, using a tiered approach to balance between kernel fusion, overlap, and sharding. The new tier 2 path is a clever way to reduce compute on large batches by folding the up-projection into the existing all-reduce, avoiding an extra GEMM. The refactoring centralizes the tail-fusion enablement logic in the runner, making it more maintainable. The performance results show that the optimization is effective for TTFT, which is critical for prefill latency.
