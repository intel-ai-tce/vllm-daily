## 1. [Fix MNNVL Lamport mailbox publication and cleanup](https://github.com/vllm-project/vllm/pull/53000)


### Base Information

- **PR Number:** #53000
- **Author:** [alexeldeib](https://github.com/alexeldeib)

- **Merged time:** 2026-08-23 23:56:54

- **[Changed Files](https://github.com/vllm-project/vllm/pull/53000/files) (3):**

  - `csrc/custom_all_gather_reduce_scatter.cuh`
  - `tests/distributed/test_custom_all_gather_reduce_scatter.py`

### Summary

**What changed and why**  
This PR fixes two bugs in the MNNVL Lamport all-gather and reduce-scatter kernels: (1) mailbox publication now uses the required `multimem.st.relaxed.sys` PTX instruction instead of ordinary stores, which are undefined for CUDA multicast mappings; (2) the triple-buffer cleanup stage is changed from `(epoch+1)%3` to `(epoch+2)%3` to avoid erasing a next-epoch publication from a faster peer while a slower rank is still finishing the current epoch. It also adds a new distributed test that reproduces the one-epoch skew and validates the fix.

**Technical impact**  
The change modifies the core communication kernels used in sequence-parallel all-gather/reduce-scatter for MNNVL, affecting performance and correctness. The new multicast store instruction is more efficient than the previous release/acquire plus proxy fence approach, removing three memory barriers. The cleanup logic change prevents silent data corruption in multi-epoch scenarios. The added test increases CI coverage for this path, requiring a two-GPU B200/GB300 environment with CUDA multicast support.

**Potential risks**  
The `multimem.st.relaxed.sys` instruction is only available on SM90+ and CUDA 12.1+; the code traps on unsupported targets, which could cause failures if the kernel is dispatched incorrectly. The relaxed memory ordering relies on volatile readers and the sentinel pattern; any change to the payload format or reader logic could reintroduce stale reads. The cleanup change assumes the previous stage is always safe to clean, which holds for the triple-buffer scheme but must be verified if the number of stages changes. The new test depends on specific hardware and may be flaky if multicast mapping is not available.

**Key insights**  
The PR correctly identifies that CUDA multicast addresses require special PTX instructions and that the previous memory ordering was over-specified. The stage cleanup fix is a classic off-by-one bug in a ring buffer, where cleaning the next stage instead of the previous one can destroy in-flight data. The test design cleverly uses the production kernels and a controlled skew to deterministically reproduce the race, making it a strong regression test. The use of `multimem.st.relaxed.sys` with volatile readers is a valid pattern for publish-subscribe over multicast, relying on the sentinel to reject partial writes.

## 2. [[Bugfix] Reuse CUDA streams in packed weight transfer to cap reserved-memory waste](https://github.com/vllm-project/vllm/pull/52951)


### Base Information

- **PR Number:** #52951
- **Author:** [qgallouedec](https://github.com/qgallouedec)
- **Merged By:** [ywang96](https://github.com/ywang96)
- **Merged time:** 2026-08-23 23:54:42
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/52951/files) (1):**
  - `vllm/distributed/weight_transfer/packed_tensor.py`

### Summary

**What changed and why**  
The fix caches CUDA streams used in packed weight transfer to avoid creating new streams on every call. Previously, each call created fresh streams, causing the caching allocator to strand 2 GiB of reserved memory per call because cached blocks are keyed by stream. This led to memory saturation and OOM in long-running training. By reusing streams, the stranded memory is capped at 2 GiB, resolving the OOM issue.

**Technical impact**  
The change introduces a module-level cached function `_get_streams` that returns a tuple of streams for a given device and buffer count. Both producer and consumer functions now use this cached stream set instead of creating new ones. This reduces memory waste and improves stability in training workloads that synchronize weights frequently. The change is minimal and does not alter the synchronization logic, as each buffer slot is still synchronized before reuse.

**Potential risks**  
Potential risks include thread-safety if multiple threads call the cached function concurrently, though `functools.cache` is thread-safe for the cache itself. Also, if the device index changes (e.g., multi-GPU with different current devices), the cache key includes the device index, so streams are per-device. There is a slight risk of stream reuse causing unintended serialization if the same stream is used for overlapping operations, but the existing synchronization per buffer slot mitigates this. The change is low-risk and validated with a repro and real training run.

**Key insights**  
The root cause was the interaction between the caching allocator's stream-keyed block caching and the creation of new streams per call. This is a subtle memory management issue that can cause gradual memory growth in long-running processes. The fix leverages Python's `functools.cache` to reuse streams, which is a simple and effective solution. The validation shows a clear improvement from +2.09 GB per step to flat memory usage, confirming the fix's effectiveness.
