## 1. [[XPU][INC] Add int4 w4a8 (dynamic int8 activation) backend for INC linear layers](https://github.com/vllm-project/vllm/pull/50501)


### Base Information

- **PR Number:** #50501

  - `vllm/envs.py`
  - `vllm/model_executor/layers/quantization/inc/schemes/inc_w4a8_linear.py`
  - `vllm/model_executor/layers/quantization/inc/schemes/inc_wna16_scheme.py`

### Summary

**What changed and why**  
Adds a new opt-in backend for INC int4 linear layers on XPU that uses dynamic per-token int8 activations (w4a8) via the oneDNN int4_gemm_w4a8 kernel. This is motivated by performance gains on compute-bound shapes (e.g., diffusion) where int8 activations avoid dequantizing weights to activation dtype. The change also introduces a VLLM_XPU_INC_WNA16_BACKEND environment variable to select between auto, ark, w4a16, and w4a8 backends, with auto preserving current behavior. Additionally, it adds validation for partition alignment (multiples of 8) to prevent silent truncation of weights.

**Technical impact**  
Adds a new linear method class (INCXPUW4A8LinearMethod) that reuses the existing w4a16 weight layout, creates an fp16 copy of scales for the w4a8 kernel, and falls back to w4a16 for small token counts (<512). The scheme selection logic now reads the new env var and raises errors for unsupported configurations (e.g., int2 with oneDNN backends, unaligned group sizes, missing kernel). The change is purely additive: no existing behavior changes when the env var is unset (auto). A new test file with 32 tests covers backend selection, weight processing, apply_weights, and partition alignment.

**Potential risks**  
The w4a8 kernel requires both GEMM dims to be multiples of 8; the new validation in create_weights raises an error for unaligned partitions, which could break existing models that previously ran with w4a16 (though w4a16 is unaffected). The fallback threshold of 512 tokens is a heuristic that may not be optimal on all devices. The new env var is not documented in docs/configuration/env_vars.md (though it is auto-included from envs.py). The tests rely on mocking and may not fully cover real hardware variations.

**Key insights**  
The PR demonstrates a clear performance win on B70 (1.39x over ARK for FLUX, 1.52x for text generation) while maintaining numerical fidelity (cosine 0.99996). The design carefully preserves backward compatibility by making the new backend opt-in and keeping the default auto behavior unchanged. The validation for partition alignment addresses a subtle bug where unaligned dims would be silently truncated, which is a good defensive practice. The test suite is comprehensive, including mutation testing to ensure the backend selection is not vacuously green.

## 2. [[Kimi K3] Allocate internal checkpoints only from aligned starts](https://github.com/vllm-project/vllm/pull/53212)


### Base Information

- **PR Number:** #53212
- **Author:** [ZeldaHuang](https://github.com/ZeldaHuang)
- **Merged By:** [ZJY0516](https://github.com/ZJY0516)
- **Merged time:** 2026-08-20 23:33:45
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53212/files) (2):**
  - `tests/v1/core/prefix_cache/test_partial_prefix_cache_hits.py`
  - `vllm/v1/core/single_type_kv_cache_manager.py`

### Summary

**What changed and why**  
This PR modifies the KV cache manager to allocate internal Mamba checkpoint blocks only when the current model-input start is aligned to the Mamba block size. It passes total_computed_tokens through the allocation path so that _needs_internal_checkpoint can enforce the same start-alignment invariant as scheduling. It also stores the checkpoint decision in a per-request dictionary to avoid recomputation and ensures unaligned checkpoint positions remain null blocks, preventing prefix-cache hashing of unwritten states.

**Technical impact**  
The change ensures that checkpoint blocks are only allocated when the worker will actually write them, preventing mismatches between scheduler allocation and worker export. It adds a new dictionary _num_checkpoint_blocks to track the checkpoint decision per request, which is cleaned up on free. The logic in get_num_blocks_to_allocate and allocate_new_blocks now uses the stored value instead of recomputing, and the alignment check uses total_computed_tokens.

**Potential risks**  
The new alignment condition may cause checkpoint blocks to be skipped in cases where they were previously allocated, potentially affecting performance or correctness if the worker expects a checkpoint at an unaligned start. The dictionary must be kept in sync with request lifecycle; if a request is freed without pop_blocks_for_free, it could leak. Also, the change relies on total_computed_tokens being accurate at allocation time, which could be a source of bugs if not updated correctly.

**Key insights**  
The PR addresses a subtle lifecycle issue where the scheduler could allocate a checkpoint block that the worker would not write, leading to an unwritten state receiving a prefix-cache hash. By enforcing alignment at allocation time and storing the decision, the code ensures consistency between allocation and export. The added test verifies the null-block invariant for unaligned starts.

The change also adds a new model class DFlash2DraftModel, a new speculator (DFlash2Speculator) with a Triton path-walk kernel, and forces the V2 model runner for DFlash2 checkpoints to ensure the candidate selector is used. **Technical impact**

The change includes new tests and updates to existing tests to cover the new functionality.

**Potential risks**

The path-walk kernel and the caching of draft logits introduce complexity that could be prone to subtle bugs, especially around sampling consistency and edge cases (e.g., temperature handling, padding). The forced V2 model runner for DFlash2 could break existing deployments if they rely on V1 for some reason, but the PR ensures DFlash1 checkpoints remain unaffected. The use of FlashInfer's top-k kernel is optional and falls back to torch.topk, but the fallback path may have performance implications. The changes to the gumbel kernel refactor could introduce regressions if the extracted function does not exactly match the original behavior.

**Key insights**  
The PR demonstrates a clear performance improvement in acceptance length and throughput over the existing DSpark drafter, with the overhead of the new components being minimal (less than 1% of step time). The design of the candidate selector using a path walk over top-K candidates is a novel approach that improves draft quality. The use of a separate architecture class (DFlash2DraftModel) ensures backward compatibility with existing DFlash checkpoints. The PR also includes careful handling of sampling consistency between the draft and verification phases, and the use of Triton kernels for performance-critical parts.

**Key insights**  
The performance bottleneck was identified as repeated tracing in fuse, which is now avoided by caching eps source during match.
