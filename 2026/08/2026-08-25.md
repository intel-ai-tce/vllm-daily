  - `tests/parser/engine/test_parser_engine.py`
  - `vllm/parser/parser_manager.py`

### Summary

**What changed and why**  
This PR fixes a bug where structured-output reasoning configuration was silently disabled when the reasoning and tool parsers shared the same parser engine. Previously, ParserManager.get_parser() returned the raw shared ParserEngine, whose reasoning_parser attribute is None, causing the serving paths to treat reasoning as disabled and skip forwarding request-specific parser kwargs like enable_thinking=False. The fix removes the optimization that collapsed shared engine adapters back into the engine, instead always composing a DelegatingParser subclass that preserves both reasoning and tool parser adapters.

**Technical impact**  
The change ensures that reasoning adapters are always preserved, so request-specific reasoning settings (e.g., enable_thinking=False) are correctly forwarded to the parser. This prevents the structured-output backend from using the parser's default thinking mode and waiting for a reasoning boundary that the model was instructed not to emit, which could lead to unconstrained schema generation or running until max_tokens. The code change simplifies ParserManager by removing the _get_parser_engine_cls helper and the shared-engine shortcut, making the composition logic more straightforward and consistent.

**Potential risks**  
Removing the shared-engine optimization may introduce a slight performance overhead because a DelegatingParser is now always used instead of a direct engine instance. However, this is likely negligible compared to the correctness fix. The change also removes a test that verified the old behavior, so there is a small risk that other code paths relying on the collapsed engine behavior might be affected, but the updated tests cover the new expected behavior.

**Key insights**  
The bug stemmed from an optimization that assumed a shared engine could be used directly, but that assumption broke the reasoning adapter wiring. The fix prioritizes correctness over micro-optimization by always composing adapters. The test plan demonstrates that the fix resolves the issue across various structured-output modes (required, named, auto) and streaming/non-streaming cases, including scenarios with enable_thinking=False and include_reasoning:false.

This PR moves cli_args.py and dp_supervisor.py from the vllm.entrypoints.openai package to vllm.entrypoints.launchers, reflecting that these modules are no longer OpenAI-specific but serve the general online serving launcher. All imports and references across the codebase and tests are updated accordingly, and the docstring in cli_args.py is adjusted to describe the online server instead of the OpenAI-compatible server.

**Technical impact**  
The change is a refactor that reorganizes module locations without altering functionality. It updates import paths in multiple files, including CLI entry points, launcher internals, and tests. The relative imports in the moved files are adjusted to use relative paths, and the documentation generator's mock target is updated. This improves code organization and aligns with the project's direction of decoupling from OpenAI-specific naming.

**Potential risks**  
The main risk is missing any import references that were not updated, which could cause ImportError at runtime or in tests. However, the PR appears to have updated all known references. There is also a minor risk of circular imports due to the new relative imports, but the changes seem to avoid that. The test file renames and import updates should be verified to ensure no broken test paths.

**Key insights**  
The PR is a straightforward module relocation with no behavior changes. It is part of a series of PRs to move vLLM online serving away from the 'OpenAI-compatible' label. The use of relative imports in the moved files is a good practice to avoid absolute path issues. The update to the documentation generator ensures that the generated docs still point to the correct module.
