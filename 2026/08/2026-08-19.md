**Key insights**  
The bug was caused by over-clearing metadata: zeroing both device and CPU query offsets, when only the device offsets needed to be zeroed for the kernel safety. **Key insights**  
The root cause is that container sample counts include hidden decode lead-in packets, while the presentation timeline (edit list) defines visible frames. The fix leverages edit-list-aware duration or seek position to determine the true frame count. The OpenCV fix uses a mixin to resample over the true length, while PyAV trusts duration over header count. The test creates a hermetic reproducer using stream-copy remuxing with rebased timestamps.

### Summary

**What changed and why**  
This PR optimizes the GDNAttentionMetadataBuilder.build() method by avoiding redundant tensor computations. Previously, the condition for spec decode detection computed num_decode_draft_tokens_cpu >= 0 twice and ~spec_sequence_masks_cpu four times. The change computes spec_sequence_masks_cpu once, reuses it for the sum check, and precomputes non_spec_sequence_masks_cpu for all subsequent uses. The logic is preserved exactly, with the same behavior for edge cases.

**Technical impact**  
The change reduces the number of tensor operations (e.g., aten::ge) from two to one, and eliminates repeated bitwise NOT operations. This can reduce CPU/GPU overhead in the metadata build path, which is called frequently during speculative decoding. Benchmark results show slight improvements in throughput and latency, though the gains are modest. The change also improves code clarity by naming the negated mask.

**Potential risks**  
The refactor is straightforward and behavior-preserving, but there is a subtle change in the condition evaluation order: previously, the sum of num_decode_draft_tokens_cpu >= 0 was computed before the sum of the masked values; now the masked sum is only computed if num_spec_decodes != 0. This is logically equivalent because if num_spec_decodes == 0, the masked sum is also 0. However, if num_decode_draft_tokens_cpu is None, the code now skips the entire spec decode branch, which is correct. The risk of introducing bugs is low, but the change touches a critical path in speculative decoding, so thorough testing is recommended.

**Key insights**  
The PR demonstrates a good practice of avoiding redundant tensor computations in performance-sensitive code. The profiling confirms the reduction in kernel launches. The benchmark results show minor but consistent improvements, and accuracy is preserved. The change is well-scoped and includes detailed profiling and benchmark evidence, making it a solid optimization.
