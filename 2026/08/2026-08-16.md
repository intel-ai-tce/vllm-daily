## 2. [[Bugfix][Mamba] Fix overlapping state copy race](https://github.com/vllm-project/vllm/pull/50729)


### Base Information

- **PR Number:** #50729
- **Author:** [AndreasKaratzas](https://github.com/AndreasKaratzas)
- **Merged By:** [tdoublep](https://github.com/tdoublep)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50729/files) (2):**
  - `tests/v1/worker/test_mamba_utils.py`
  - `vllm/v1/worker/mamba_utils.py`

### Summary

**What changed and why**  
This PR fixes a race condition in Mamba state copies where overlapping source and destination ranges within the same physical block could cause incorrect results due to parallel memcpy-style loads/stores lacking memmove ordering. It modifies the fused GPU copy kernel for DS and SD convolution states to use ordered token-by-token copies for same-block left shifts, and adds a debug_barrier in the generic batch_memcpy kernel for left-overlap cases. Tests are expanded to verify memmove semantics against untouched snapshots across various biases, dtypes, and same/distinct block scenarios.

**Technical impact**  
The change ensures correct behavior for overlapping in-place left shifts in Mamba convolution state copies, fixing intermittent AMD CI failures. Performance impact is minimal: same-page SD copies incur a small latency increase (~1-2%), while distinct-page copies retain the tiled memcpy and DS copies see significant latency reduction (95-98% lower). The kernel now handles different element sizes (2, 4, 8 bytes) with appropriate pointer types, and the generic batch_memcpy adds a conditional debug_barrier for left overlaps, which may slightly reduce throughput in those cases.

**Potential risks**  
The ordered token copy loops in the kernel could be slower for large state sizes, though benchmarks show acceptable overhead. The debug_barrier in batch_memcpy is a synchronization point that could impact performance if many left-overlap copies occur. The change relies on precise overlap detection (dst_ptr < src_ptr and dst_ptr + size > src_ptr) which must be correct for all pointer alignments and sizes. Tests cover multiple dtypes and biases, but edge cases like zero-size copies or exact self-copies are handled separately and should be verified.

**Key insights**  
The PR correctly identifies that parallel memcpy-style operations do not guarantee memmove semantics for overlapping ranges, and addresses it by either using ordered copies or barriers. The design preserves performance for the common distinct-block case while adding safety for the rare same-block overlap. The test improvements are valuable: they compare against untouched snapshots rather than comparing Python vs GPU, which could hide shared bugs. The rebase over PR #49436 ensures compatibility with recent changes.

**What changed and why**

Previously, `_requires_logits_processing()` scanned multiple per-request NumPy/Python states on every sampling step. Now, the predicate is computed once in `add_request()` and stored in a compact boolean array, so the hot path only checks active rows via `idx_mapping_np`. This reduces per-step overhead and improves throughput, especially for CPU-bound decision paths.

**Technical impact**  
The change replaces a multi-array scan with a single boolean array lookup, reducing host-side decision time by ~70% in microbenchmarks and improving median output throughput by ~4.5% in a GPU-bound serving benchmark. It also adds unit tests covering cache correctness, slot reuse, active-subset filtering, and thinking-budget integration. The public API and downstream processor interfaces remain unchanged.

**Potential risks**  
The cached boolean must stay in sync with all underlying states. If any state is modified after `add_request()` without updating the cache, the sampler could incorrectly skip logits processing. The code relies on the fact that sampling parameters are immutable per request, but future changes to state mutation patterns could introduce subtle bugs. Additionally, the dependency on #52284 means the PR's first commit includes that change; if #52284 is not merged first, this PR may be incomplete or conflict.

**Key insights**  
The optimization leverages the observation that per-request sampling parameters are fixed at request start, so the combined predicate can be computed once. The active-subset filtering is preserved by indexing the cached array with `idx_mapping_np`. The tests specifically cover edge cases like slot reuse and active-subset filtering, ensuring the cache is correctly overwritten and only active requests are considered. The performance gains are most significant for CPU-bound scenarios, while GPU-bound models see negligible impact, as expected.
