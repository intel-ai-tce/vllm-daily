## 4. [[Bugfix] Avoid repeated layerwise reload warning scans](https://github.com/vllm-project/vllm/pull/49505)


### Base Information

- **PR Number:** #49505
- **Author:** [aoshen02](https://github.com/aoshen02)
- **Merged By:** [jeejeelee](https://github.com/jeejeelee)
- **Merged time:** 2026-08-11 22:53:50
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/49505/files) (2):**
  - `tests/model_executor/model_loader/test_reload.py`
  - `vllm/model_executor/model_loader/reload/layerwise.py`

### Summary

**What changed and why**  
This PR optimizes the layerwise reload warning logic in vLLM's online_process_loader. Previously, every weight tensor application during an online reload would scan all concurrently buffered layers, compute memory sizes, and trigger a warning_once call, even when the set of loading layers hadn't changed. This caused severe performance degradation (180x slowdown) and a warning storm (179,828 warnings) in large MoE reloads. The change now only evaluates the warning when a new layer is added to LOADING_LAYERS, and the detailed size/name calculation only runs when the set transitions from one to two loading layers. This preserves the useful signal (first overlap) while eliminating repeated work.

**Technical impact**  
The change reduces the time complexity of the warning block from O(N*M) per weight application to O(1) amortized, where N is the number of loading layers and M is the size of their buffered weights. It also fixes the warning_once cache issue by ensuring the arguments (memory total and layer names) are constant for a given overlap event. The PR includes a regression test that verifies the detailed size accounting runs exactly twice (once per layer) and the warning is emitted once. The end-to-end test on H200 shows a 180x speedup (6075.7s to 33.7s) and a 99.45% reduction in warnings.

**Potential risks**  
The change alters the condition for emitting the overlap warning: it now only fires when the set size is exactly two, not when it grows beyond two. This means if three or more layers are concurrently loading, the warning will not be emitted for the third layer. However, the warning is intended to signal the first overlap, so this is likely acceptable. There is a small risk that the 'layer not in LOADING_LAYERS' check could miss a case where a layer is re-added after being removed, but since LOADING_LAYERS is cleared appropriately, this is unlikely. The change is logging-only and does not affect tensor handling or inference correctness.

**Key insights**  
The PR identifies a classic performance anti-pattern: performing expensive work inside a hot loop that is idempotent and only needs to happen on state transitions. By moving the check to the transition point, the code becomes both faster and more correct in terms of warning suppression. The use of warning_once with changing arguments was a subtle bug that caused the warning to repeat; fixing the arguments to be stable is a key insight. The regression test is well-designed to catch regressions in the warning behavior without needing full model execution.

### Summary

**What changed and why**  
This PR fixes a bug in the Mamba align request handling where an externally loaded prefix that already provides all needed blocks for the first continuation was not marked as allocated. This caused a subsequent partial-tail copy-on-write to be misclassified as a first-prefill CoW, leading to core and worker disagreeing about the live Mamba state column. The fix adds the request to _allocated_block_reqs on the early-return path in allocate_new_blocks, ensuring the running-request CoW branch is used.

**Technical impact**  
The change is minimal (one line in the core manager) and ensures correct ownership bookkeeping for Mamba requests that resume from an external state. It preserves fine-grained partial-tail caching and prevents incorrect block replacement during continuation. A new regression test validates the fix by simulating the external-load sequence and asserting the live block remains in place and the partial-tail hash moves to the CoW target.

**Potential risks**  
The fix changes the allocation state for requests that previously were not marked allocated, which could affect other code paths that rely on this state. However, the change is limited to the early-return path when no new blocks are needed, and the test suite passes. There is a note that model evaluation has not been rerun, so production behavior at the affected geometry should be verified post-fix.

**Key insights**  
The root cause is a subtle interaction between external block allocation and the early-return path in allocate_new_blocks. Marking the request as allocated on that path is necessary to ensure consistent CoW semantics. The PR also clarifies that this is distinct from previous fixes (#51763, #51358) and does not suppress valid partial-tail caching.

## 60. [[Perf] Avoid repeated multimodal prompt update scans](https://github.com/vllm-project/vllm/pull/51774)


### Base Information

- **PR Number:** #51774
- **Author:** [gty111](https://github.com/gty111)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)
- **Merged time:** 2026-08-11 02:23:24
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/51774/files) (2):**
  - `tests/multimodal/test_processing.py`
  - `vllm/multimodal/processing/processor.py`

### Summary

**What changed and why**  
This PR optimizes the prompt update planning in vllm/multimodal/processing/processor.py to avoid quadratic behavior when many multimodal items share the same target. Previously, each non-empty replacement was applied one per round, and each round rescanned all unresolved items, leading to O(N²) processing. The change groups items with identical ordered (mode, target) choices into FIFO queues, so matching only examines the next item in each queue, making the common shared-target path linear in prompt length, output length, and item count. A new test verifies linear scaling for many shared targets.

**Technical impact**  
The core algorithm in _plan_prompt_updates is rewritten to use queues and a priority-based selection. It introduces helper functions _compile_prompt_update_queues, _find_queue_match, and _next_priority. The change preserves existing behavior for alternative targets, insertion/replacement modes, PromptIndex, overlapping matches, and modality priority. The performance benchmark shows a ~995x speedup on a synthetic case with 10,000 image placeholders and 1M input tokens. The change touches 2 files with +226/-121 lines, including a new test for linear scaling.

**Potential risks**  
The refactoring is complex and could introduce subtle bugs in edge cases, such as overlapping matches, mixed modes, or PromptIndex targets. The differential testing with 20,000 random cases provides some confidence, but not exhaustive. The new test only checks linear scaling for a simple shared-target scenario; it may not catch regressions in more complex interactions. The use of object identity for PromptIndex targets in _target_key could cause unexpected grouping if the same index object is reused across different items, but that is likely intended. Performance improvements are significant, but the code readability may suffer due to the added complexity.

**Key insights**  
The optimization leverages the observation that items with identical match rules can be processed in batches, avoiding repeated scans. The use of FIFO queues preserves original priority order while enabling O(1) access to the next candidate. The algorithm carefully separates empty and non-empty replacements to maintain the previous behavior of applying only one non-empty replacement per round. The PR includes a comprehensive test plan and a new performance regression test, indicating a strong commitment to correctness and performance.

## 63. [[MRV2][Spec] Fuse AR speculator multi-step decodes back into one CUDA graph](https://github.com/vllm-project/vllm/pull/46849)


### Base Information

- **PR Number:** #46849
- **Author:** [yiz-liu](https://github.com/yiz-liu)
- **Merged By:** [ZJY0516](https://github.com/ZJY0516)
- **Merged time:** 2026-08-11 00:06:23
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/46849/files) (10):**
  - `docs/design/model_runner_v2.md`
  - `tests/v1/worker/test_gpu_autoregressive_speculator.py`
  - `vllm/models/deepseek_v4/amd/rocm.py`
  - `vllm/v1/attention/backend.py`
  - `vllm/v1/attention/backends/flash_attn.py`
  - `vllm/v1/attention/backends/mla/sparse_swa.py`
  - `vllm/v1/attention/backends/mla/triton_mla.py`
  - `vllm/v1/attention/backends/triton_attn.py`
  - `vllm/v1/worker/gpu/spec_decode/autoregressive/speculator.py`
  - `vllm/v1/worker/utils.py`

### Summary

**What changed and why**  
This PR restores fused multi-step CUDA graph execution for autoregressive speculative decoding in Model Runner V2. Previously, each draft step rebuilt attention metadata and replayed a separate CUDA graph, causing per-step Python dispatch and launch overhead. The change captures the entire post-prefill draft loop into a single CUDA graph, building attention metadata once and updating step-dependent metadata in place between steps via a new backend hook.

**Technical impact**  
Adds a new `supports_draft_decode_metadata_update` flag and `update_draft_decode_metadata()` method to attention metadata builders. Backends like FlashAttention, DeepSeek sparse SWA, Triton Attention, and Triton MLA opt in, while others fall back to the previous per-step rebuild. The speculator now selects between `_multi_step_decode` and `_fused_multi_step_decode` based on backend support. Refactors FlashAttention scheduler metadata generation into reusable methods and adds tests for graph replay counts and metadata updates.

**Potential risks**  
The fused path relies on backend implementations being CUDA-graph capture-safe and keeping all replayed tensor state in persistent storage. Incorrect metadata updates could cause illegal memory access or incorrect attention, especially for complex backends like DeepSeek sparse SWA. The PR disables fused path for DCP and ROCm sparse SWA, but other backends may have subtle issues. Performance gains are not consistently observed in device-bound workloads, and the change adds complexity to the speculator and attention builders.

**Key insights**  
The PR addresses a historical illegal memory access that was not fully explained by stale metadata, suggesting other factors. The fused path reduces CPU overhead significantly (draft decode CPU span down ~58%) but shows mixed performance in device-bound scenarios. The design emphasizes backend opt-in and careful auditing of derived metadata, with a clear fallback for unsupported backends.
