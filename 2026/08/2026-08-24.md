## 1. [[Bugfix][MRV2] Dispatch uniform decode to a padded FULL cudagraph](https://github.com/vllm-project/vllm/pull/53407)


### Base Information

- **PR Number:** #53407
- **Author:** [xiaohuguo2023](https://github.com/xiaohuguo2023)
- **Merged By:** [LucasWilkinson](https://github.com/LucasWilkinson)
- **Merged time:** 2026-08-24 23:59:39
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53407/files) (2):**
  - `tests/v1/cudagraph/test_cudagraph_manager.py`
  - `vllm/v1/worker/gpu/cudagraph_utils.py`

### Summary

**What changed and why**  
This PR fixes a performance bug in CUDA graph dispatch for speculative decoding on ROCm. Previously, when the decode query length did not divide the capture ladder, some decode batches would fall back to eager attention (PIECEWISE mode) even though a larger FULL decode graph existed that could serve them with padding. The fix reorders candidate lists in _init_candidates so that FULL decode graphs are offered before PIECEWISE fallback, and adds a filter to only include FULL decode graphs with matching uniform_token_count. This ensures uniform decode batches are padded to the next available FULL graph, eliminating the eager-attention fallback for affected batch sizes.

**Technical impact**  
The change modifies the candidate list construction in vllm/v1/worker/gpu/cudagraph_utils.py, replacing the previous token-count-based range building with a mode-based approach that groups descriptors by mode and token count. It adds one candidate per query length for FULL decode graphs, reducing the number of candidates from 43 to 2 per token count on the default ladder. The change is gated behind current_platform.is_rocm(), so it is a no-op on CUDA. It also adds six new unit tests covering the fix, the ROCm gate, exact matches, mixed batches, fallback beyond the ladder, and dynamic speculative decoding scenarios.

**Potential risks**  
The change is gated to ROCm, so CUDA behavior is unchanged. However, there is a risk of subtle dispatch differences on ROCm for edge cases not covered by the tests, such as unusual capture ladders or dynamic speculative decoding configurations. The new candidate list construction uses groupby and setdefault, which could introduce ordering or deduplication issues if not handled correctly. The tests cover several scenarios but may not exhaustively cover all possible combinations of capture sizes, query lengths, and lora cases.

**Key insights**  
The bug was identified through profiling traces on MI355X, showing that half of decode batch sizes fell back to eager attention. The fix is elegant: it reuses existing captured graphs without adding new ones, and the exhaustive differential testing over 4440 reachable batches confirms that only PIECEWISE->FULL transitions occur, with no regressions. The narrowing to one candidate per query length is proven safe by testing 105576 reachable batches with zero differences, confirming that larger same-query-length graphs are unreachable. The end-to-end benchmark shows dramatic latency improvements (up to 80% reduction) for the affected concurrency levels.
