  - `vllm/model_executor/layers/fused_moe/oracle/mxfp4.py`

### Summary

**What changed and why**  
This PR modifies the MXFP4 rounding oracle to preserve native 128-aligned shard widths for AITER BF16/SiLU activations, specifically enabling DeepSeek-V4 TP8 to use a native 384-wide routed-expert shard instead of the previous 512-wide padded allocation. The change moves the rounding rule into the generic MXFP4 oracle, adds a regression test, and removes the need for AMD-specific subclassing.

**Technical impact**  
The change reduces model memory per rank by 31.25 GiB for DSV4 TP8, increasing available KV cache capacity and KV-token throughput by up to 82.76%. Performance benchmarks show up to 5.56% throughput gains at high concurrency and up to 47.45% request throughput improvement in agentic prefix-cache scenarios. The code change is minimal (6 lines in the oracle plus a test) and centralizes the alignment policy.

**Potential risks**  
Existing vLLM sharded_state snapshots that used the previous 256-alignment must be regenerated for DSV4 TP8, as physical shapes change. The change only affects AITER BF16/SiLU activations; other backends and activations retain existing alignment, but there is a risk of subtle kernel incompatibility if the AITER SiLU kernel does not fully support all native dimensions. The performance improvements are measured on specific hardware (gfx950) and may not generalize.

**Key insights**  
The PR demonstrates that physical padding in MXFP4 shard allocation was inflating memory usage without functional benefit, and that aligning to native kernel tile sizes (128) can yield significant memory and performance gains. The change is well-tested with a focused regression test and extensive performance validation, including memory, throughput, and model evaluation. The approach of centralizing the rounding rule in the generic oracle is clean and avoids model-specific special cases.

### Summary

**What changed and why**  
This PR introduces an adaptive budget for speculative decoding scheduled input tokens. Previously, the scheduler reserved a fixed number of draft slots based on max_num_seqs, which limited the token budget even when few requests were active. Now, the scheduler dynamically tracks the remaining input budget (max_num_batched_tokens) and subtracts draft slots per scheduled request, allowing more tokens to be scheduled when request count is low. This improves throughput and reduces TTFT, especially for low concurrency.

**Technical impact**  
The change modifies the scheduler's token budget calculation in vllm/v1/core/sched/scheduler.py and simplifies the max_num_scheduled_tokens configuration in vllm/config/vllm.py. It removes the conservative subtraction of draft slots based on max_num_seqs, instead enforcing a per-request draft slot reservation during scheduling. This allows the scheduler to utilize the full max_num_batched_tokens budget when few requests are present, while still preventing over-allocation of draft slots. Tests were added to verify the new behavior.

**Potential risks**  
The new logic relies on accurate tracking of input_budget across running and waiting requests. There is a risk of under- or over-allocation if the budget accounting is incorrect, especially in edge cases like preemption or when draft_slots is large. The change also alters the validation logic for max_num_scheduled_tokens, which could allow configurations that previously errored, potentially leading to runtime issues if the scheduler cannot handle the actual draft slot demand. The performance improvement is significant but may vary across different speculative decoding methods and hardware.

**Key insights**

### Summary

**What changed and why**  
This PR fixes a memory leak in the packed IPC weight transfer path. The producer exports its staging buffer once and ships the same rebuild args with every chunk, but the consumer rebuilt and released the mapping per chunk, causing the refcount to go negative and the producer buffer to become unreclaimable. The fix introduces a PackedBufferImporter cache that reuses the mapping across chunks of the same export and releases it exactly once per export, balancing the refcount.

**Technical impact**  
The change adds a one-slot import cache (PackedBufferImporter) owned by the receiving IPCWeightTransferEngine. It modifies packed_ipc_consumer to accept an optional importer parameter, defaulting to an ephemeral one for backward compatibility. **Potential risks**  
The importer caches the mapping keyed by rebuild args; if the same args are reused for different data (e.g., producer reuses the same buffer address for different content), the cached mapping might serve stale data. However, the PR notes that each chunk reads its current bytes from the aliased memory, so this is safe. Another risk is that if the consumer does not call finish_weight_update or shutdown, the mapping is only released on the next export, which could delay buffer reclamation. Also, the ephemeral importer in packed_ipc_consumer for single-chunk callers preserves old behavior but could still leak if used for multi-chunk transfers without sharing the importer.

**Key insights**  
The root cause is a mismatch between torch's refcount pairing (one export per release) and the per-chunk release in the consumer. Caching the rebuilt tensor across chunks restores the pairing. The fix is minimal and backward compatible, with a clear contract documented in the importer docstring. The test plan includes a two-process harness that verifies both memory flatness and data integrity, which is good coverage for the aliasing semantics.
