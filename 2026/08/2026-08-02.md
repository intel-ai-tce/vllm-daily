### Summary

**What changed and why**  
This PR migrates the unquantized (BF16/FP16/FP32) CPU MoE from the legacy monolithic path to the modular-kernel experts structure. It replaces the entangled CPUFusedMOE and SGLFusedMOE classes with three decoupled FusedMoEExpertsMonolithic subclasses (X86CPUUnquantizedExperts, ArmCPUUnquantizedExperts, TorchCPUUnquantizedExperts) selected by the oracle. The change removes the CPU escape hatches in UnquantizedFusedMoEMethod, deletes the old cpu_fused_moe.py, and moves routing helpers (select_experts, grouped_topk) into experts/cpu_moe.py. It also fixes FP16/FP32 on AMX hosts, removes the SGL MoE kernel, and adds vector operations for non-x86 architectures.

**Technical impact**  
The refactor aligns CPU MoE with the modular-kernel structure, enabling consistent backend selection and future maintainability. It changes behavior on x86: always uses grouped gemm, raising for unsupported swigluoai shapes instead of falling back to torch loop. It also fixes FP16/FP32 on AMX hosts by selecting the vector kernel. The removal of SGLFusedMOE simplifies the codebase. The change adds new vector operations (exp, er, tanh, clamp, unary minus) to CPU type headers for non-x86 architectures, and introduces INT8Vec64 reference implementations. The build system now includes cpu_fused_moe.cpp for all CPU architectures, and torch_bindings.cpp removes the AVX512/ARM guard for fused MoE ops.

**Potential risks**  
The main risk is the behavior change on x86: previously, unsupported swigluoai shapes silently fell back to the torch loop on non-AMX hosts, now they raise an error. This could break models that relied on that fallback. The removal of SGLFusedMOE might affect users who explicitly enabled VLLM_CPU_SGL_KERNEL for MoE, though the env var still works for linear layers. The new vector operations for non-x86 architectures (RISC-V, VSX, VXE) are only validated by code inspection, not tested on hardware, so there is a risk of subtle numerical or performance issues. The routing logic is preserved but moved, and the custom_routing_function path now forces contiguous tensors, which could introduce a slight overhead or change behavior if the custom function returned non-contiguous tensors.

**Key insights**  
The PR successfully unifies the CPU MoE backend with the modular-kernel structure, removing technical debt and improving consistency. The decision to raise on unsupported x86 shapes rather than fall back is a deliberate trade-off for performance, but it may require users to adjust tensor parallel size. The routing logic is carefully preserved by capturing router config in process_weights_after_loading, avoiding regressions for grouped-topk and custom routing models. The extensive test coverage and output-identity checks provide confidence, but the lack of hardware testing for non-x86 architectures is a gap that should be addressed in future work.

**What changed and why**  
This PR fixes a bug in the Mooncake KV connector where EAGLE state was not propagated across merged cache groups with identical specs. **Technical impact**

The _find_hit_blocks method now uses per-group eagle flags instead of a global set of attention group indices, and the store_mask logic (not shown but implied) will use the same eagle_group_ids to shift masks for all merged members. This restores external prefix-cache hits for DeepSeek-V4-style configurations without changing model outputs for non-EAGLE cases.

**Potential risks**  
The change touches core lookup and mask logic, and there is a potential conflict with open PR #48361 that modifies the same Mooncake lookup loop. The new tests cover the specific regression but do not include full model evaluation; the PR is a draft and requires validation on DeepSeek-V4 MTP+P/D serving. There is also a risk that the propagation logic might over-apply EAGLE to groups that should not have it, though the conservative fallback when no group is flagged remains.

**Key insights**  
The fix aligns the Mooncake connector's grouping semantics with the core coordinator's SpecGroup, which is the correct abstraction for merged groups. The regression tests are well-designed, simulating the exact DeepSeek-V4 five-group scenario and verifying both mask equality and round-trip hit length. The PR also includes a thorough duplicate-work check and AI assistance disclosure, showing good engineering practice.

## 14. [[Elastic EP] Fix non-contiguous weight transfers](https://github.com/vllm-project/vllm/pull/50641)


### Base Information

- **PR Number:** #50641
- **Author:** [itayalroy](https://github.com/itayalroy)
- **Merged By:** [tlrmchlsmth](https://github.com/tlrmchlsmth)
- **Merged time:** 2026-08-02 08:13:43
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50641/files) (1):**
  - `vllm/distributed/elastic_ep/elastic_execute.py`

### Summary

**What changed and why**  
Fixed a bug in Elastic EP weight transfer where non-contiguous tensor views were sent directly to PyNccl, which treats tensors as flat contiguous memory and ignores strides, causing incorrect weights on receivers. The fix ensures each weight tensor is made contiguous before transfer, and for non-contiguous tensors, transfers are done one at a time to limit temporary HBM usage, with received data copied back into the original tensor view.

**Technical impact**  
This change corrects weight transfer for non-contiguous tensors, which is critical for models like DeepSeek-V3 that have such views. It introduces a temporary contiguous buffer per non-contiguous tensor, potentially increasing HBM usage, but the one-at-a-time approach limits peak usage. Performance benchmarks show no measurable degradation, with slight improvements in mean and median transfer times.

**Potential risks**  
The one-at-a-time transfer for non-contiguous tensors could reduce parallelism compared to batched transfers, though benchmarks show no degradation. There is a risk of increased memory overhead if many non-contiguous tensors are transferred sequentially, but the approach mitigates this. Also, the code assumes `param.contiguous()` returns the same tensor if already contiguous, which is correct, but the logic for clearing p2p_ops and copying back must be correct for all cases.

**Key insights**  
The fix addresses a subtle issue with PyNccl's flat memory assumption. By making tensors contiguous before transfer and copying back after receive, correctness is ensured without significant performance loss. The code structure cleverly handles both contiguous and non-contiguous cases, batching contiguous ones and processing non-contiguous ones individually.
