**Key insights**

### Summary

**What changed and why**  
This PR fixes an overflow in the KV block zeroing kernel launch geometry. The old kernel flattened block, segment, and chunk indices into a single 1D grid, which could exceed the signed 32-bit limit for large configurations like DeepSeek-V4. The change maps these indices directly onto a 3D grid, uses a wider chunk size (up to 1024 elements) with masking for tail segments, and adjusts the chunk count calculation accordingly. This reduces the number of programs launched and prevents the overflow.

**Technical impact**  
The kernel signature changes: removed n_blocks, N_SEGS, and MAX_CHUNKS parameters, and now uses 3D program IDs. The chunk size is now based on the maximum page size instead of the minimum power-of-two divisor, and the chunk count is computed with ceiling division. The grid is now (n_blocks, n_segs, max_chunks) instead of a single flattened dimension. Tests were updated to reflect the new geometry and add a regression test for the DeepSeek-V4 shape.

**Potential risks**  
The new masking logic (cols < page_size_el) must correctly handle cases where the page size is not a multiple of the chunk size. The change from power-of-two divisor to a power-of-two chunk size based on max page size could affect performance for heterogeneous page sizes, but the PR claims a 233.6x reduction in programs. There is a risk of introducing off-by-one errors in the chunk count calculation, but tests cover the new geometry. The kernel now relies on the 3D grid limits (x, y, z) which are typically 2^31-1, 65535, 65535 on CUDA; the y and z dimensions are within limits for the tested case.

**Key insights**  
The PR correctly identifies that the previous approach of using the smallest power-of-two divisor across all segments caused excessive program launches. By using the maximum page size and masking, it reduces the number of chunks per segment. The change also removes the need for do_not_specialize on n_blocks, simplifying the kernel. The test plan includes compute-sanitizer and a B200 validation, indicating thorough testing. The PR also distinguishes itself from a revert PR (#52062) by preserving the generalized zeroing feature.
