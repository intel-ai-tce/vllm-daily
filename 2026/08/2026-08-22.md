**What changed and why**  
This PR simplifies the multimodal prompt update system by replacing the `PromptSeq` union type (`str \\| list[int]`) with `list[int]` everywhere. The core motivation is to remove the tokenizer dependency from the prompt matching logic, making the engine tokenizer-free. This involves converting all text-based targets and replacements to token IDs, removing text-specific matching functions, and moving the BPE fallback into a private helper owned by `BaseMultiModalProcessor`.

**Technical impact**  
The change removes the tokenizer parameter from key functions like `iter_token_matches`, `_plan_prompt_updates`, `apply_token_matches`, and `find_mm_placeholders`, simplifying the API. It deletes the `PromptSeq` alias, `_S` TypeVar, and several text-based helper functions. The `PromptUpdateDetails` class is no longer generic and now always holds `list[int]`. The BPE fallback for non-special-token targets is preserved but privatized and moved to the processor, keeping the engine tokenizer-free. Many model files are updated to encode text placeholders to token IDs using the new `cached_encode` helper.

**Potential risks**  
The main risk is that converting text to token IDs may change behavior if the tokenizer encodes text differently in different contexts (e.g., BPE merges). The fallback handles this but only for non-special tokens. There is also a risk of performance regression due to additional tokenizer calls, though caching is used. The change touches many model files, increasing the chance of subtle bugs in prompt update logic. The removal of text-based matching could break models that relied on string matching for placeholders that are not single tokens.

**Key insights**  
The PR successfully decouples the prompt matching engine from the tokenizer, which is a significant architectural improvement. The careful preservation of the BPE fallback shows awareness of tokenization edge cases. The use of `cached_encode` helps mitigate performance concerns. The change is large but well-structured, with clear documentation updates and test adjustments.

**Key insights**  
The change correctly subtracts setup time from the timeout budget, ensuring the teardown minute is reserved. ## 10. [[Core][RL] Support sparse checkpoint updates through native weight loaders](https://github.com/vllm-project/vllm/pull/50723)


### Base Information

- **PR Number:** #50723
- **Author:** [ShuoleiWang](https://github.com/ShuoleiWang)
- **Merged By:** [Isotr0py](https://github.com/Isotr0py)
- **Merged time:** 2026-08-22 10:39:59
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50723/files) (2):**
  - `tests/model_executor/model_loader/test_checkpoint_weight_patch.py`
  - `vllm/model_executor/model_loader/checkpoint_weight_patch.py`

### Summary

**What changed and why**  
This PR introduces a new API for applying dense or sparse weight updates in checkpoint coordinates, leveraging the model's native load_weights method. It adds a CheckpointWeightPatch named tuple and a load_checkpoint_weight_patches function that validates patches, batches them, and for sparse updates uses NaN-masked tensors with a temporary torch.Tensor.copy_ override to preserve unchanged values. The change addresses the need to bridge checkpoint-coordinate updates from RL trainers to vLLM's runtime parameter coordinates, supporting TP/EP and packed layouts.

**Technical impact**  
Adds a new module (checkpoint_weight_patch.py) with ~273 lines and a test file with ~110 lines. The API enables efficient sparse updates by only transferring changed indices/values, reducing weight sync time significantly (7.2x speedup in companion integration). It introduces a global monkey-patch of torch.Tensor.copy_ during sparse loading, which is serialized and restored in a finally block. The implementation includes validation for patch structure, index ranges, duplicates, and NaN sentinel usage, and supports batching by byte size.

**Potential risks**  
The temporary monkey-patching of torch.Tensor.copy_ is process-wide and could interfere with concurrent operations if not properly serialized; the PR assumes exclusive access. Sparse updates are not transactional; a loader error can leave partial updates, requiring external rollback. The NaN sentinel approach fails if the checkpoint dtype is not floating-point or if NaN is a legitimate value. The implementation is narrow: it only supports single-copy loaders and same-shaped floating-point final copy_ calls; composed or custom loaders will raise NotImplementedError. Performance is not O(nnz) as it allocates full checkpoint-shaped tensors, which could be memory-intensive for large models.

**Key insights**  
The design cleverly reuses the native load_weights path to handle complex mappings (TP/EP, packed) without duplicating logic. The NaN-masking technique is a simple yet effective way to preserve unchanged values during sparse updates. The batching by bytes and repeated-name handling ensure correct ordering and memory control. The companion VERL integration demonstrates substantial performance gains, but correctness is only validated on a representative probe, not full training trajectories.
