## 1. [Replicated embedding and norm fusion for DSV3 flat model](https://github.com/vllm-project/vllm/pull/48484)


### Base Information

- **PR Number:** #48484

- **[Changed Files](https://github.com/vllm-project/vllm/pull/48484/files) (5):**
  - `tests/kernels/core/test_fused_embed_norm.py`
  - `vllm/envs.py`
  - `vllm/model_executor/layers/fused_embed_norm.py`
  - `vllm/models/deepseek_v32/nvidia/model.py`
  - `vllm/models/deepseek_v32/nvidia/mtp.py`

### Summary

**What changed and why**  
This PR introduces an optional replicated embedding path (VLLM_REPLICATE_EMBED) for the DSV3 flat model, where the full embedding table is replicated on every TP rank instead of being vocab-parallel. This enables fusing the embedding gather with the first layer's RMSNorm and the MTP eh-norm, reducing all-reduce overhead and improving latency/throughput, especially at low concurrency. The change adds new Triton kernels (fused_embed_norm and fused_embed_eh_norm), a new module (fused_embed_norm.py), an environment variable, and modifies the model and MTP code to use the fused path when the table is replicated.

**Technical impact**  
The change adds a new environment variable (VLLM_REPLICATE_EMBED) that, when enabled, replicates the embedding table across TP ranks and uses fused Triton kernels to combine embedding lookup with normalization. This removes the all-reduce for embedding outputs, reducing communication overhead. The fused kernels are bit-exact with the unfused reference, as verified by unit tests. The change also adds a new module and modifies the model and MTP forward paths to conditionally use the fused kernels. Performance improvements are observed at low concurrency (up to 7% ITL reduction and 5% throughput gain at concurrency 1), but diminish at higher concurrency.

**Potential risks**  
The replicated embedding increases memory usage per rank (full table on each rank), which could be significant for large vocabularies. The feature is disabled by default, so it is opt-in. Tied word embeddings are rejected at TP>1 when the feature is enabled, which could break configurations that rely on weight tying. The fused kernels are only used when the full vocab is on-rank and the weight is unquantized; if these conditions are not met, the code falls back to the original path, but this fallback logic must be correct. The performance gains are only significant at low concurrency; at higher concurrency the gains are within noise, so the feature may not be beneficial for all workloads. The new Triton kernels may have edge cases (e.g., H not a power of two) that are handled but not exhaustively tested.

**Key insights**  
The PR demonstrates a clear trade-off: replicating the embedding table reduces communication overhead at the cost of increased memory, and the benefit is most pronounced when the number of tokens per step is small (low concurrency). The fused kernels are designed to be bit-exact, ensuring no accuracy impact. The implementation is modular, with the fused kernels placed in a self-contained module, and the model code uses a predicate (has_full_vocab_on_rank) to decide whether to use the fused path. The performance data shows that the all-reduce cost is constant per step, so its relative impact decreases with more tokens per step, explaining the diminishing returns at higher concurrency.
