  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/events.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`

### Summary

**What changed and why**  
This PR enhances the KV offloading event system to emit self-describing events for partial recurrent blocks (e.g., Mamba/SSM groups) in full-attention cache groups. Previously, partial recurrent tails used placeholder events with empty token_ids and block_size=0. Now, the scheduler records metadata for partial tails during store and lookup operations, and the event tracker translates them into self-describing BlockStored events with hash-aligned token ranges and block sizes. Sliding-window groups intentionally retain the placeholder behavior.

**Technical impact**  
The change adds new methods (record_partial_store, record_partial_lookup, _record_partial_tail) to the events tracker, and modifies the scheduler to call these methods when handling partial tail stores and lookups. It also removes a condition that previously disabled partial tail support when self-describing events were enabled. This enables external consumers to index offloaded partial blocks accurately, improving observability and potentially enabling more efficient cache reuse. The change is backward compatible as it only affects behavior when self_describing_kv_events is enabled.

**Potential risks**  
The new logic relies on assumptions about token boundaries and hash alignment (assertions in _record_partial_tail). If these assumptions are violated in edge cases (e.g., unusual token counts or hash configurations), it could cause assertion failures or incorrect metadata. The change also modifies the scheduler's partial tail lookup path, which could affect performance or correctness if the new record_partial_lookup calls introduce unexpected side effects. Additionally, the removal of the condition in _alignment_chunk_count might enable partial tail support in scenarios that were previously disabled, potentially exposing untested code paths.

**Key insights**  
The PR carefully distinguishes between full-attention groups (which get self-describing events) and sliding-window/SSM groups (which keep placeholders). The implementation uses hash-aligned boundaries to compute the valid prefix of a physical block, ensuring that token_ids and block_hashes are consistent. The tests cover both store and lookup paths, and verify that sliding-window groups still produce placeholders. The documentation update clarifies the new behavior for partial recurrent tails.

  - `vllm/v1/kv_offload/tiering/fs/manager.py`
  - `vllm/v1/kv_offload/tiering/obj/manager.py`

### Summary

**What changed and why**  
This PR fixes a livelock in the KV offload tiering layer where a failed secondary-tier load (e.g., due to a truncated or unreadable block file) leaves a stale positive lookup verdict in the async lookup cache, causing the scheduler to repeatedly re-issue the same doomed promotion. The fix marks the cached verdict as a miss on failed loads, narrows file deletion to only provable short reads, and adds partial-success reporting for batched loads. It also adds regression tests and enforces an enqueue-once invariant in the lookup cache to prevent stale results from resurrecting a corrected verdict.

**Technical impact**  
The change modifies the async lookup manager to support marking cached verdicts as misses, and updates both the filesystem and object tier managers to track in-flight load job keys and mark failed keys as misses in get_finished_jobs. The filesystem load path now only deletes files on short reads, and batched loads report the number of successfully loaded blocks before a failure. This prevents the livelock and reduces unnecessary I/O, while preserving valid data on transient errors. The change also adds an assertion in drain_results to enforce that each key is enqueued only once, preventing duplicate results from overwriting a corrected miss.

**Potential risks**  
The new mark_miss logic relies on the assumption that a failed load always indicates the block is unavailable, which may not hold for transient errors that do not delete the file; however, the code only marks misses on actual load failures, and the file is only deleted on short reads. The partial-success reporting adds complexity and relies on the C extension and Python fallback both setting the num_succeeded attribute consistently. The enqueue-once assertion could trigger false positives if there are legitimate scenarios where a key is probed more than once, though the tests cover normal operation. There is also a small risk of memory leaks if _load_job_keys entries are not cleaned up on successful loads (they are popped in get_finished_jobs, but if a job never finishes, the entry remains).

**Key insights**  
The fix is well-targeted and addresses the root cause of the livelock by correcting the cached verdict on failure. The decision to only delete files on short reads is a good balance between cleaning up corruption and avoiding data loss on transient errors. The partial-success reporting for batched loads is a thoughtful enhancement that preserves valid data. The tests are comprehensive, covering both C and Python paths, and the mutation-checking approach adds confidence. The enqueue-once invariant is a strong safeguard against future regressions.
