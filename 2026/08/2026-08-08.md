### Summary

**What changed and why**  
This PR ports a memory leak fix for stable ABI string conversions from PyTorch 2.14 to the 2.13 build. It adds a CMake patch mechanism that detects the affected header in PyTorch 2.13 and applies a patch to replace a heap-allocated std::string with a stack-allocated one, preventing a memory leak. The patch is conditional on the Torch version being >=2.13 and <2.14, and is intended to be reverted after upgrading to 2.14.

**Technical impact**  
The change introduces a build-time patch step that modifies the PyTorch stable ABI header in the build directory. It adds a shadow include directory that takes precedence over the original headers, ensuring the patched version is used. This fixes a memory leak in the stable ABI string conversion path, which could cause memory growth in long-running processes. The change is scoped to PyTorch 2.13 and does not affect other versions.

**Potential risks**  
The patch relies on the exact content of the header matching the expected pattern; if PyTorch updates the header in a patch release (e.g., 2.13.1), the patch may fail to apply, causing the build to fail. The use of `patch` command assumes it is available in the build environment. The shadow include directory could mask other header changes if not cleaned up properly. There is also a risk that the patch is not applied when building with certain configurations (e.g., if TORCH_INCLUDE_DIRS is empty or has multiple entries).

**Key insights**  
The PR demonstrates a pragmatic approach to backporting a fix without changing the supported version range. The conditional version check and the comment to revert after 2.14 show awareness of the temporary nature. The patch is minimal and directly addresses the memory leak by avoiding a heap allocation. The use of a shadow include directory is a clean way to override the header without modifying the installed PyTorch package.

**Technical impact**  
This is a bug fix in the offline LLMEngine metrics path. It ensures prefix-cache hit/query counters are accurately recorded even on zero-output steps, aligning the sync path with the async path. There is a small risk that iteration_stats being None on zero-output steps could cause issues if downstream code expects a non-None value, but the existing code already tolerates None on other paths. No other risks identified.

**Key insights**  
The bug was specific to the synchronous LLMEngine path and was empirically observed on GB200 with hybrid-Mamba, where prefix-cache hits were being dropped. The fix is a one-line condition removal plus a guard for iteration stats, demonstrating that subtle metric recording conditions can lead to silent data loss. The PR is well-scoped and includes a clear test plan with concrete before/after metrics.

### Summary

**What changed and why**  
This PR reworks the GPU sync check mechanism to be thread-local and fixes its suppressors. The previous implementation used torch's process-global sync debug mode, which caused background threads to raise on deliberate syncs and allowed any thread to disarm the check globally. The new approach arms torch at 'warn' mode and uses a warnings hook plus ContextVars to scope enforcement per thread and per asyncio task. It also fixes the compile-time suppressors to work during torch compilation and adds regression tests.

**Technical impact**  
The change replaces global state with thread-local ContextVars, improving correctness in multi-threaded environments. It also reduces the disabled-path overhead of gpu_sync_allowed() from ~1.7us to ~110ns by caching the env var and using a shared no-op context manager. The warning hook is re-asserted per checked call to work with pytest's warnings.catch_warnings(). The compile-time suppressors now use a dedicated _allow_syncs() context that bypasses gpu_sync_allowed()'s no-op during compilation, and they also cover inductor's cudagraph tree setup.

**Potential risks**  
The new warning hook and filter manipulation could interfere with other warning handling in the application, especially if other code installs its own showwarning hook. The per-call arming and refcounting of the sync debug mode adds complexity and potential race conditions if not properly locked. The suppressors patch internal torch modules, which may break with future torch versions. The tests rely on monkeypatching module attributes instead of env vars, which could be fragile if the implementation changes.

**Key insights**  
The PR correctly identifies that torch's sync debug mode is process-global and not suitable for thread-local enforcement. Using ContextVars for scoping is a clean solution. The fix for the suppressors is important because gpu_sync_allowed() no-ops during compilation, making it ineffective for compile-time syncs. The performance optimization for the disabled path is a nice touch, showing attention to hot-path overhead.

## 9. [[Perf][Sparse MLA] Drop the atomic contention in the index remap](https://github.com/vllm-project/vllm/pull/50365)


### Base Information

- **PR Number:** #50365
- **Author:** [njhill](https://github.com/njhill)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-08-08 16:32:40
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/50365/files) (3):**
  - `tests/v1/attention/test_indexer_dcp_localize.py`
  - `tests/v1/attention/test_sparse_mla_backends.py`
  - `vllm/v1/attention/backends/mla/sparse_utils.py`

### Summary

**What changed and why**  
This PR optimizes the sparse-MLA index remap kernel by eliminating atomic contention when counting valid indices per row. Previously, each row was split into multiple column tiles, and each tile atomically added its valid count to a shared per-row counter, causing 16-way contention on wide rows. The change gives one program the entire row when the row width is a power of two and counting is enabled, turning the count into an in-register reduction with a plain store, and making the compaction base statically zero. This removes the need for zero-initialization of the counter buffer in that path and improves performance significantly, especially for larger tile counts.

**Technical impact**  
The kernel now selects between a single-tile path (power-of-two row width and counting enabled) and the existing multi-tile atomic path. The single-tile path uses a larger block size (NUM_TOPK_TOKENS) and more warps (8 vs 4), reducing launch overhead and eliminating atomics. The valid-count buffer allocation changes from torch.zeros to torch.empty when single-tile, saving initialization cost. Tests were updated to cover non-power-of-two widths (384) to ensure the atomic path remains correct. Performance gains range from 1.5x to 3.18x on GB200, with larger gains for wider rows.

**Potential risks**  
The single-tile path is only used when NUM_TOPK_TOKENS is a power of two; for non-power-of-two sizes, the atomic path remains, so no regression there. The change relies on Triton's tl.cumsum and tl.sum behavior within a single program, which should be correct but could have edge cases with very large row widths exceeding register limits. The test modifications increase coverage but also introduce new parameterizations that could be flaky if random ranges are not carefully bounded. The performance improvement is measured on specific hardware and may not translate identically to other GPUs.

**Key insights**  
The optimization leverages the observation that counting is the only cross-tile dependency; by giving one program the whole row, the count becomes a local reduction. This is a classic trade-off between parallelism and synchronization: using fewer, larger programs can reduce contention and improve efficiency when the workload is memory-bound. The PR also demonstrates a thoughtful approach to testing by adding non-power-of-two sizes to ensure the fallback path remains correct.
