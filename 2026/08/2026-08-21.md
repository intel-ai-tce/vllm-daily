## 1. [[Refactor][Model Runner V2][Multimodal] Move the encoder-only path out of the shared runner](https://github.com/vllm-project/vllm/pull/53176)

  - `vllm/v1/worker/gpu_worker.py`
  - `vllm/v1/worker/mm_encoder_model_runner.py`

### Summary

**What changed and why**  
This PR refactors the V2 model runner to extract the encoder-only execution path into a dedicated MMEncoderModelRunner subclass. Previously, encoder-only logic was scattered across the shared GPUModelRunner via is_encoder_only branches. The new subclass overrides methods like get_kv_cache_spec, capture_model, _dummy_run, and execute_model to handle encoder-only behavior, and the worker selects it based on vllm_config.is_mm_encoder_only. The change also renames is_encoder_only to is_mm_encoder_only and adds a check to disable prefix caching for encoder-only instances. The primary motivation is to fix an illegal memory access caused by UvaBufferPool slot recycling without proper synchronization in encoder-only steps; the new subclass introduces a blocking event-based semaphore to synchronize host writes with device reads.

**Technical impact**  
The shared GPUModelRunner is simplified by removing encoder-only branches, reducing code complexity and maintenance burden. The new MMEncoderModelRunner inherits most functionality but overrides key methods to skip LM-related operations, avoiding unnecessary work. The input_tensor_semaphore context manager ensures that host writes to pooled buffers are synchronized with device execution, preventing race conditions. The rename of is_encoder_only to is_mm_encoder_only clarifies its scope and is propagated through scheduler and warmup code. The addition of prefix caching disablement for encoder-only instances prevents potential issues with coordinator groups. Tests were updated to reflect the rename, and the change is backward-compatible for normal multimodal serving.

**Potential risks**  
The new synchronization mechanism using blocking events could introduce performance overhead if not properly tuned, though it only applies to encoder-only instances. The subclass relies on assumptions like dp_size == 1 and supports_mm_inputs, which are asserted but could be violated in edge cases. The rename of is_encoder_only to is_mm_encoder_only might break external code that references the old property, though it's likely internal. The change to disable prefix caching for encoder-only instances could affect performance if prefix caching was previously used, but it's logically correct since no KV cache exists. The refactor touches multiple files and could introduce subtle bugs if the overridden methods don't exactly replicate the original behavior, but tests cover the main paths.

**Key insights**  
The root cause of the illegal memory access was a missing device synchronization in encoder-only steps, which the new semaphore elegantly addresses by reusing the existing event mechanism. The refactor improves code organization by isolating a distinct execution mode, making the shared runner cleaner and easier to reason about. The change also demonstrates a good pattern for handling special cases in complex systems: instead of scattering conditionals, create a subclass that encapsulates the differences. The extensive testing with 35,000 producer requests and zero crashes provides strong confidence in the fix.

### Summary

**What changed and why**  
This PR fixes a bug in the fused Triton MXFP8 quantizer on ROCm where the shared block scale was computed using floor(log2(amax)) + 127, mapping the block maximum to 1.0 instead of the top of the e4m3 range. This caused small elements to fall into the subnormal region, leading to drift from the torch reference. The fix changes the scale calculation to ceil(log2(amax / FP8_MAX)) + 127, matching the torch reference, and passes FP8_MAX and TINY as constexprs to avoid hardcoding.

**Technical impact**  
The change modifies the Triton kernel's scale computation and adds two new constexpr parameters (FP8_MAX and TINY) to the kernel launch. This ensures the Triton path produces results consistent with the torch reference on ROCm, fixing test failures in the MXFP8 quantization tests. The change is isolated to the ROCm-specific Triton path and does not affect CUDA behavior.

**Potential risks**  
The change could affect numerical precision or performance on ROCm, but it aligns with the torch reference and should improve accuracy. There is a slight risk of performance impact due to the additional division and ceil operation, but it is likely negligible. The change is limited to a single file and only affects the ROCm Triton path, so the risk is low.

**Key insights**  
The bug was specific to ROCm because the Triton kernel is only used on ROCm for the 2D non-swizzled activation-quant case. The fix ensures consistency with the torch reference by using the same exponent calculation and passing the e4m3 limit and tiny value as constexprs, avoiding hardcoded values. The test plan includes a dedicated test file that exercises the Triton path against the torch reference, and the fix passes all 55 tests on MI355.

**What changed and why**  
This PR standardizes the KV cache layout across vLLM by introducing a KVCacheLayout enum that enumerates physical stride permutations for the logical [L, B, H, N, C] shape. It removes per-backend cache-shape and stride-order hooks, centralizes layout resolution in CacheConfig with a single writer (attention-backend selection), and updates all consumers (attention backends, KV connectors, offloading, tests) to use standardized views. The change also renames legacy layout names (NHD/HND) to new enum names (LBNHC/LBHNC) with aliases, and replaces compress_ratio with tokens_per_state for MLA compression.

**Technical impact**  
This is a large refactor touching 150 files with +3993/-5802 lines. It changes the core KV cache allocation and view creation logic, affecting all attention backends, KV connectors (Nixl, Mooncake, Offloading, etc.), and model runners. The new layout resolution flow runs in the engine core before memory profiling and propagates to workers via RPC and KVCacheConfig. This introduces new abstractions (KVCacheLayout, compute_layout_strides, create_kv_cache_views) and removes legacy methods (get_kv_cache_shape, get_kv_cache_stride_order, indexes_kv_by_block_stride). It also changes the MLA spec field from compress_ratio to tokens_per_state, which may affect model configurations and serialized artifacts.

**Potential risks**  
The change is massive and touches many subsystems, increasing the risk of subtle regressions in KV cache memory layout, especially for less common backends (e.g., ROCm, HPC, TurboQuant) and connectors. The removal of per-backend stride hooks means all backends must correctly declare supported layouts; any missed backend could cause incorrect memory access. The rename of layout names (NHD->LBNHC, HND->LBHNC) could break external integrations that rely on the old names, despite aliases. The change to tokens_per_state may break existing model configs that use compress_ratio. The new layout resolution logic has complex preference ordering and intersection logic that could fail for models with mixed specs. The PR also modifies the Nixl compatibility hash version, which could cause handshake failures between old and new versions.

**Key insights**  
The PR is a foundational refactor that simplifies the KV cache layout system by making the logical shape uniform and moving layout decisions to a single point. It removes a lot of duplicated per-backend logic, which should improve maintainability. The introduction of KVCacheLayout as an enum with properties like is_block_compact and is_layer_compact provides a clear way to reason about physical layouts. The change also enables cross-layer layouts (e.g., BLHNC) to be expressed uniformly, which is important for KV transfer performance. The extensive test updates indicate a thorough effort to cover the new abstractions, but the sheer size of the change warrants careful review and testing.

This PR adds parallelism to long-running Intel GPU CI tests by introducing Buildkite parallelism settings and pytest sharding. It modifies CI configuration files to set parallelism levels for specific test steps and updates the test runner script to pass shard environment variables and PYTEST_ADDOPTS into the Docker container, enabling pytest-xdist's --num-shards and --shard-id options.

**Technical impact**  
The change reduces wall-clock time for long-running Intel GPU test suites by splitting them across multiple parallel agents. It requires pytest-xdist to be installed in the test environment, and the sharding logic is conditionally applied only when BUILDKITE_PARALLEL_JOB_COUNT is greater than 1, preserving existing behavior for non-parallel runs. The script also ensures PYTEST_ADDOPTS is exported into the container so sharding options are honored.

**Potential risks**  
Potential risks include: if pytest-xdist is not installed, the sharding options will cause errors; sharding may lead to uneven test distribution or resource contention on GPU agents; the combined pytest command for multiple test files may have different failure reporting or require proper test isolation; environment variable propagation must be correct to avoid sharding not being applied.

**Key insights**  
The PR leverages Buildkite's built-in parallelism feature and pytest-xdist's sharding to parallelize CI tests. The conditional logic in the shell script ensures backward compatibility. The changes are focused on CI infrastructure and do not alter product code behavior.
