### Base Information

- **PR Number:** #49608
- **Author:** [almogtavor](https://github.com/almogtavor)

  - `vllm/v1/engine/async_llm.py`
  - `vllm/v1/engine/input_processor.py`

### Summary

**What changed and why**  
This PR offloads raw-prompt preprocessing (tokenization and multimodal processing) from the asyncio event loop to the renderer's thread pool in AsyncLLM.add_request(). It fixes #49317, where synchronous preprocessing blocked the event loop and serialized concurrent multimodal requests, leaving the GPU idle. The change adds an async variant of process_inputs (process_inputs_async) using the existing make_async helper and the renderer's executor, and uses it for raw prompts while keeping the synchronous path for already-rendered EngineInput dicts.

**Technical impact**  
The change introduces a new method process_inputs_async on InputProcessor, which wraps the synchronous process_inputs to run on the renderer's thread pool. In AsyncLLM.add_request(), the code now checks if the prompt is a dict with a 'type' key (indicating rendered EngineInput) to decide between synchronous and async processing. This keeps the hot serving path unchanged for pre-rendered inputs, while raw prompts benefit from offloading. The streaming-input path is left unchanged, as noted in the PR.

**Potential risks**  
Potential risks include: (1) The check for rendered EngineInput relies on the presence of 'type' in the prompt dict, which might be fragile if other dict prompts without 'type' are used; (2) The async path uses the renderer's executor, which might be shared with other async operations, potentially causing contention or deadlocks if not properly managed; (3) The change could introduce subtle differences in error handling or ordering because the async call is awaited, but the synchronous path is not; (4) The test added requires CUDA and may not run in all CI environments, limiting coverage.

**Key insights**  
The PR correctly identifies a performance bottleneck in AsyncLLM for raw prompts and leverages existing infrastructure (make_async and renderer's executor) to offload blocking work without introducing a new thread pool. The decision to keep the synchronous path for rendered EngineInputs is sensible to avoid unnecessary overhead. The change is minimal and focused, with a clear test plan. However, the reliance on the 'type' key for distinguishing raw vs rendered prompts could be improved by using a more explicit type check or a dedicated flag.

### Summary

**What changed and why**  
Fixes a causality bug in the ROCm AITER MLA backend's small-head verify flatten path. Previously, when num_heads < 16, a multi-token verify block was flattened into single-token Gluon decodes, each row receiving the entire paged-KV range for its request, allowing verify positions to attend to future draft tokens. The change adjusts the row lengths to be causal (row t gets context + t + 1 entries) and updates comments accordingly. A regression test was added to verify the causal masking.

**Technical impact**  
Alters the KV window computation in forward_mqa for the sub-16-head flatten path. Row lengths are now computed as per_req_len - (qlen - 1) + t, clamped to zero, and min_kv_seq_len is updated to reflect the shortest row. This reduces KV work and ensures correct causal attention, potentially affecting performance and correctness for affected configurations.

**Potential risks**  
The change may alter behavior for configurations that previously worked (e.g., head counts dividing 16) by now applying causal masking where full-range attention was used, potentially affecting throughput or numerical results. The fix relies on paged_kv_indices being in ascending order, which is assumed but not explicitly enforced. The test only spies the kernel, not running it, so end-to-end correctness is not fully validated.

**Key insights**  
The bug was subtle because it produced plausible outputs and even appeared as a throughput win, making it hard to detect without inspecting the KV window. The fix leverages the existing structure of paged_kv_indptr and paged_kv_indices to implement causal masking without additional indexing overhead. The regression test is well-designed to catch the issue by asserting exact row lengths and page prefixes.
