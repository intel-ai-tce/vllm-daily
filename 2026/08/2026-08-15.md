## 3. [[Bugfix][DSv4] Revert adaptive C128A metadata packing](https://github.com/vllm-project/vllm/pull/51318)


### Base Information

- **PR Number:** #51318
- **Author:** [tobymao](https://github.com/tobymao)
- **Merged By:** [ywang96](https://github.com/ywang96)
- **Merged time:** 2026-08-15 18:39:24
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/51318/files) (2):**
  - `tests/kernels/attention/test_flashmla_sparse.py`
  - `vllm/models/deepseek_v4/sparse_mla.py`

### Summary

**What changed and why**  
This PR reverts the adaptive C128A top-k width and packed persistent-buffer views introduced in #50004. The revert is necessary because the C128A metadata builder runs before FULL CUDA graph replay, but the sparse decode consumer is captured and reuses its capture-time row layout. With the adaptive width, runtime metadata writes packed rows using a batch-dependent active_topk_width, while the captured consumer retained the capture-time row stride, causing stale offsets for rows beyond the first. The change restores the fixed c128a_max_compressed width, capacity-strided slices of the persistent buffers, and uses each buffer's stride(0) for Triton metadata writes. It also removes the test that asserted the packed layout being reverted.

**Technical impact**  
The change restores deterministic metadata layout for CUDA graph replay, ensuring that the captured sparse decode consumer reads correct row offsets. It simplifies the buffer slicing logic by using capacity-strided views instead of packed views, which aligns with the pre-#50004 behavior. The kernel invocation now passes the buffer stride(0) as the row stride, which is constant across batches, maintaining graph compatibility. The removal of the test reduces coverage for the packed layout but aligns with the reverted behavior.

**Potential risks**  
The revert may reintroduce the original issue that #50004 aimed to fix, such as potential memory inefficiency or performance degradation due to using the maximum compressed width instead of adaptive widths. However, the PR validation shows no issue-signature hits and zero errors on the reported scenario, suggesting the revert resolves the bug without regressions. There is a risk that other code paths or future changes might rely on the adaptive width behavior, but the PR description indicates this is a targeted revert to fix a specific bug.

**Key insights**  
The core insight is that CUDA graph capture requires static memory layouts; any batch-dependent size or stride changes during runtime can cause silent data corruption. The revert prioritizes correctness and graph stability over potential memory savings from adaptive widths. The validation on GB300 hardware with the exact issue scenario provides strong evidence that the revert fixes the reported problem. The PR also notes that this is an update to an existing PR (#51318) rather than a new one, indicating a collaborative fix process.
